## 1. 製品方針と対象範囲

### 1.1 決定済みのコンセプト

3D Theater は、**MMD型の3Dアニメーション制作に特化**する。既存のモデル・モーションを読み込み、ボーン、表情、カメラ、照明、物理演算、タイムラインを編集し、静止画・動画へ出力する。

- **軽量性:** 編集中の操作レスポンスを重視する。
- **非破壊性:** 読み込んだPMX/VMDなどの原本を直接改変しない。
- **拡張性:** 共通プラグイン基盤およびアプリ専用SDKによる機能拡張ができる構造にする。
- **高品質映像:** MMD風トゥーン、イラスト風、フォトリアル／シネマティックまで発展させる。
- **独立動作:** Drawing Canvasとは別アプリとして開発し、相互連携は任意のプラグイン／通信機能で実現する。

### 1.2 対象外・後日検討

本格的なメッシュモデリング、スカルプト、テクスチャペイント、Blender代替の総合3D制作機能は本体の必須対象にしない。PMM完全互換、MMEエフェクト完全互換、VRM/FBX/glTF全対応、モーションクリップの高度なブレンド、パストレーシング、GPUレイトレーシング等は**ロードマップ事項**であり、初期版での完成を要求しない。

## 2. UI・ウィンドウ設計（最新モックアップ準拠）

### 2.1 参考画像

`references/3D_Theater_UI_Mockup.png`

参考画像の意図は、**Visual Studio型ドッキング、ダークテーマ、左側のシーン/アセット、中央の複数3Dビュー、右側のプロパティ、下部のタイムライン**である。画像内のサンプルキャラクター・背景・数値は機能要件や同梱素材を意味しない。著作権・利用条件が不明なモデルや素材を無断同梱しない。

### 2.2 タイトルバーとツールバー【確定】

- **メニューバーをタイトルバー内に統合**し、タイトル文字列を常時大きく表示する専用領域は作らない。
- メニューは左端のアプリアイコンに寄せて横並びに配置。
- ウィンドウ操作（最小化／最大化・復元／閉じる）は右端に置く。
- **ツールバーはタイトルバーのすぐ下に独立した1段として配置**する。タイトルバー内へツールアイコンを詰め込まない。
- タイトルバーの空白領域でウィンドウドラッグ可能にし、メニュー操作・最大化操作を妨げない。DPI変更や複数モニターでも破綻しない。
- ファイル、編集、表示、シーン、モデル、モーション、カメラ、レンダリング、ツール、プラグイン、ヘルプ等のメニュー群を整理して実装する。実装されていないコマンドは無効表示・予定機能として区別する。

### 2.3 Visual Studio型ドッキングUI【確定】

- パネルを上下左右・中央へドッキング、タブ化、フローティング、マルチモニターへ移動できる。
- ピン留め、自動非表示、境界ドラッグでのサイズ変更、閉じる／再表示に対応。
- レイアウトの保存・復元と「初期配置に戻す」を用意する。
- 初期表示の中心パネルは**プレビュー（3Dビューポート）**と**タイムライン**。ほかは任意に表示／非表示できる。
- 追加候補：シーン一覧、プロパティ、アセットブラウザ、ボーン一覧、モーフ操作、グラフエディタ、レンダリング、物理演算、ログ。
- プラグイン由来のドッキングパネルも同じホストで管理する。
- レイアウトにプラグイン由来パネルが含まれていても、該当プラグイン不在時に起動失敗しない。

### 2.4 プレビューと視点【確定】

- プレビューパネル内部で**1画面／2画面／4画面**表示へ切替できる。
- 各ビューは独立したカメラ位置・ズーム・パン・投影方式・グリッド表示等を持つ。**選択状態・編集結果・再生フレームは共通**とする。
- Blenderのような軸に一致した**真正面・真後ろ・右側面・左側面・真上・真下**の固定正投影ビューを提供する。
- 自由視点（透視投影を初期値）およびアクティブカメラ視点を提供する。
- 固定視点への切替はワンタッチで正確な軸方向へスナップする。右／左の呼称はモデル基準とし、方位を一貫させる。
- 4画面プリセットは変更可能にする。例えば「正面・右側面・背面・自由視点」や「正面・右側面・上面・自由視点」を選べる。
- 各ビューを個別に最大化／復帰できる。
- **複数のプレビューパネルをドッキングUIに追加可能**とし、一方を四面図、他方をカメラ視点にするなど自由配置できる構造を採用する。
- 非表示ビューや表示外タブの描画を抑え、GPUリソースは共有する。

### 2.5 マウス・キーボード操作【確定】

| 操作 | 標準動作 |
|---|---|
| 左クリック | モデル／ボーン／オブジェクト選択 |
| 左ドラッグ | ギズモ操作。空白からの範囲選択はツール状態に従う |
| **中ボタン押し込み＋ドラッグ** | **視点回転（オービット）** |
| **Shift＋中ボタンドラッグ** | **視点の平行移動（パン）** |
| **ホイール回転** | **拡大縮小（ズーム）** |
| 右クリック | コンテキストメニュー |
| ダブルクリック | 対象にフォーカス（衝突するUI領域では適切に調整） |

- 固定正投影ビューで中ドラッグした場合、そのビューの固定方向を解除して自由回転へ移行する。Shift＋中ドラッグとズームは固定方向を維持する。
- 操作感度、ズーム反転、ショートカットは後から設定変更可能にする。
- Blender準拠の視点ショートカット候補：Num1 正面、Ctrl+Num1 背面、Num3 右側面、Ctrl+Num3 左側面、Num7 上面、Ctrl+Num7 下面、Num0 カメラ、Num5 投影切替。ショートカット衝突は設定で管理する。

### 2.6 ギズモとボーン操作【確定】

- **MMD方式とBlender方式（XYZ軸ギズモ）の両方**を搭載し、ユーザーが切り替えられる。
- 移動・回転、対応する対象での拡大縮小、ワールド／ローカル座標、数値指定、スナップ、Undo/Redoに対応。
- 方式切替そのものではモデル位置・姿勢・キーフレームを変更しない。
- 初期設定は全ビュー共通、必要に応じてビュー別の方式を許可する。
- ギズモへのドラッグ操作と視点操作は衝突しないようイベント優先順位を整理する。

### 2.7 シーン一覧・プロパティ【確定】

- シーン一覧はモデル、ボーン、モーフ、カメラ、ライト、アクセサリ等を階層表示。検索、展開、表示／非表示、編集ロック、名前変更、複数選択等を用意。
- 階層の変更は許可したオブジェクトに限る。読み込んだPMXのボーン階層や変形順を勝手に書き換えない。
- プロパティは選択対象に応じて編集項目を切り替える。位置・回転・倍率・IK・モーフ値・画角・光源等を数値操作可能にする。
- プレビュー／シーン一覧／タイムラインの選択同期を実装し、循環通知や無限更新を起こさない。

## 3. タイムライン・アニメーション

### 3.1 基本【確定】

- フレーム基準のキーフレーム編集。30fpsを標準とし、24fps・60fps等に設定変更可能。
- モデル、ボーン、IK、モーフ、カメラ、ライト、アクセサリ、音声の階層トラック。
- 選択（単一・複数・範囲）、移動、Ctrl＋ドラッグ複製、コピー／貼り付け、削除、スナップ、ズーム、スクロール、ループ範囲。
- キーの補間はステップ・線形・ベジェ。グラフエディタをドッキングパネルとして追加。
- 音声波形・再生との同期（最終的な正確なシンクは再生時刻の単一管理が必要）。
- クリップ方式の高機能なモーション編集／ブレンドは将来拡張。初期はキーフレーム方式優先。

### 3.2 プレビューとの同期【確定】

- 再生ヘッドが示すフレームでポーズ・モーフ・カメラ・照明・物理の表示結果を更新。
- 四面図や複数プレビューで**同一時刻のシーン**を表示。
- スクラブ中も可能な範囲でリアルタイム更新。重い場合は描画品質を一時低下できる。
- ボーン選択で対応トラックを強調し、キー選択時にも対応対象を確認可能にする。

### 3.3 キーフレーム登録【確定】

- **自動キーフレーム（Auto Key）の初期値はOFF**。
- ONでは編集確定時に現在フレームへ自動登録。OFFでは明示的な登録操作を必要とする。
- 手動モードで未登録変更がある場合、状態を表示し、フレーム移動時の破棄・登録・保持の扱いを明示する。**黙って失わない**。
- 登録対象を単一ボーン／選択ボーン群／モデル全体等で切替可能。
- ドラッグ1回を基本的に1つのUndo操作としてまとめる。

### 3.4 再生中の編集【確定】

- 基本は再生中のポーズ変更を禁止。編集操作を開始した場合は自動一時停止してから編集へ移行。
- 視点回転／パン／ズームは再生中でも使用可能。
- 再生停止、フレーム移動、書き出しで評価結果が矛盾しないよう同じアニメーション評価系を利用する。

## 4. モデル・モーションの互換性

### 4.1 読み込み優先順位【確定】

| フォーマット | 方針 |
|---|---|
| **PMX 2.0** | 最優先。読み込み、基本描画、ボーン、モーフ、剛体・ジョイント |
| **PMX 2.1** | 読み込み対応を段階拡張。追加機能は未対応項目を明示 |
| **VMD** | モーション・モーフ・カメラ等の読み込み／書き出しを優先 |
| **VPD** | ポーズ読み込み／書き出しを優先 |
| PMD | 後日 |
| Xアクセサリ | 後日／優先度中 |
| FBX / glTF / GLB / VRM | 将来の拡張候補 |

- 複数モデルをシーンに配置できる。処理対象数の固定上限は初期に設けず、実性能とメモリ制約に応じた警告／品質調整を行う。
- 不足テクスチャ、無効参照、未対応PMX要素を読み込みレポートとして通知する。
- 読み込み成功とMMDでの見た目・挙動の一致は**別々に検証**する。
- 元ファイルの文字列・メタデータは可能な範囲で保持し、ラウンドトリップ時の情報損失に注意する。

### 4.2 頂点変形・ボーン

- PMXのBDEF1、BDEF2、BDEF4、SDEFを扱う。QDEF（PMX 2.1）は段階対応。
- FK、IK、ボーン階層、回転／移動付与、固定軸、ローカル軸、変形階層、物理後変形などをPMX仕様と検証結果に沿って実装。
- ボーン・モーフ・IK・物理演算は適切な評価順が必要。**単純な全ボーン一括処理で済ませない**。
- モデル／ボーンの描画と実際の変形結果を分け、計算処理をユニットテスト可能にする。

### 4.3 モーフ

- 初期：頂点／ボーン／UV／材質／グループモーフ。
- 段階対応：フリップ／インパルスモーフ等のPMX 2.1拡張。
- モーフ専用パネルから値変更、プリセット・キーフレーム登録、複数値の混合を行える構造にする。

### 4.4 非破壊編集

- PMXやVMDの原本は直接上書きしない。プロジェクトファイル内にシーン配置・姿勢・キー・材質上書き・表示設定を保存する。
- 外部素材は基本的に参照管理。リンク切れ検索、再指定、一括収集（後日）を想定する。

## 5. 物理演算・キャッシュ

### 5.1 物理エンジン

- **Bullet Physics を第一候補**とし、ライセンス・採用バージョン・MMD互換動作を検証して選定。
- PMX剛体（球・箱・カプセル）、剛体モード、ジョイント、衝突グループ、重力、ばね・制限を扱う。
- モード：常時演算／再生・レンダリング時のみ演算（**初期値**）／無効。
- モデル単位の物理ON/OFF、剛体／ジョイント表示、重力や演算精度の設定を提供する。

### 5.2 物理キャッシュ

- 固定時間刻みによる演算と、必要に応じた物理状態のスナップショット・フレーム結果キャッシュを提供。
- タイムラインで過去フレームへ戻っても、計算済みキャッシュ利用、または適切な初期状態からの再計算で結果を復元する。
- キャッシュの計算済み範囲表示、再生成、無効化、レンダリング前のベイク、削除に対応。
- 物理設定・モデル・関連アニメーションを変更したら影響範囲を無効化する。
- 演算条件が異なる環境で完全決定論的動作が得られると安易に仮定しない。プレビュー／書き出しの一致をキャッシュと検証で高める。

## 6. 映像表現・レンダリング

### 6.1 描画方針【確定した目標】

**「編集時は軽く、最終出力は極めて高品質」**を目指す。品質はモデルや材質、ライティング等の入力素材にも左右されるため、単にモード変更するだけで全PMXモデルが写真のようになるとは保証しない。

- **トゥーン:** MMDに近いトゥーンテクスチャ、セル影、輪郭線、材質単位の表現、スフィアマップ的処理。
- **イラスト風:** 線画、塗り・影色、色調、質感テクスチャやポスト処理による2Dイラスト感。
- **リアル／シネマティック:** PBR材質、HDRI・環境光、柔らかな影、反射、AO、被写界深度、ブルーム、フォグ、モーションブラー、色調補正等。
- 編集用の軽量描画と、書き出し用の高品質描画を分離する。プレビュー品質プリセットも設ける。

### 6.2 マテリアル

- **MMD互換材質**を保持しつつ、任意の**拡張材質オーバーライド**を別データとして設定可能にする。
- PBR項目候補：ベースカラー、金属度、粗さ、法線、発光、クリアコート、肌向け散乱表現等。
- PMX材質やテクスチャの破壊的変換は避ける。原本素材と拡張設定を分離。

### 6.3 出力

- 初期：PNG静止画、透過PNG（RGBA）、PNG連番。解像度・FPS・フレーム範囲・背景透過を設定可能。
- 発展：JPEG、H.264/MP4動画、アルファ対応の透過動画（採用コーデックと再生環境を検証）、EXR連番、高度なカラー管理。
- 将来：Beauty／Alpha／Depth／Normal／Shadow／Emission／Object ID／Material ID等のレンダーパス出力。
- 描画ギズモ、ボーン、グリッド、UIは通常の最終出力に映り込まない。
- レンダリング処理の進捗、キャンセル、失敗理由をユーザーに通知する。

### 6.4 描画基盤の実装方針

- **初期の技術候補は Direct3D 11**。ただし将来D3D12、ハードウェアレイトレーシング、パストレーシング等へ発展できるようレンダリングAPIを抽象化する。
- レンダラー実装、シーンデータ、ライト、マテリアル、レンダーパス、ポスト処理を分離する。
- 最初にWPF内のGPU描画面とネイティブ描画エンジンの接続をプロトタイプ検証する。毎フレームの不要なGPU→CPU読戻しは禁止。
- 複数ビューポートはモデル・テクスチャ等のGPU資源を共有する。
- リアルタイム描画と最終品質は段階的に進め、未実装機能を「完成」と扱わない。

## 7. プラグインSDK（汎用基盤）

### 7.1 原則【確定】

**特定のアプリ間連携だけのために設計しない。** Drawing Canvasとの「現在のフレームをレイヤーに追加」は、できるプラグインの一例にすぎない。

- 共通基盤：`Plugin.Core`
- 共通UI拡張：`Plugin.UI`（WPF実装を分離したアダプター構成が望ましい）
- 3D Theater専用SDK：モデル、シーン、選択、モーション、レンダリング等を公開
- Drawing Canvas専用SDK：キャンバス、レイヤー、画像、ブラシ等を公開（別アプリ側で実装）
- 両アプリは**SDKがなくても、それぞれ単体で動作**する。

### 7.2 共通拡張ポイント

| API | 機能 |
|---|---|
| Plugin / Lifecycle | 初期化・停止・有効化・無効化・登録解除 |
| Command | メニューコマンド、ショートカット |
| UI | メニュー、ツールバー、ドッキングパネル、ダイアログ、コンテキストメニュー、編集ツール、ステータスバー |
| Event | ドキュメント・選択・フレーム等の変更通知 |
| Document | アプリが公開するドキュメントの取得・編集 |
| Undo | 履歴・トランザクション登録 |
| Settings | 個別設定保存／復元 |
| Task | 非同期処理、進捗、キャンセル |
| File | 追加インポーター／エクスポーター |
| Interop | 外部アプリ連携（選択式アダプター） |

- プラグインがSDK公開外の内部オブジェクトを直接操作することを前提にしない。
- 編集処理はアプリ本体のUndo/Redoと整合するAPI経由で行う。
- ドッキングパネルも本体のドッキングサービスに登録し、同じルールで表示・タブ化・分離・復元できるようにする。

### 7.3 DLL・ロード・管理

- C#/.NETのDLLを基本。各プラグインに`plugin.json`（ID、名前、バージョン、対象ホスト、SDKバージョン、エントリポイント、必要機能等）を付与。
- `.NET AssemblyLoadContext`と依存関係解決機構を基本候補にし、**共通のSDK契約アセンブリが重複ロードされないように設計**する。
- 追加・削除・有効・無効・設定・互換性チェック・ログ表示・安全モードに対応。
- 更新・削除の反映はアプリ再起動を標準とし、DLLの確実なホットアンロードは初期要件としない。
- 同一プロセスのDLLは強いセキュリティ境界ではない。公開APIの制限だけで悪意あるコードを隔離できると主張しない。信頼できない拡張は将来の別プロセス実行方式を検討する。
- プラグイン同士の機能連携は将来、公開サービス登録／取得方式を採用できるようにする。相手の内部DLLへの直接依存を前提にしない。

### 7.4 Drawing Canvas連携の参考例（必須実装ではない）

外部連携プラグインが3D Theaterから現在のフレームを透過PNGで取得し、Drawing Canvasの公開レイヤーAPIを通じて新規レイヤーに追加することは可能な設計とする。ただし、**この例専用のAPIをPlugin.Coreに設けない**。実際の通信方式（Named Pipes等）は連携機能を実装する段階で決める。

## 8. プロジェクト・設定・データ管理

- 独自プロジェクト形式（拡張子候補：`.3dtproj`。正式確定前は識別子と仕様を記録）。内部フォーマットはバージョン管理可能にする。
- プロジェクトにはシーン、モデル参照、アニメーション、カメラ、ライト、材質オーバーライド、レンダリング設定等を保存。
- レイアウト、テーマ、ショートカット、プラグイン状態はユーザー設定として分離する。
- 保存は破損を避ける安全な更新方式（例：一時ファイル書き込み後の置換）を採用。
- 自動保存・復旧、欠損素材の警告、プロジェクトを開けない場合の診断ログを設ける。
- 物理・レンダリングなど再生成可能なキャッシュは原則別保存し、削除可能にする。
- パスの取り扱いは相対参照を優先しつつ、外部絶対パスも安全に管理する。

## 9. 技術構成・推奨ソリューション

### 9.1 技術選定

| 層 | 初期推奨 |
|---|---|
| UI | C# / WPF、現在サポートされる.NET LTS |
| ドッキング | WPF対応の信頼できるドッキング基盤を検証し採用（ライセンス確認必須） |
| 3Dエンジン | ネイティブC++ |
| GPU | Direct3D 11を初期候補としインターフェースで分離 |
| .NET / C++間 | C API + P/Invoke等の明示的なInterop境界を第一候補としてプロトタイプ検証 |
| 物理 | Bullet Physics候補 |
| テスト | .NET単体テスト＋C++単体テスト＋サンプルモデルによる統合検証 |
| プラグイン | 共通Plugin.Core / Plugin.UIアダプター / 3D Theater専用SDK |

特定のOSSライブラリやコーデックを採用する前に、**配布形態・ライセンス・保守状況・Windows互換性**を確認すること。

### 9.2 ディレクトリ構成例（変更可）

```text
3DTheater/
├─ src/
│  ├─ 3DTheater.App/                 # WPF UI／ドッキング／コマンド
│  ├─ 3DTheater.Application/         # アプリケーションサービス／Undo／状態管理
│  ├─ 3DTheater.Domain/              # シーン、モデル、モーション、設定データ
│  ├─ 3DTheater.Engine.Interop/      # C#からネイティブへ渡す境界
│  ├─ 3DTheater.Engine.Native/       # C++描画・変形・物理
│  ├─ 3DTheater.Formats/             # PMX／VMD／VPD等
│  ├─ 3DTheater.Plugin.SDK/          # アプリ専用SDK
│  ├─ Plugin.Core/                   # 共通プラグイン契約・管理基盤
│  └─ Plugin.UI.Wpf/                 # WPF UI拡張アダプター
├─ tests/
├─ docs/
├─ samples/                          # ライセンス確認済みの検証素材のみ
└─ references/                       # UI参考画像
```

- 層と依存方向を明示し、WPFの画面コードにPMXパーサーや物理エンジンを直書きしない。
- UIからのイベントをコマンド／サービスへ伝達し、レンダリングスレッドとUIスレッドを適切に分離する。
- GPUデバイスロスト／ウィンドウリサイズ／高DPI／最小化／復帰を考慮する。
- ログは外部依存・エラー・性能問題を追跡できる粒度で残すが、過剰な毎フレーム出力は避ける。

## 10. 開発手順（段階的リリース）

### Phase 0：開発環境・検証用土台

**実施内容:** Windows/WPF/C++ソリューション、ビルドスクリプト、テストプロジェクト、ログ、UI／ネイティブ連携の最小検証、Git管理、ライセンス一覧。

**完了判定:** 何もモデルがない状態でアプリが起動し、3D描画領域が表示され、ビルド手順が再現可能であること。

### Phase 1：編集UIの骨組み

**実施内容:** タイトルバー統合メニュー、直下のツールバー、ドッキングUI、プレビュー（1/2/4画面）、固定6方向ビュー、自由視点、規定マウス操作、シーン一覧、プロパティ、タイムラインの最小構成。

**完了判定:** レイアウトを自由に変更・保存・復元でき、ビューの切替／パン／回転／ズームが動く。モデル未対応の場合はテスト用ジオメトリで検証する。

### Phase 2：PMXモデル・ポーズ・基礎モーション

**実施内容:** PMX 2.0基本読み込み、テクスチャ・材質・変形・ボーン／IK・初期モーフ、シーンへの複数配置、選択、2方式のギズモ、キー編集、VMD/VPDの基本入出力。

**完了判定:** 権利処理済みの検証用モデルを読み込み、変形・ポーズ・モーション再生・保存／再読込ができる。未対応要素は警告が出る。

### Phase 3：物理・高度なアニメーション編集

**実施内容:** Bullet導入、剛体／ジョイント・変形順・物理キャッシュ、スクラブ整合性、モーフ拡張、音声、グラフエディタ、Undo/Redoの検証。

**完了判定:** 再生位置を往復しても適切に姿勢が復元され、ベイクした結果と書き出しで目立つ破綻がない。

### Phase 4：品質向上・書き出し

**実施内容:** 基本トゥーン描画・輪郭線・影・カメラ、PNG／アルファ付き連番出力。続いてイラスト風表現、PBR材質、ライト、反射、ポストエフェクト、動画出力を段階実装。

**完了判定:** 期待したフレーム範囲・解像度・背景透過で出力でき、プレビューと最終結果の違いが説明可能・検証可能であること。

### Phase 5：SDK公開・さらなる映像品質

**実施内容:** Plugin.CoreとUI/アプリ別SDK、管理画面、サンプルプラグイン、API文書。高品質レンダーパス、発展的な反射・レイトレーシング等を必要に応じて追加。

**完了判定:** サンプルプラグインを有効化してコマンド／ドッキングパネルを登録でき、無効化・異常時にも本体が適切に対処する。

> フェーズは実装依存関係に応じて部分的に前後可能。ただし、各フェーズは単独で起動・検証できる状態を維持すること。プラグインSDKの**インターフェース境界の設計**は初期から開始するが、公開SDKの機能完成は後段でも構わない。

## 12. 実装担当への進め方・報告形式

1. **最初に**現在のリポジトリ状態と使用可能なSDK／ビルドツールを確認する。既存コードがある場合、削除・大規模改変前に依存関係を調査する。
2. 本指示書から「決定済み」と「検討事項」を整理し、実装できる単位のタスクに分割して着手する。
3. 第一着手は、**起動するシェル＋タイトルバー統合メニュー＋直下ツールバー＋Visual Studio型ドッキング＋最低限のプレビュー／タイムライン**とする。
4. 次にネイティブ3Dの最小検証、固定視点・マウス操作、モデル読み込みを進める。
5. 変更の都度ビルドとテストを実行し、未実装項目は明示したまま進める。見た目だけのダミーボタンを完成扱いしない。
6. ユーザーへの報告は**日本語**で「実装したこと／検証したこと／未実装・問題点／次に着手すること」の順に簡潔に整理する。
7. 主要な設計判断、互換性制限、利用ライブラリ、ライセンス、ビルド方法をREADME・設計文書へ継続記録する。

- 高品質レンダリング技術の導入順、必要GPUと対応範囲。

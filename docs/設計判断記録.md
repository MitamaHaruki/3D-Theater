## 1. 開発環境とソリューション構成（確定・Phase 0、Phase 1 で追加）

| 項目 | 決め | 理由 |

| C++ | C++20、Visual Studio 2026（ツールセット v145）、Windows SDK 10.0.26100 | 開発機に入っている最新の組み合わせ |

## 2. C# と C++ のつなぎ方（確定・Phase 0、Phase 1 で API 0.2）

指示書の未決定事項「ネイティブ Interop の具体方式と ABI・所有権ルール」への答え。公開する関数は [`tt_engine.h`](../src/3DTheater.Engine.Native/include/tt_engine.h) だけ。

- **方式:** C の関数として公開し、C# は `LibraryImport`（P/Invoke）で呼ぶ。C++ のクラスや例外は境界を越えさせない。
- **呼び出し規約・文字:** `__cdecl`、文字列は UTF-16（`wchar_t`）。
- **版の確認:** `tt_get_api_version()` の大きな版が違う DLL とは組まない（C# 側が起動時に確認）。Phase 1 で 0.2 に上げた（描画の条件を C# から渡すようにしたため）。
- **構造体:** 先頭に `struct_size` を置き、C# と C++ で大きさが食い違ったら `TT_E_INVALID_ARG` にする。
- **行列:** 「行ベクトル × 行列」の並びの 16 個の float。System.Numerics と DirectXMath がどちらもこの並びなので、そのまま渡せる。
- **結果の返し方:** 0 以上は成功（`TT_OK`、`TT_S_NOT_READY`）、負の値は失敗。失敗の説明は `tt_get_last_error_message()` で、失敗した呼び出しと同じスレッドから取り出す。C# 側では `NativeEngineException` に変換する。「この環境では使えない（`TT_E_NOT_SUPPORTED`）」は呼び出し側が別の方法へ切り替える前提なので、ログは警告にとどめる。
- **所有と破棄の順番:** ビュー → エンジンの順に破棄する。ビューが残っているとエンジンの破棄は `TT_E_INVALID_STATE` で断る。
- **スレッド:** エンジンとビューは作ったスレッドからだけ呼べる。他のスレッドからは `TT_E_WRONG_THREAD`。
- **ファイナライザーは使わない:** GPU とウィンドウの資源は作ったスレッドでしか安全に解放できないため。`Dispose` を必ず呼ぶ。
- **ログ:** C++ 側のログはコールバックで C# へ渡し、アプリのログファイルにまとめる。
- **描く内容:** エンジンはシーンを持たない。視点の行列と「何を表示するか」を毎回 C# から渡す（`TtFrameParams`）。シーンの状態を 1 か所（C# 側）に保つため。

## 3. WPF への 3D の埋め込み方式（確定・2026-11-04）

指示書の未決定事項「WPF 上の D3D ビュー埋め込み方式」。Phase 0 で 2 方式を並べて比べ、Phase 1 の開始時に**方式 B（D3DImage）**を本採用した（利用者の了承済み）。

- **方式 A（HwndHost）:** ネイティブの子ウィンドウを WPF に埋め込み、そこへスワップチェーンで直接表示する。
- **方式 B（D3DImage）:** Direct3D 11 で画面外のテクスチャに描き、Direct3D 9Ex と共有して WPF の `D3DImage` として表示する。

### Phase 0 で測った結果（2026-11-04、RTX 4060 Ti、拡大率 100%、Windows 11）

| 項目 | 方式 A | 方式 B |
|---|---|---|
| 1 枚あたりの UI スレッドの時間 | 約 0.06 ms | 約 0.8〜1.0 ms（GPU の完了待ちを含む） |
| WPF の部品を 3D の上に重ねる | **できない**（子ウィンドウの下に隠れる） | できる |
| ソフトウェア描画（WARP） | 動く | 共有はできない（下の予備の方式で動かす） |

### 方式 B を選んだ理由

1. 参考画像では、各ビューの上に「上 (Top)」などの見出しとボタンが 3D に重ねて置かれている。方式 A ではこれを WPF で作れない。
2. 指示書のドッキングには「自動非表示」がある。自動非表示のパネルは中央の領域の上に滑り出てくるため、方式 A では 3D の下に隠れてしまう。
3. マウス操作を普通の WPF 部品として受け取れる。方式 A は子ウィンドウに入力が届くため、別に橋渡しが要る。

### 方式 B の弱点への対策（Phase 1 で実装）

- **GPU の完了待ち:** 区画ごとに待たず、「全区画の描画を頼む → 1 回だけ待つ → 全区画を表示に反映」の 3 段階にした（`tt_engine_wait_for_gpu`）。
- **共有できない環境**（WARP、画面につながっていない GPU など）: 描いた絵を読み出して `WriteableBitmap` で表示する**予備の方式**に自動で切り替える。指示書は「毎フレームの不要な GPU→CPU 読み戻し」を禁じているが、これは共有できない環境に限った必要な読み戻しとして扱う。状態表示に「読み出し方式」と出る。
- 方式 A のネイティブ側（子ウィンドウへの描画）はテスト付きで残している。WPF 側の部品（HwndHost）は Phase 1 で外した（Git の履歴に残っている）。

### まだ測っていないこと

入力の遅れ、拡大率の変更・複数モニター間の移動、リモートデスクトップ、GPU が 2 つあるノート PC。

## 4. 描画ループ（仮・Phase 1）

- WPF の画面更新（`CompositionTarget.Rendering`）に合わせて、UI スレッドで描く。
- 変化のあった区画だけを描く（シーンの値・選択・再生位置が変わると全区画、視点や大きさが変わるとその区画だけ）。
- 隠れている区画（裏のタブ、最大化で隠れた区画、1/2 画面で使わない区画）は描かず、GPU の資源も作らない。
- 何も変わらず再生もしていないときは購読をやめて GPU と CPU を休ませる（「編集時は軽く」）。
- **決定（Phase 2 の 9 段階目）:** 指示書は「レンダリングスレッドと UI スレッドを適切に分離」としている。実物のモデルで測った結果、今は UI スレッドで描くままにした（理由と見直す目安は 15 章）。

## 5. 座標系と視点（確定・2026-11-04、単位などは仮）

- 座標は MMD と同じ**左手系・Y 軸が上**。モデルの前は −Z 側。
- 回転は度で、X = 上下の向き（正で見下ろす）、Y = 左右の向き、Z = 傾き。Z → X → Y の順に回す。
- **「右側面」は Blender と同じ向き**（画面の右側 = +X 側から見る。こちらを向いたモデルでは左半身が映る）。指示書 2.4 の「モデル基準」と 2.5 の「Blender 準拠のショートカット」が食い違っていたため、利用者に確認して決めた。

| 視点 | ショートカット | 見る向き | 画面の右 | 画面の上 |
|---|---|---|---|---|
| 正面 | Num1 | −Z 側から +Z へ | +X | +Y |
| 背面 | Ctrl+Num1 | +Z 側から −Z へ | −X | +Y |
| 右側面 | Num3 | +X 側から −X へ | +Z | +Y |
| 左側面 | Ctrl+Num3 | −X 側から +X へ | −Z | +Y |
| 上面 | Num7 | 真上から | +X | +Z |
| 下面 | Ctrl+Num7 | 真下から | +X | −Z |

- 固定視点は平行投影で始まる。中ボタンで回すと自由視点（透視投影）へ移る。平行移動とズームでは固定視点のまま（指示書 2.5）。
- カメラ視点では、どの操作でもカメラの位置から自由視点へ移る（シーンのカメラそのものは動かさない）。
- 固定視点では、格子を画面に平行な面（正面・背面 = XY、側面 = YZ、上下 = XZ）に描き、その面の 2 本の軸に色を付ける。
  - 格子と軸は、固定視点では**いちばん奥**に描く（奥行きを比べも書きもしない。格子の面はモデルを貫くので、奥行きどおりだとモデルの上に線が出るため。2026-11-10、利用者の指摘で変えた）。自由視点・カメラ視点では床として奥行きどおりに描く。描画エンジンの `TT_FRAME_GRID_BEHIND`（API 0.8）。
- **未確定:** 単位（MMD の 1 単位 = 約 8 cm と言われる）、各ファイル形式からの変換方針。Phase 2 の PMX 読み込みで決める。

## 6. 画面の作り（確定・Phase 1）

### ドッキング部品: Dirkster.AvalonDock 4.74.1（Ms-PL）

- 候補のうち、無料で Visual Studio 型の操作（タブ化・フローティング・自動非表示・複数モニター）がそろい、.NET 10 向けの版がある。
- 最新は 5.0.1（2026-10 公開）だが、作りを大きく変えた直後の版で、レイアウトの保存方法も変わっていたため見送った。4.x の最新 4.74.1（2026-04 公開、.NET 10 向けあり）を使う。5.x は落ち着いたら検討する。
- 配色は付属の `Vs2013DarkTheme`。

### 標準部品の配色: WPF の Fluent テーマ（`ThemeMode="Dark"`）

- 入力欄・メニュー・スクロールバーなどの暗色化を自前で書かずに済む。.NET 10 では警告なしで使えた。
- ただしタイトルバーの一番上のメニュー項目は、Fluent の見た目だと文字が上下につぶれて表示されたため、その段だけ自前の見た目（`TitleMenuItemStyle`）にした。開いた中身は Fluent のまま。
- `TextBox` を継いだ部品（数値入力欄）には Fluent の見た目が自動では付かないので、`Theme.xaml` で明示的に当てている。

### タイトルバー（指示書 2.2）

- `WindowChrome` で標準のタイトルバーを消し、アイコン・メニュー・最小化/最大化/閉じるを自前で並べた。空いた所はドラッグで移動できる。
- Windows 11 のスナップレイアウト（最大化ボタンにマウスを乗せると出る配置の候補）を残すため、最大化ボタンの上では OS に「最大化ボタン」と答える。WPF の `WindowChrome` が先に答えてしまうので、ウィンドウをサブクラス化して WPF より手前で受け取っている（`TitleBarHelper`）。
- 最大化すると枠の分だけ画面の外にはみ出すので、その分だけ中身を内側に寄せる。

### レイアウトの保存と復元（指示書 2.3・8 章）

- 置き場所: `%APPDATA%\3DTheater\UserSettings\`（`layout.xml` = ドッキングの並び、`settings.json` = プレビューの分け方・視点とウィンドウの位置）。プロジェクトとは別。
- 保存は一時ファイルに書いてから置き換える（途中で止まっても壊れない）。
- 保存したレイアウトに知らないパネル（無効になったプラグインのパネルなど）があれば、そのパネルだけ外して起動する（実際に差し込んで確認済み）。読めないときは初期配置で起動する。
- `settings.json` の形式の版（`Version`）が合わなければ読まずに初期状態にする。

### ウィンドウの位置（Phase 4 の途中で直した）

- 閉じるときに、ウィンドウの置き場所（元の大きさのときの位置と大きさ・最大化）を覚え、次に開いたときに戻す（`WindowMemory`。`settings.json` の `Windows`）。
  - メインのウィンドウ: 位置・大きさ・最大化。
  - 設定などの画面（書き出し・映像効果・霧・影の設定・材質の設定・読み込みレポートなど）: 種類ごとに位置。大きさを変えられる画面（材質の設定・読み込みレポート）は大きさも。同じ起動の中で開き直したときも、次の起動でも戻す。
- **直した不具合**: 前は WPF の座標（`Left`・`Top`）と `WindowState` を、ウィンドウができる前に入れていた。最大化したまま閉じると、次の起動で別のモニターに最大化された（試した PC のモニター 3 台で、右上で最大化 → 右下や主モニターに出た）。最大化を先に指定すると、元の位置が Windows に伝わる前に最大化されるため。
- 今は Windows の GetWindowPlacement / SetWindowPlacement と同じ画素の座標（作業領域の座標）で覚え、ウィンドウができた所（まだ見せる前）で元の位置に置いてから最大化する。画素の座標なので、拡大率の違うモニターでもずれない。
- 覚えた位置のタイトルバー（上の端の帯）がどのモニターにも出ないとき（モニターを外したなど）は戻さず、初めの位置に開く（前は全部のモニターを囲む四角で比べていたので、モニターの無いすき間でも戻していた）。
- 前の版の設定（WPF の座標の `Window`）は、初めて起動したときに新しい形式へ移し、以後は書かない。
- 確かめたこと（実物の PC、モニター 3 台）: 主モニター・右上・右下で、ふつうと最大化のそれぞれを、前の版の形式からと、閉じたときに保存した値からの 2 回ずつ起動し、同じモニター・同じ位置に戻ること。設定の画面を動かして閉じると、開き直しても次の起動でも同じ位置に戻り、材質の設定は大きさも戻ること。どのモニターにも出ない位置を覚えていると、メインのウィンドウの真ん中に開くこと。
- 浮かせたパネル（AvalonDock）の位置は、今までどおり `layout.xml` に保存される。

## 7. PMX の読み込み（確定・Phase 2 の 1 段階目）

指示書 4.1〜4.4 のうち「読み込み」と「読み込みレポート」まで。表示・変形・物理は次の段階以降。

### 読むもの

- PMX 2.0 のすべての要素（頂点・面・テクスチャ・材質・ボーン・IK・モーフ・表示枠・剛体・ジョイント）と、PMX 2.1 の QDEF・フリップ／インパルスモーフ・2.1 のジョイントの種類・材質の頂点色／点／線の指定。
- 名前（日本語・英語）、コメント、材質のメモ、番号の大きさ・文字コードなど、元ファイルの情報は捨てずに持つ（指示書 4.1・4.4）。
- 座標は PMX も 3D Theater も左手系・Y が上なので変換しない。角度はラジアンのまま。
- 番号の読み方: 頂点の番号は 1・2 バイトのとき符号なし（0〜255、0〜65535）、それ以外の番号は符号付き（-1 =「なし」）。
- 古い書き出し器で表示枠から後ろが無いファイルは、無い部分を 0 個として読む（情報としてレポートに載せる）。
- PMX 2.1 のソフトボディは中身を読まず、数だけ数えて「未対応」と知らせる。
- PMD（古い形式）は「後日対応」と理由を出して読まない。

### 壊れたファイルへの備え

- 数の欄が残りのバイト数に収まらなければ、大きな配列を確保する前に止める（壊れたファイルで固まったりメモリを使い果たしたりしない）。
- 読み途中で終わったら、どの部分の何バイト目かを添えて「途中で切れているか壊れている可能性」と伝える。
- 形式の誤りは例外を外へ出さず、エラー入りの読み込みレポートとして返す。

### 読み込みレポート

- 区分: 形式・未対応・参照の誤り・素材が見つからない・補足。重さ: エラー（読めない）・注意（読めたが元と違う可能性）・情報。
- 範囲外の参照（存在しないボーン・頂点・テクスチャなど）はデータを直さずに知らせる。使う側（描画・変形）で無視する前提。
- 同じ種類の問題はまとめて 1 行（件数と最初の 3 つの例）にする。
- テクスチャはモデルのファイルの場所からの相対パスで探す（区切りの `\` と `/` の両方を受け付ける）。材質が使っていないテクスチャは調べない。`toon01.bmp`〜`toon10.bmp` が手元に無いときは、MMD 付属の共有トゥーンとして扱う（情報）。
- 同じ名前のボーン・モーフは、モーションを名前で当てはめるときに区別できないので注意として出す。
- 「読み込めた」ことと「MMD と同じ見た目・動きになる」ことは別に確かめる（指示書 4.1）。レポートの窓にもそう書いた。

### 画面からの使い方

- 「ファイル → モデルを読み込む」「モデル → PMX を読み込む」（Ctrl+I）、ウィンドウへのドラッグ、起動時の引数（「プログラムから開く」）。
- 読み込みは別のスレッドで行い、画面を止めない。読めたモデルはシーンの「モデル」に加わり、プロパティで形式・数・コメント・レポートを見られる。
- ファイルの中身（`PmxDocument`）はアプリ側（`EditorContext.Models`）に持ち、シーンの項目（`ModelNode`）には場所と概要だけを持つ。プロジェクトにはモデルの場所だけを保存する（12 章）。

### 測った速さ（2026-11-06、開発機）

合成した頂点 30 万・面 50 万・ボーン 200・頂点モーフ 100 個（各 2,000 頂点）、26 MB のデータで、点検を含めて 1 回 約 74 ms（ファイルの読み出し時間は含まない）。

### テストの方針

- 実在のモデルは使わない（権利の確認が要らないよう、テストの中でデータを組み立てる）。
- テスト用の書き出し器（`PmxTestWriter`）で全要素入りのデータを作って読み戻すほか、仕様の並びどおりに手でバイト列を組んだテストも置き、書き出し器と読み込み側が同じ思い込みで間違えていないことを確かめる。
- 実物のモデルでの確認は、利用条件の確かな検証用モデルを用意してから行う（まだしていない）。

## 8. モデルの表示（確定・Phase 2 の 2 段階目）

読み込んだ PMX を全プレビューに描く。ボーンとモーフでの変形は 9 章、トゥーン・スフィア・輪郭線・影は Phase 4。

### 描画エンジンの公開関数（API 0.3）

- `tt_texture_create` / `tt_mesh_create` でテクスチャとメッシュ（頂点・面・材質）を GPU に載せる。描く内容は毎回 `TtFrameParams.items`（メッシュと置き方の一覧）で渡す。エンジンはシーンを持たない決まりはそのまま（2 章）。
- メッシュは作るときに面の頂点番号と材質の範囲を確かめ、範囲外なら断る（GPU に壊れたデータを渡さない）。
- メッシュはテクスチャの中身を参照し続けるので、テクスチャの入れ物は作った直後に破棄してよい。
- ビュー・テクスチャ・メッシュが残っている間はエンジンを破棄できない。アプリは終了時に「プレビュー → モデル → エンジン」の順に片付ける。

### 描き方（MMD に合わせた点）

| 点 | 決め | 理由 |
|---|---|---|
| 表裏 | 時計回りの面が表。両面描画の材質以外は裏面を描かない | MMD（Direct3D 9 の既定）と同じ |
| 描く順 | 材質の並び順のまま、半透明は重ね合わせ（アルファブレンド）、深度は書く | MMD と同じ。並べ替えると作者の意図と変わる |
| 色の扱い | テクスチャも画面も sRGB の補正をしない | MMD は補正しないため、同じ見た目に近づける |
| 照明 | MMD の初期値（向き (-0.5, -1, 0.5)、明るさ 154/255）に固定 | 照明の項目の反映は Phase 4 |
| 陰影 | `(環境色 + 拡散色 × 0.6)` × テクスチャ × 明るさ（0.62〜1.0、光の当たり方で変える） | 形が分かる程度の簡単なもの。トゥーンは Phase 4 |
| テクスチャ | 縮小版（ミップマップ）を作り、繰り返しで貼る | 遠くでちらつかないように |

### テクスチャの読み込み

- PNG・BMP・JPG・GIF・TIFF・DDS は Windows 標準の画像機能（WIC）で、TGA は自前（`TgaDecoder`：フルカラー 16/24/32 ビット・グレースケール・パレット、それぞれの RLE 圧縮）で読む。スフィア（.spa/.sph）は中身が BMP なので WIC で読める。
- 拡張子と中身が違うときは、最後に TGA として試す。読めなければ読み込みレポートに「読めなかった」と載せ、テクスチャなしで描く。
- 今は材質の基本のテクスチャだけを読む（スフィア・トゥーンは Phase 4 で使い始める）。

### 壊れたデータの扱い（描く側）

- 存在しない頂点を指す面は、3 点とも 0 番にして大きさ 0（描かれない）にする。材質の範囲は面の数で切る。どちらも読み込みレポートの「表示しません」と対応する。元の `PmxDocument` は書き換えない。

### 選択と画面に収める

- クリックでの選択は、モデルの三角形（今の姿勢の頂点。9 章）に視線を当てて調べる。先に囲む箱で外れを除く。いちばん手前に当たったものを選ぶ。
- 選択中のモデルは、囲む箱の線を強調色で描く。
- **画面に収めるとき・選択の枠・ボーンの印の大きさには「見た目の箱」を使う**（`DisplayBounds`）。MMD のモデルには、使わない部品（眼鏡など）を足元のずっと下に隠しておく作りがあり、すべての頂点を囲むと箱が大きくなりすぎて、モデルが見えないほど引いてしまうため（実物のモデルで、高さ −983 に眼鏡の頂点 1,287 個がある例で起きた）。
  - 決め方: 面に使われている頂点の真ん中（座標ごとの中央の値）からの距離で、8 割の頂点が入る距離を目安にし、その 4 倍より遠い頂点を除く。隠した部品が頂点の 2 割より少なければ除ける。体から伸びる長い物（剣など）は、ほかから離れていないので残る。
  - 除いた頂点があれば、読み込みレポートに情報として載せる。クリックでの選択（当たり判定）は、これまでどおりすべての頂点で調べる。
- 最初のモデルを読み込んだときは、全プレビューの区画（カメラ視点を除く）をそのモデルに合わせる。MMD のモデル（高さ約 20）は確認用の立方体（1 辺 1）よりずっと大きいため。シーンのカメラは動かさない（シーンのデータを勝手に変えない）。
- 床の格子は ±50（1 目盛り = 1、太線は 5 ごと）に広げた。

### 確かめたこと・まだのこと

- 合成した人形（高さ約 20、TGA と BMP のテクスチャ、半透明で両面描画のマント）で、全区画の表示・選択の箱・自動で合わせる動き・予備の方式（読み出し）での表示を確かめた。
- **実物の PMX ではまだ確かめていない。** 面の表裏の向きは MMD の決まりに合わせたが、実物で裏表が逆に見える材質がないかは、検証用モデルで確かめる必要がある。

## 9. ボーンとモーフ（確定・Phase 2 の 3 段階目）

指示書 4.2・4.3 の「ボーン・モーフ・IK は適切な評価順で」「計算処理をユニットテスト可能に」に合わせ、計算は `3DTheater.Animation` に分けた（画面にもエンジンにも依存しない）。

### 計算の順番（`PoseEvaluator`）

1. モーフの値を求める。グループモーフは中のモーフに「値 × 割合」を足す（グループの中のグループと自分自身は MMD と同じく効かせない）。
2. ボーンモーフの回転・移動を、そのボーンの回転・移動に重ねる。
3. 各ボーンの回転・移動を決める。軸固定のボーンは、その軸まわりの成分だけを残す。親から子へ置き方を積み上げる。
4. **変形の順番（物理後かどうか → 変形階層 → 番号）**に、ボーンごとに「付与 → その下の置き方を更新 → IK を解く」を行う。全ボーンを一度に処理しない。
5. 頂点モーフ・UV モーフ・材質モーフを求める。材質モーフは乗算をすべて掛けてから、加算をすべて足す（並び順によらない）。

| 点 | 決め | 理由・出どころ |
|---|---|---|
| 付与（回転・移動を受け継ぐ） | 元のボーンの回転を「重み」倍する（負の重みも可）。元のボーンも付与を受けていれば、その付与の分を受け継ぐ。元が IK で動くボーンなら IK の回転も含める | MMD の結果に合わせる実装として広く使われている saba（MIT）の考え方に合わせた。足 D などが IK に従う |
| IK | 繰り返し法（CCD）。1 回に回す角度は IK の「単位角」まで。前より遠ざかったら、いちばん近かった状態に戻して終える | PMX の項目（繰り返し回数・単位角・角度制限）をそのまま使う |
| 1 軸だけ制限のあるリンク（ひざ） | その軸まわりの角度だけを動かす。最初の 1 回で制限の外へ向かうなら逆向きに曲げる | 足がまっすぐなときにひざが逆に曲がったり止まったりしないように（saba と同じ方法） |
| 複数の軸に制限のあるリンク | X・Y・Z の角度に分けて制限し、前回の角度に近い分け方を選ぶ | 角度が飛ばないように |
| IK が最初から届いているとき | 解かない | 初期の姿勢で、ひざが勝手に少し曲がらないように |
| 物理後のボーン | 今は続けて計算する | 物理演算は Phase 3 |
| PMX 2.1 の追加 UV・フリップ・インパルスモーフ | 今は効かせない（一覧には「今は効きません」と出す） | 指示書 4.3「段階対応」 |

### 頂点の変形（スキニング、`Skinner`）

- BDEF1・BDEF2・BDEF4 は重みで混ぜた行列で動かす。重みの合計が 1 でないモデルや、ボーンが欠けた頂点は、残りのボーンに割り振る。
- SDEF は 2 本のボーンの回転を球面で補間し、回転の中心（C）まわりに回す。曲げても関節からの距離が変わらない（テストで確かめている）。ボーンが欠けた SDEF は BDEF2 として扱う。QDEF（PMX 2.1）は今は BDEF4 として扱う。
- **変形は CPU で行う。** 選択の当たり判定（今の姿勢の形に当てる）とテストに同じ計算を使えるため。頂点が多いときは複数の CPU に分ける。
  - 測った速さ（2026-11-06、開発機・24 スレッド、Release）: 頂点 15 万・ボーン 500 で、ボーンの計算 約 2.3 ms、頂点の変形 約 3.3 ms。
  - 再生やモーションで重くなったら、GPU での変形（シェーダーでのスキニング）を測ってから検討する。
- 変形した頂点は `tt_mesh_update_vertices`、材質モーフの結果は `tt_mesh_update_materials` で描画エンジンへ送る（API 0.4）。値を変えたモデルだけを、次の描画の直前に 1 回だけ計算し直す（`PoseUpdater`）。

### シーンでの持ち方と操作

- ボーンとモーフはシーンの項目（`BoneNode` / `MorphNode`）としてモデルの下に置く。名前・親子関係・順番はモデルのファイルのままで変えない（指示書 2.7）。
- シーン一覧では、ボーンを PMX の表示枠（MMD のボーン一覧の分け方）ごとに、モーフを種類（目・まゆ・口・その他）ごとにまとめる。表示枠に無いボーンは「表示枠にないボーン」にまとめる。数が多いので、シーン一覧とタイムラインでは最初は閉じておく。
- ボーンの値は、初期の位置からの移動と、回転（度。シーンの項目と同じく Z → X → Y の順）で、どちらも親のボーンから見た向き。プロパティ欄では、移動できないボーンには移動の欄を、回転できないボーンには回転の欄を出さない。
  - 回転は四元数で持ち、プロパティ欄では度で見せる（10 章。最初は角度で持っていたが、モーションの段階で変えた）。
- モーフの値は 0〜1。プロパティ欄と「モーフ」パネル（分類と名前で絞り込み、つまみで変える）で変えられる。「ポーズを初期化」はボーンとモーフをすべて戻す（ロックした項目は変えない）。
- 値を変えると再生を一時停止する（指示書 3.4）。

### ボーンの表示と選択

- 今操作しているモデル（選んだモデル、または選んだボーン・モーフの持ち主）のボーンだけを、モデルより手前に線で描く。プレビューごとに切り替えられ、書き出しには映らない（指示書 5 章）。
- 色: 回転だけ = 水色、移動もできる = 緑、IK = 橙、動かせない = 灰、選択中 = 黄。長さの無いボーンは小さな十字で描く。MMD で非表示のボーンと、シーン一覧で隠したボーンは描かない。
- プレビューでボーンの線の 6 ピクセル以内をクリックすると、モデルより先にそのボーンを選ぶ。

### 確かめたこと・まだのこと

- 合成した人形（ボーン 27・IK 2・付与・軸固定・SDEF と BDEF2 の腕・頂点/グループ/ボーン/UV/材質モーフ・表示枠）で、ひじの曲げ・足 IK・付与・モーフを画面で確かめた（GPU 共有方式と読み出し方式の両方）。
- **実物の PMX ではまだ確かめていない。** MMD と同じポーズになるかは、検証用モデルと MMD で同じ値を入れて見比べる必要がある。
- プレビューでのボーンのクリック選択は、計算をテストで確かめ、利用者が実際のマウスでも確かめた（2026-11-07）。

## 10. モーションとキーフレーム（確定・Phase 2 の 4 段階目）

### 読み込めるもの

| 形式 | 読むもの | 今は使わないもの |
|---|---|---|
| VMD（モーション） | ボーンのキー（移動・回転・4 本の補間曲線）、モーフのキー、カメラのキー（14 章） | 照明・セルフ影のキー（読んで数を知らせる）、表示と IK の切り替えのキー |
| VPD（ポーズ） | ボーンの移動・回転、モーフの値 | ― |

- 古い VMD（モーフの後ろの区切りが無い・モデル名が 10 バイトの版 1）も読む。後ろの区切りが途中で切れているときは、注意を出してそこまでを使う。
- 元のファイルは読むだけで書き換えない。読み込みレポートは PMX と同じ窓で見せる。
- 書き出し（VMD・VPD）は次の段階。

### 名前の対応

- VMD の名前は Shift-JIS の決まった長さ（ボーン・モーフ 15 バイト、モデル 20 バイト）で、長い名前は途中で切れている。**MMD と同じく、モデルの名前を Shift-JIS にして同じ長さで切ったバイト列で比べる。** 文字列にして比べると、2 バイト文字の途中で切れた名前が合わなくなるため。
- モデルに無いボーン・モーフは、使わずにレポートで知らせる。モーションのボーンの半分以上が合わないときは「別のモデル用かもしれない」と注意にする（少しだけ合わないのは普通なので、情報にとどめる）。

### キーと補間（`Theater3D.Domain`）

- キーはボーン・モーフの項目が持つ（`BoneNode.Keys` / `MorphNode.Keys`）。同じフレームには 1 つだけ。
- 補間は MMD と同じく「前のキーからこのキーまで」の動き方を後ろのキーが持つ。ボーンは移動の X・Y・Z と回転で別々の 3 次ベジェ曲線。直線（線形）はベジェの特別な形として扱い、段階（次のキーまで値を変えない）は別の種類として持つ（指示書 3.1 のステップ・線形・ベジェ）。VMD には段階が無いので、書き出しのときの扱いは書き出しの段階で決める。
- 回転は四元数の球面補間。最初のキーより前は最初のキー、最後のキーより後ろは最後のキーの値を使う。
- **ボーンの回転は四元数で持つように変えた**（9 章の仮の決めを確定）。角度は同じ回転にいくつもの表し方があり、キーの補間がずれるため。プロパティ欄では度で見せ、度で入れた値は四元数に直す。
- VMD は 30 fps で作られている。作品のフレームの速さが違うときは、読み込むときにキーの位置を合わせる（60 fps なら 2 倍）。読み込んだ後にフレームの速さを変えたときは、キーの位置も合わせるか尋ねる（15 章）。
- 読み込んだキーは、同じボーン・モーフ・フレームのキーだけを置き換え、ほかのキーは残す（読み込みそのものは 11 章のとおり元に戻せる）。モーションの最後のキーが終わりのフレームより後ろなら、終わりのフレームを延ばす。

### 再生とキーの登録（`AnimationService`）

- 再生位置が変わると、キーのあるボーン・モーフにそのフレームの値を当てはめる。停止中・再生中・（将来の）書き出しで同じ計算を使う（指示書 3.4）。
- **自動キーは初期値 OFF**（指示書 3.3）。OFF のときに手で値を変えると「未登録の変更」になる。
  - フレームを動かしても、再生しても、その値を保つ（**黙って捨てない**）。
  - タイムラインの上に「未登録の変更 n 件」と出し、「すべて登録」（今のフレームのキーにする）か「破棄」（キーの値、キーが無ければ初期の値に戻す）を選ぶ。シーン一覧では「＊」、タイムラインでは名前を橙色にして示す。
  - 指示書の「破棄・登録・保持の扱いを明示する」は、「保持して状態を表示し、登録か破棄をいつでも選べる」形にした。フレームを動かすたびに確認の窓を出すと、スクラブ（再生位置のドラッグ）の邪魔になるため。
- 「キーを登録」（I キー）は、選んだボーン・モーフを今のフレームのキーにする。モデルやまとまりを選んでいるときは、その中の未登録の変更だけを登録する（動かしていない全ボーンにキーを作らない）。ロックした項目は登録しない。
- 新しいキーの補間は直線。同じフレームにキーがあれば、その補間を引き継ぐ。
- ポーズ（VPD）は今の値として置くので、未登録の変更になる（キーにするかは利用者が決める）。
- 自動キーが ON なら、値を変えたときに今のフレームへキーを登録する。

### タイムライン

- ボーン・モーフの行にキーを◆で描く。まとまり（モデル・表示枠など）の行には、中のキーをまとめて薄く描く。今のフレームのキーは強調色。
- キーの選択・移動・複製・削除・コピーは 11 章。補間曲線の細かい編集はグラフエディター（Phase 3）。

### 確かめたこと・まだのこと

- 合成した人形と確認用のモーション（ひじ・腕・センター・足 IK・まばたき・口・材質モーフ、モデルに無いボーンとモーフ、カメラのキー）で、フレーム移動・再生（30 fps で進む）・補間曲線・未登録の変更の保持と登録・ポーズの読み込みを画面で確かめた。
- **実物の VMD・VPD ではまだ確かめていない。** MMD と同じ動きになるかは、検証用のモデル・モーションで見比べる必要がある。
- 元に戻す/やり直しは 11 章。

## 11. 元に戻す/やり直しとキーの編集（確定・Phase 2 の 5 段階目）

### 元に戻す/やり直し（`UndoService` / `EditService`）

- 画面からのシーンの編集は、すべて `EditService.Change` を通す（プロパティ欄・シーン一覧の名前・表示・ロック・モーフのつまみ・ポーズの初期化・キーの登録と破棄・モーションとポーズの読み込み・キーの編集）。
- 1 つの操作で変わる項目について、**変える前と後の値の写し**（`NodeState`）を残す。元に戻すときは前の写し、やり直すときは後の写しに書き戻す。
  - 操作ごとに「元に戻す処理」を書く方法より、書き漏れが起きにくい。項目の種類が増えても、写しの取り方を足すだけで済む。
  - キーの写しは大きくなることがあるので、キーを変える操作（登録・読み込み・キーの編集、自動キーが ON のときの値の編集）のときだけ写す。
  - 「未登録の変更」の印も写しに入れる。キーの登録を元に戻すと、登録前の「未登録」に戻る。
- 書き戻すときは、キーの当てはめと「手で変えた」判定を止める。書き戻した後に、今のフレームのキーを当てはめ直す（操作したときとフレームが違うことがあるため）。
- 同じ項目の同じ値を 1.5 秒以内に続けて変えたとき（つまみのドラッグ、ホイールでの増減）は 1 つの操作にまとめる（指示書 3.3「ドラッグ 1 回を 1 つの Undo に」）。元に戻した後の操作は、前の操作とまとめない。
- 履歴は 300 個まで。新しい操作をすると、やり直しの履歴は消える。
- 何も変わらなかった操作は積まない。
- 元に戻せないもの: 選択、視点、再生位置・終わりのフレーム。（モデルの読み込みは 14 章、フレームの速さの変更は 15 章で戻せるようにした）
- ショートカット: Ctrl+Z = 元に戻す、Ctrl+Y / Ctrl+Shift+Z = やり直し。文字を入力している欄では、その欄の元に戻すが働く。メニューとツールバーのボタンには、何を戻すかを出す。

### キーの編集（`KeyEditing` / タイムライン）

| 操作 | 動き |
|---|---|
| キーをクリック | そのキーを選ぶ（Ctrl で追加・解除、Shift で追加） |
| 帯の空いている所からドラッグ | 範囲の中のキーを選ぶ |
| 選んだキーをドラッグ | 動かす（Ctrl を押しながらだと複製）。1 回のドラッグが 1 つの操作 |
| キーをダブルクリック | そのキーのフレームへ移動 |
| 帯の空いている所をクリック | キーの選択を外し、そのフレームへ移動 |
| 目盛りをドラッグ | 再生位置を動かす |
| 右クリック | 補間（線形・なめらか・段階）、コピー、貼り付け、削除、そのフレームへ移動 |
| Delete / Ctrl+C / Ctrl+V | 選んだキーを削除 / コピー / 今のフレームに貼り付け |

- これまでは帯の上のドラッグでも再生位置が動いたが、キーの範囲選択に使うため、再生位置のドラッグは目盛りだけにした（帯のクリックでの移動は残した）。
- まとまり（モデル・表示枠など）の行の◆は、中のキーをまとめたもの。選ぶと中のキーすべてを選び、動かすとまとめて動く。
- キーを動かした先に、選んでいないキーがあれば、動かしたキーで置き換える。フレームが 0 より前にならないよう、ずれを抑える。
- 貼り付けは、コピーしたキーのうち最も前のキーが今のフレームに来るように、同じ項目へ貼る（アプリの中だけのコピー）。
- 補間の「なめらか」は、MMD の補間曲線の (64, 0)・(64, 127)。曲線の細かい編集はグラフエディター（Phase 3）で行う。
- ロックした項目のキーは動かさない・消さない・貼らない。

### 確かめたこと・まだのこと

- 元に戻す・やり直し・キーの編集の計算は、テストで確かめた。
- 画面では、値の変更 → Ctrl+Z → Ctrl+Y、キーの登録の取り消し（「未登録」に戻る）、モーションの読み込みの取り消しとやり直し（タイムラインの◆が消えて戻る）を、キーボードで確かめた。
- タイムラインのマウス操作（キーのクリック・範囲選択・ドラッグ・右クリック）は、利用者が実際のマウスで確かめた（2026-11-07）。

## 12. プロジェクトの保存と VMD・VPD の書き出し（確定・Phase 2 の 6 段階目）

### プロジェクトファイル（`.3dtproj`）

- 拡張子は指示書の候補どおり **`.3dtproj`**。中身は **UTF-8 の JSON** で、先頭に形式の名前 `"format": "3DTheater.Project"` と版 `"version": 1` を持つ（指示書 8 章「内部フォーマットはバージョン管理可能に」）。
  - 文字の形式にしたのは、壊れたときに中を見て直せること、版の違いを足しやすいこと、差分が読めることのため。
  - キーの数が多いと大きくなるので、キーは数の並びで短く書き、字下げもしない。ボーンのキーは「フレーム・移動 3・回転 4（四元数）・種類」の 9 個。曲線が直線でなければ 16 個を足す。モーフのキーは 3 個（曲線があれば 7 個）。
  - 新しい版の 3D Theater で保存したファイル（版の数が大きい）は開かずに、新しくするよう知らせる。
- 保存するもの: 再生の設定（フレームの速さ・終わりのフレーム・今のフレーム・ループ）、自動キー、カメラ・照明・確認用の立方体・床の値と表示・ロック、モデル（場所・名前・置き方・表示・ロック・中のまとまりの表示とロック）、ボーン・モーフのキーと今の値。
  - **未登録の変更もそのまま保存し、開いたときに「未登録」の印ごと戻す**（黙って捨てない）。
  - ボーン・モーフは、初期のまま（キーなし・動かしていない・ロックも非表示もなし）なら書かない。
  - カメラ・照明などは名前を変えられるので、名前ではなく役目（`camera`・`light` など）で書く。
- 保存しないもの: 選択、視点、パネルの並べ方（ユーザーの設定として別に保存。指示書 8 章）。
- モデルは**場所だけ**を書き、中身は元のファイルから読み直す（原本は書き換えない。指示書 4.4）。
  - 場所はプロジェクトのフォルダーから見た相対パスで書き、予備として保存したときの絶対パスも書く。開くときは相対パス → 絶対パスの順に探す（指示書 8 章「相対参照を優先」）。ドライブが違うときと、無題のときは絶対パス。
  - ボーン・モーフは番号と名前が合えばそれを、合わなければ名前で探す（モデルのファイルが変わったとき）。見つからないものは知らせる。
- **見つからないモデルは消さない。** 開いたときに見つからない（読めない）モデルは、知らせたうえで設定とキーを覚えておき、保存し直してもそのまま書き戻す。ファイルを戻して開き直せば元に戻る。
- 保存は一時ファイルに書いてから置き換える（指示書 8 章「安全な更新方式」）。

### 新規・開く・保存と、保存していない変更

- 新規（Ctrl+N）・開く（Ctrl+O）・保存（Ctrl+S）・名前を付けて保存（Ctrl+Shift+S）。プロジェクトはウィンドウへのドラッグ・起動時の引数でも開ける。
- 変更があると題名に「＊」を付ける。変更とみなすのは、元に戻せる操作・モデルの読み込み・再生の設定（フレームの速さ・終わりのフレーム・ループ）の変更。
- 閉じる・新規・開くの前に、保存していない変更があれば保存するか尋ねる（はい・いいえ・キャンセル）。
- 新規・開くでは、元に戻す/やり直しの履歴を消す。

### 自動保存と復旧（指示書 8 章）

- 変更があれば **2 分ごとに** `%LOCALAPPDATA%\3DTheater\AutoSave\autosave_<プロセス番号>.3dtproj` に書く（元のプロジェクトの場所も入れる）。保存したとき・新規にしたとき・閉じると決めたとき（保存した／保存しないを選んだ）に消す。
- 起動したときに、もう動いていないアプリの自動保存が残っていれば、開くかどうかを尋ねる（はい = 開く・いいえ = 捨てる・キャンセル = 次に起動したときにまた尋ねる）。開いた作業は保存していない扱い（題名に「＊」）で、保存先は元のプロジェクト。
- 同時に複数のアプリを動かしても、ファイル名にプロセスの番号を入れて互いに上書きしない。

### VMD・VPD の書き出し

- モーション（VMD）: 今操作しているモデルのボーン・モーフのキーを書く。補間の曲線は MMD と同じ 64 バイトの並び（最初の 16 バイトに 4 本の曲線、後ろは 1 バイトずつずらした写し）。
  - 作品のフレームの速さが 30 でなければ、30 fps に直す（重なったキーは注意で知らせる）。
  - **段階の補間は VMD に無いので、1 つ前のフレームに前の値のキーを足して表す。** モーフの曲線も VMD に無いので線形になる（知らせる）。
  - 名前は Shift-JIS にして決まった長さ（15 バイト）で切る（MMD と同じ）。
  - 未登録の変更は書かない（注意で知らせる）。
- ポーズ（VPD）: 今のフレームの、動かしているボーンと値の入ったモーフを書く（MMD と同じ書き方。小数 6 桁）。
- 書き出したモーションを読み込み直すと、曲線も含めて同じキーに戻ることをテストで確かめた。
- 元の情報をできるだけ残す（指示書 4.1）点で、読み込んだ VMD の補間の 64 バイトの後ろの部分（MMD の物理の切り替えなどに使われることがある）は今は残していない。必要になったら残し方を考える。

### 確かめたこと・まだのこと

- 合成した人形とモーションで、名前を付けて保存 → 変更の印 → VMD の書き出し → 閉じるときの確認 → 開き直し（キーと題名が戻る）→ 自動保存からの復旧、を画面で確かめた。
- 2 分ごとの自動保存そのもの（時間が来たときに書くこと）は、画面ではまだ確かめていない（書く中身は保存と同じ処理）。
- **実物のモデルでの保存と開き直しは、まだ確かめていない。**

## 13. ギズモ（確定・Phase 2 の 7 段階目）

指示書 2.6 の「MMD 方式と Blender 方式（XYZ 軸ギズモ）の両方を搭載し、切り替えられる」に合わせた。

### 2 つの方式

| 方式 | 出す取っ手 | 道具の切り替え |
|---|---|---|
| **MMD 方式**（初期設定） | 選んだ物に、移動の矢印と回転の輪を一緒に出す。移動できないボーンには矢印を、回転できないボーンには輪を出さない | 使わない（ツールバーの道具のボタンは押せない） |
| **Blender 方式** | ツールバーで選んだ道具の取っ手だけを出す（移動 = XYZ の矢印、回転 = XYZ の輪、選択 = 何も出さない） | ツールバー、または Q（選択）・W（移動）・E（回転）。キーを押すと Blender 方式に切り替わる |

- 「MMD 方式」は、MMD のボーン操作（選んだボーンに回転の輪と移動の軸が出る）に近づけたもの。MMD と同じ見た目・細かな動きをそのまま再現したものではない。
- 方式・道具・座標は全プレビューで共通で、ユーザーの設定として保存する（指示書 2.6「初期設定は全ビュー共通」、8 章）。プレビューごとに別の方式にする機能はまだ無い。
- 方式を切り替えても、モデルの位置・姿勢・キーは変えない（元に戻すの履歴にも積まない）。

### 操作

- 取っ手を左ボタンでドラッグする。Ctrl を押しながらだとスナップ（移動 0.5・回転 5°）。
- ドラッグ中に右クリックか Esc で取り消して、つかむ前に戻す。
- **ドラッグ 1 回を 1 つの「元に戻す」にする**（`EditService.Begin` で始めて、離したときに 1 つの操作として積む。指示書 3.3）。
- 座標はワールド（シーンの XYZ）とローカル（選んだ物の向き。ボーンなら今の姿勢でのボーンの向き）を切り替えられる。
- 操作の優先順: 左クリックは「ギズモの取っ手 → ボーンの線 → モデル」の順。視点の操作は中ボタンなので、ぶつからない（指示書 2.6）。
- ギズモを出すのは、選んでいる物が 1 つで、ロックされておらず、見えているときだけ。ボーン・モデル・確認用の立方体・カメラ・照明に出せる。

### 計算（`GizmoMath`、テストあり）

- 取っ手の大きさは、画面の上でいつも同じ大きさ（矢印の長さ 90 ピクセル。両方出すときは、矢印の先が輪の外に出るよう輪を少し小さくする）。
- 当たり判定は画面の上で、取っ手の線から 7 ピクセル以内。近さが同じなら矢印を優先する。
- 移動の量は、マウスの視線と軸の線が最も近づく所から求める。軸がこちらを向いているときは、画面に写った軸の向きへの動きで求める。
- 回転の量は、輪の面とマウスの視線の交わりの角度から求める（少しずつ足すので 180° を超えても回せる）。輪を真横から見ているときは、つかんだ所の接線（見えなければ画面に写った軸に直角な向き）への動き 100 ピクセルで 90°。
- ボーンへの直し方: ワールドの動きを、親のボーンの向き（モデルの回転を含む）とモデルの拡大で割り戻して、ボーンの値（親から見た移動・回転）にする。回転は「親の向きの中で見た回転」を今の回転の外側から掛ける。
  - 付与・IK・ボーンモーフが重なったボーンでは、見た目の回転とつかんだ輪の向きが少しずれることがある（値は利用者が入れる回転に掛かるため）。

### 確かめたこと・まだのこと

- 合成した人形で、MMD 方式（回転だけのボーンには輪だけ、移動もできるボーンには矢印と輪）、ローカルの座標（輪がボーンの向きに傾く）、Blender 方式の道具の切り替え（移動できないボーンでは何も出ない）を画面で確かめた。
- マウスでのドラッグは、利用者が実際のマウスで確かめた（2026-11-07）。ドラッグの量の計算と、1 つの操作にまとめること・取り消しは、テストでも確かめている。
- 拡大の取っ手・平面の移動（2 つの軸をまとめて動かす）・画面に平行な回転の輪・数値を打ち込んでのギズモ操作は、まだ無い（数値はプロパティ欄で入れられる）。

## 14. カメラのモーションとモデルを外す操作（確定・Phase 2 の 8 段階目）

### カメラのキー

- シーンのカメラ（`CameraNode`）は今までどおり位置・回転（度）・視野角で置き、**キーは MMD と同じく「注視点・回転・距離・視野角」で持つ**（`CameraKey`）。キーの間はこの形のまま補間する。
  - 位置を直線で補間すると、注視点のまわりを回るカメラが注視点に近づいてしまうため。回転は四元数ではなく角度を成分ごとに直線で動かす（MMD と同じ。1 周を超える回転も表せる）。
  - 補間の曲線は MMD と同じ 6 本（注視点 X・Y・Z、回転、距離、視野角）。段階の補間も使える。
- カメラに「注視点までの距離」（`TargetDistance`）を足した。キーを登録するときの注視点は「位置から見ている向きへこの距離だけ進んだ所」。プロパティ欄で変えられる。MMD と同じく、注視点より奥に置く（負の距離）こともできる。
- **キーの無いカメラを手で動かしても「未登録の変更」にしない**（置くたびに未登録が残らないように）。キーのあるカメラの手の変更は、ボーンと同じく未登録の変更として保つ。自動キーが ON なら、キーが無くても登録する。
- カメラを選んで「キーを登録」（I）でカメラのキーになる。タイムラインのカメラの行にもキーが出て、移動・複製・削除・コピー・補間の切り替えができる。プロジェクトにも保存する。

### VMD のカメラ（`MmdCamera`・`CameraMotion`）

- MMD のカメラの位置 = 注視点 + 回転 × (0, 0, 距離)。距離は負の数で注視点の手前。回転は Z → X → Y の順に掛ける（saba と同じ）。
- **回転の向き（符号）は、シーンのカメラ（X が正なら見下ろす）と X・Y が逆**とした。saba と three.js の MMD の扱いから導いたもので、MMD 本体との見比べはまだ。変換はこの 1 か所にまとめてあり、違っていたらここだけを直せばよい。
- 補間は 24 バイト（6 本 × 各 4 バイト: x1・x2・y1・y2）。すべて 0 のもの（古い書き出し器）は直線とみなす。
- 読み込み: カメラ用のモーション（ボーン・モーフのキーが無く、カメラか照明のキーがある）か、カメラを選んで読み込んだ VMD は、シーンのカメラへ当てはめる（モデルを選んでいなくてよい）。モデル用のモーションのカメラのキーは、モデルには当てはめない（知らせる）。
  - 30 fps 以外の作品では位置を合わせる。そのとき、**元で 1 フレームしか離れていないキー（カメラの切り替え）は段階の補間にする**（60 fps にすると 2 フレームの間に途中の絵が出てしまうため）。
  - パース OFF（平行投影）は今は透視投影で表示する（キーには残して書き戻す）。照明・セルフ影のキーは今は使わない（陰影の描画は Phase 4）。
- 書き出し: モーションメニュー「カメラのモーションを書き出す（VMD）」。モデル名は MMD と同じ「カメラ・照明」。30 fps に直し、段階の補間は 1 つ前のフレームにキーを足して表す。
- 書き出したカメラのモーションを読み込み直すと、曲線・720° の回転も含めて同じキーに戻ることをテストで確かめた。

### モデルを外す・読み込みを元に戻す

- モデルメニュー「選んだモデルを外す」、または Delete（キーを選んでいないとき）。ボーン・モーフを選んでいれば、その持ち主のモデルを外す。ロックしたモデルは外さない。モデルのファイルは消さない。
- 外す操作もモデルの読み込みも、元に戻せる（`ModelPresenceAction`）。**外している間も GPU に載せた形を手放さずに持っておき、戻すときにそのまま使う**（読み直さない）。
- 履歴から消えたとき（古くなった・新しいプロジェクトにした・終了した）に、外したままのモデルだけを手放す。そのため、履歴の操作が `IDisposable` なら、捨てるときに破棄するようにした。終了するときは、描画エンジンより先に履歴を消して手放す。

### 確かめたこと・まだのこと

- 合成した人形と確認用のカメラのモーション（半周してから顔の寄りに切り替わる）で、カメラ視点の区画の動き（正面 → 横 → 背中側 → 寄り → 少し上から）を画面で確かめた。
- モデルを外す（Delete）→ 元に戻す（ツールバー）で、シーン一覧と描画から消えて戻ることを確かめた。
- **実物のカメラのモーションを、MMD 本体と見比べてはいない。** 回転の向きが逆に見えたら、`MmdCamera` の符号を直す。

## 15. 描画の土台（確定・Phase 2 の 9 段階目）

### 描画の重さ（実物のモデルで測った・2026-11-07）

- 条件: YYB式鏡音レン水着（頂点 23,547・材質 16・ボーン 163・モーフ 129）に、主なボーン 10 本と表情 2 つを毎フレーム動かす測定用のモーションを当てて 30 fps で再生。RTX 4060 Ti、Debug ビルド。
- 8 区画（プレビュー 2 枚 × 4 画面）で、1 回の描画にかかる UI スレッドの時間は **約 3.4 ms**（変形 0.3・描画の依頼 1.7・GPU の完了待ち 1.1・表示への反映 0.0 ms）。
- 状態表示の「描画 N 回/秒・X ms」にマウスを乗せると、この内訳が出る（`RenderLoop.Breakdown`）。

### 描画専用スレッドは、今は作らない

- 60 Hz の 1 回分（16.7 ms）に対して 3.4 ms で、UI の操作を妨げるほどではない。重い計算（頂点の変形）は、頂点が 2 万を超えると既に複数の CPU で分けている。
- 分けるには、「エンジンは作ったスレッドからだけ使う」「D3DImage は UI スレッドで開け閉めする」という決まりがあるため、描いた絵の受け渡し（描画先を 2 つ持って交互に使う）と、シーンの値の写しが要る。作りが大きく複雑になるわりに、今は得るものが少ない。
- 見直す目安: GPU の完了待ちが 1 回 5 ms を超えたとき（Phase 4 の影・輪郭線・効果）か、UI の操作中に再生がかくつくとき。内訳の表示で見分けられる。

### GPU が使えなくなったとき（取り外し・ドライバーの更新・応答なし）

- **気づく所:** 描画・GPU の完了待ち・資源の作成で、Direct3D 11 が「デバイスが取り除かれた」と返したとき。WPF へ渡す側（Direct3D 9Ex）が失われたときも同じに扱う。
- **使えない間:** GPU を使う操作は `TT_E_DEVICE_LOST` を返す。変形した頂点・材質の値・区画の大きさの変更は受け取って覚えておく。
- **作り直し（`tt_engine_recover`）:** デバイスを作り直し、ビュー・テクスチャ・メッシュの GPU の資源を全部作り直す。**C# 側の持ち手（`NativeView`・`NativeMesh` など）はそのまま使える**ので、アプリはモデルを読み直さなくてよい。
  - そのため、GPU へ送った中身（テクスチャの画素・頂点・面）を CPU 側にも持っておく。テクスチャの画素の分だけメモリを余分に使う（2048 × 2048 の画像 1 枚で 16 MB）。
  - メッシュを作った後にテクスチャの持ち手を破棄しても、メッシュが使っている画素は残り、作り直しで戻る。
  - D3DImage に渡す面は別の物になる。作り直す前に古い面を D3DImage から外し、作り直した後に新しい面を渡し直す（`DeviceResetting`・`DeviceRestored`）。
- **アプリ側（`RenderLoop`）:** 描画が「GPU が使えない」で失敗したら、区画を止めずに描画を止め、その画面更新を終えてから作り直す。作り直せなければ 1・2・4・8 秒、その後は 15 秒ごとに試し、10 回（約 2 分）で諦めて「作業を保存して、アプリを再起動してください」と出す。再生位置は進み続ける。
  - モデルを GPU に載せる途中で気づいたときは、作り直してから 1 度だけ載せ直す。
  - 状態表示に「作り直しています（n 回目）」「作り直して、描画を再開しました」「作り直せませんでした」を出す。
- **ヘルプ「GPU を作り直す（表示がおかしいとき）」:** 使えなくなったときと同じ手順（気づく → 面を外す → 作り直す → 描き直す）を通す。作り直せずに止まっているときは、もう一度試す。
- **確かめたこと:** 本物の取り外しは起こせないため、試験・診断用に「使えなくなったことにする」関数（`tt_engine_simulate_device_lost`）を足した。C++ と C# のテストで、作り直した後もテクスチャ（持ち手を破棄した物も）・使えない間に送った頂点・大きさの変更が戻ることを確かめた。本物の GPU（D3DImage の共有方式）でも、実物のモデルを出したままヘルプのメニューから作り直し、同じ絵に戻って再生が続くことを確かめた。
- **まだ:** 本物のドライバーの更新・GPU の応答なし（TDR）での確認。

### シーンのカメラの初期位置

- MMD の初期のカメラと同じにした: 注視点 (0, 10, 0)、距離 45、回転 0、視野角 30。人の大きさのモデルなら全身が収まる（確認用の立方体は小さく映る）。

### 作品のフレームの速さを変えたとき

- キーがあれば尋ねる。「はい」= キー・終わりのフレーム・今のフレームを同じ割合で動かし、動きの秒数を保つ。「いいえ」= キーはフレームの番号のまま（動きの速さが変わる。Blender と同じ）。キーが無ければ尋ねずに変える。
- 縮めて同じフレームに重なったキーは後ろのものを使い、数を知らせる。広げるときは、1 フレームしか離れていなかったカメラのキー（切り替え）を段階の補間にする（VMD の読み込みと同じ）。
- フレームの速さの変更は元に戻せる（キーの位置を合わせたときは、そのキーも戻る）。

## 16. 物理演算（確定・Phase 3 の 1 段階目）

### Bullet の取り込み方

- **Bullet Physics 3.25**（2023 年の、今ある中で最新の版。zlib ライセンス）。MMD 本体は Bullet 2.75 を使っているが、使う部品（剛体と、6 自由度のばね付きジョイント `btGeneric6DofSpringConstraint`）は 3.x にも同じものがある。
- 衝突・剛体・数学の 3 つのフォルダだけを `external/bullet3` に**そのまま写した**（約 4 MB、cpp 153 個。入手元と確かめ方は `external/README.md`）。外の道具（vcpkg など）やネットにつながらずにビルドでき、版も固定できるため。最初のビルドが 30 秒ほど長くなる。
- 物理は描画エンジンとは**別の DLL**（`3DTheater.Physics.Native`、公開する関数は `include/tp_physics.h`）。GPU に関係なく、どのスレッドからでも使える（1 つの世界は同時に 1 つのスレッドから）。後で物理を前もって計算しておく（キャッシュ）とき、画面とは別のスレッドで回せる。
- C# 側は `3DTheater.Physics`（`PhysicsWorld` = Bullet の世界、`ModelPhysics` = PMX の剛体とジョイントからモデルの物理を作る）。

### 計算のしかた（saba・three.js の MMD の物理と同じ考え方）

- 物理の世界は**モデルごとに 1 つ**で、モデルの座標で計算する。重力は 98（9.8 × 10。saba・three.js と同じ値）。モデルを傾けて置いたら、重力も傾ける。**モデルどうしの剛体はぶつからない。床（地面）との当たりも無い**（持ち越し）。
- 剛体の種類（PMX）:
  - ボーン追従: ボーンの置き方に合わせて外から動かす（ほかの剛体を押すが、押されない）。
  - 物理: 計算の結果でボーンを置く。
  - 物理＋ボーン位置合わせ: 向きだけ物理に従い、位置はボーン（動かした値）のまま。
- 衝突: 16 個のグループと、「ぶつかる相手」のビット。PMX の仕様では「非衝突グループフラグ」と書かれているが、実際のファイルには「ぶつかる相手」のビット（PMXEditor で「非衝突」に印を付けたグループが 0）が入っている（saba・three.js と同じ扱い）。読み込みの名前を `CollisionMask` に直した。
- ジョイント: 6 自由度のばね付き（PMX 2.0 の標準）と、PMX 2.1 の 6 自由度（ばねなし）。PMX 2.1 の点・円錐・スライダー・蝶番は、まだ使わない（読み込みレポートで知らせる）。
- 剛体とジョイントの回転は、ボーンと同じく Z → X → Y の順。座標は MMD と同じ左手系のまま Bullet に渡す（Bullet の計算は座標系の向きに依らない）。
- 1 フレームを 1/120 秒ずつに分けて進める（30 fps なら 4 回）。ボーン追従の剛体は、前のフレームの置き方から今の置き方まで少しずつ動かす（急に動いたときに、髪が体を突き抜けにくくする）。
- **姿勢の計算の順番（MMD と同じ）:** 物理後でないボーンまで（モーフ・回転・付与・IK）→ 物理 → 物理で動いたボーンの子（物理なし）を求め直す → 物理後のボーン（付与・IK）→ 頂点の変形。
  - 物理で動いたボーンを付与の元にするときは、物理で決まった回転を受け継ぐ。saba は動かした値を受け継ぐが、それでは物理後のボーンが物理に付いていかないため（MMD 本体とは見比べていない）。

### いつ進めるか（`PhysicsClock`）

物理は前の結果に続けて計算するので、フレームが続いているときだけ進め、飛んだときは置き直す。17 章の焼き込みができてからは、焼き込みがまだのフレームと、止まっているときに姿勢を変えた直後だけ、この進め方で計算する。

- 再生中・1 フレーム送り: 進んだフレームの分だけ進める（4 フレームまで）。
- フレームを飛ばした・戻した・ループで先頭へ戻った: 剛体を今の姿勢へ置き直し、ボーンを止めたまま 1 秒分計算して落ち着かせる（置き直すたびに髪が跳ねないように）。
- 止まっているときに姿勢を変えた: 2 秒間、実際の時間で動かして落ち着かせる。その間は描画を続け、その後は止めて休ませる（「編集時は軽く」）。
- 物理の ON / OFF: モデルメニューとツールバーの「物理」。初期値は ON で、プロジェクトに保存する（変えたら題名に「＊」）。「物理をリセット」で剛体を今の姿勢に置き直す。
- 物理の計算に失敗したモデルは、そのモデルの物理をやめて続ける（ログに残す）。物理の DLL が使えなくても、モデルは物理なしで読み込む。

### 重さ

- 実物のモデル（剛体 34 個・うち物理で動くもの 15 個、ジョイント 15 個）を 8 区画に出して再生して、1 回の描画が約 7.8 ms（そのうち変形と物理で 4.4 ms。Debug ビルド）。

### 確かめたこと・まだのこと

- テスト: 自由落下、振り子、衝突のグループ、置き直し、横に伸ばした髪が垂れる・その子（物理なし）が付いていく・物理後のボーンが付与で付いていく、頭を動かすと髪の付け根が付いていく、位置合わせの種類、物理なしのときに計算の結果が変わらないこと、進め方の決め方。
- 実物のモデルで、頭を 70° 傾けたポーズのとき、物理 ON なら前髪などが重力で垂れ、OFF なら頭と一緒に傾くこと、ON に戻すと同じ形に落ち着くこと、暴れないことを画面で確かめた。このモデルは髪が短く、揺れは小さい。
- **MMD 本体と揺れ方を見比べてはいない。長い髪・スカートのモデルでも、まだ試していない。**
- 物理の結果を前もって計算して覚えておくこと（焼き込み）と、フレームを往復しても同じ姿勢に戻ることは、17 章で作った。

## 17. 物理の焼き込み（確定・Phase 3 の 2 段階目）

指示書 Phase 3 の「物理キャッシュ」「スクラブ整合性（再生位置を往復しても姿勢が戻る）」にあたる。

### 何を覚えるか（`PhysicsBake`）

- モデルごとに、**0 フレーム目から 1 フレームずつ順に計算した全剛体の置き方**を、フレームごとに覚える（フレーム × 剛体 × 28 バイト。実物のモデルの 34 剛体・301 フレームで約 0.3 MB）。
- 計算は画面用とは**別の物理の世界**で行う。0 フレーム目は剛体を置き直して 1 秒落ち着かせ、その後は 1 フレームずつ進める（再生と同じやり方）。
- 各フレームのボーン・モーフの値は `PoseSampler` で求める。決まりは `AnimationService` と同じ（未登録の変更がある項目とキーの無い項目は今の値、それ以外はキーの値）で、シーンの値は書き換えない。

### いつ作るか

- 画面の手が空いたとき（WPF の Dispatcher の Background）に、1 回 8 ms ずつ、終わりのフレームまで作る。**UI スレッドで小分けに作る**のは、シーンの値（キーやボーン）を別のスレッドから読まないため（別スレッドにするなら、値の写しを取る仕組みが要る。持ち越し）。
- 実物のモデルで、301 フレームを約 0.8〜1.5 秒で作り終えた（Debug ビルド）。状態表示に「物理を計算中 n / N」と出る。

### 表示のしかた

- 作り終えたフレームは、焼き込みの結果を当てはめる。**どの順で再生位置を動かしても、同じフレームなら同じ姿勢**になる。再生中も物理を計算しないので軽くなった（実物のモデルで、1 回の描画の「変形」が 4.4 ms → 約 3 ms）。
- 足りないときは、少しなら（再生中 10 フレーム・止まっているとき 90 フレームまで）その場で作って追いつく。それより多ければ、画面の物理（16 章の進め方）で見せておき、そのフレームができたら切り替える。

### 作り直すとき

- キー・未登録の印の変更、キーの無い項目と未登録の変更がある項目の値の変更（その値は全フレームに効くため）、モデルの向き（重力の向き）、フレームの速さ、「物理をリセット」、物理を ON にしたとき。
- **キーのある項目の値の変化（再生位置を動かしたときのキーの当てはめ）では作り直さない**（キーから決まる値なので）。
- 今は、変えるたびに 0 フレーム目から作り直す（途中から作り直すには、そのフレームの剛体の速さなども覚える必要がある。持ち越し）。
- 止まっているときに手で姿勢を変えたら、2 秒は画面の物理で揺れを見せ、その後で焼き込みの結果に切り替える（そのとき形が少し変わることがある）。

### 確かめたこと

- テスト: 焼き込みの結果が、最初から続けて計算した結果と同じこと、行き来しても同じ姿勢になること、作り直し、`PoseSampler` の決まり（キー・今の値・未登録の変更）と、どの変更で作り直すか。
- 画面: 実物のモデルで 40 → 10 → 200 → 39 → 40 フレームと動かして、最初に見たフレーム 40 と**画素が完全に一致**した（違う画素 0。比べるための目安として、フレーム 40 と 10 では 7,367 画素違う）。
- 確かめる途中で直したこと:
  - フレームの移動（キーの当てはめ）を「姿勢を変えた」と受け取り、2 秒間画面の物理で見せていたため、行き来すると少し違う絵になっていた。手で変えたときだけ揺らすようにした。
  - ツールバーの「物理」ボタンが、押した状態そのものではなくクリックの知らせで切り替えていたため、キーボードや支援技術から切り替えると表示と中身がずれた。状態で切り替えるようにした。
  - 16 章の「物理 ON・OFF の見比べ」は、このときの確かめ方の誤りで OFF に切り替わっていなかった。正しく切り替えて確かめ直し、ON では前髪などが重力で垂れ、OFF では頭と一緒に傾くことを確かめた。
- 焼き込みの結果は、書き出し（連番・動画。24・25 章）でも使う。

## 18. 音声（確定・Phase 3 の 3 段階目）

指示書 3.1 の「音声のトラック」「音声波形・再生との同期（正確な同期には再生時刻の単一管理が必要）」にあたる。

### 部品: NAudio 2.4.0（`NAudio.Core` と `NAudio.Wasapi`、MIT）

- 最新の 3.x は 2026 年 8 月に出たばかりで、その後 2 か月で 3 回版が上がっている（落ち着いていない）。2.x も 2026 年 8 月に 2.4.0 が出ていて保守が続いているので、2.4.0 を使う。3.x は落ち着いたら見直す（持ち越し）。
- 読み方: WAV（PCM・浮動小数）は直接読み、それ以外（MP3・AAC/M4A・WMA・FLAC）は Windows の Media Foundation で読む。鳴らすのは WASAPI の共有モード（遅れ 60 ms）。
- 部品は `3DTheater.Media`（画面に依存しない）にまとめた: `AudioClip`（長さ・形式・波形）、`AudioPlayer`（鳴らす・鳴っている位置）。

### シーンでの扱い

- シーン一覧の「音声」のまとまりに、音声を 1 つまで置く（MMD と同じく 1 つ）。読み込み（ファイルメニュー・ウィンドウへのドラッグ）・入れ替え・外す（ファイルメニュー・Delete）は元に戻せる。元のファイルは書き換えない。
- プロパティ欄で、鳴り始めのフレーム（負なら音声の頭を飛ばす）と音量（0〜100%）を変えられる（元に戻せる）。シーン一覧の目の印を切ると音を消す。**音を消しても音量 0 で流し続け、時計としては使い続ける**（音を消すとタイミングが変わる、ということが起きないように）。
- 作品が音声より短ければ、音声の終わりまで終わりのフレームを伸ばす。

### 再生の時計（再生時刻を 1 か所で決める）

- `PlaybackService` に外の時計（`IPlaybackClock`）を渡せるようにした。再生中に音声が鳴っていれば、**鳴っている位置（音の出る装置の時計で数えた位置）からフレームを決め、実際の時間を足していかない**。映像と音がずれていかない。
- 時計が少し遅れて見えても（鳴らし始めの直後など）、フレームは戻さない。
- 鳴り始めのフレームより前と、音声が終わった後は、今までどおり実際の時間で進める。
- ループで先頭へ戻ったとき・再生中に位置を飛ばしたとき（鳴っている位置と 3 フレーム以上ずれたとき）は、その位置から鳴らし直す。再生を止めると止める。
- 音の出る装置が無いときは、音なしで再生する（時計は実際の時間）。プロパティ欄に注意を出す。

### 波形

- 1/100 秒ごとのいちばん大きな振れ幅を、別のスレッドで求めておく（20 秒の WAV で数 ms）。
- タイムラインの音声の行と、上の目盛りの帯（薄く）に描く。目盛りの帯にも描くのは、音声の行がスクロールで隠れていても、拍の位置が見えるようにするため。

### 保存

- プロジェクトに、音声の場所（プロジェクトから見た場所と絶対パス）・名前・鳴り始め・音量・鳴らすか・ロックを保存する。見つからなければ知らせ、保存し直しても消さない（モデルと同じ）。

### 確かめたこと・まだのこと

- 音の出る装置で: 頼んだ位置から鳴り始め、実際の時間どおりに進むこと（装置の遅れは約 15 ms で一定）、鳴っている途中で別の位置から鳴らし直せること、最後まで鳴った知らせ。
- テスト: 再生位置が時計に従う・戻さない・時計が答えなければ実際の時間・時計で終わりを越えたらループか止まる、音声の項目（終わりのフレーム・元に戻す・新しいプロジェクトで外す）、保存（相対の場所・見つからなかった音声を書き戻す）、WAV の情報と波形、壊れたファイル。
- 画面（聞こえない 8 Hz の確認音、20 秒）: 波形の山が毎秒（30 フレームごと）の目盛りにそろうこと、3 秒再生して止めたとき、鳴っていた位置（3.122 秒 = 93.6 フレーム）と表示していたフレーム（93）が 1 フレーム以内で合うこと、読み込みを元に戻す・やり直すこと、音声の入ったプロジェクトを開くこと。
- **実際の曲を、耳で聞いての確認はまだ**（利用者の確認を待つ）。止まっているときに再生位置を動かしたときの音（スクラブ）、複数の音声、100% より大きな音量はまだ。

## 19. グラフエディタ（確定・Phase 3 の 4 段階目）

指示書 3.1 の「キーの補間はステップ・線形・ベジェ。グラフエディタをドッキングパネルとして追加」にあたる。

### パネル

- 「グラフ」パネル（初めは下の段の、タイムライン・ログと同じ場所のタブ）。前の版で保存した画面の並びには無いので、起動したときにタイムラインと同じ場所へ足す。
- 対象: タイムラインで選んだキーの項目。キーを選んでいなければ、シーン一覧で選んだボーン・モーフ・カメラ。
- 左: **値のグラフ**。横がフレーム、縦が値。ボーンは移動 X・Y・Z と回転 X・Y・Z（度。1 周を越えても飛ばないようにつなぐ）、モーフは値、カメラは注視点 X・Y・Z・回転 X・Y・Z・距離・視野角。線ごとに出す・隠すを切り替えられる。キーの点、下の帯のキーの印（選んだキーは橙）、今のフレームの線、編集しているキーの範囲（前のキーからこのキーまで）の薄い色を描く。
  - 下の帯のキーの印をクリックでそのキーを選ぶ（Ctrl で足す）。ほかの所をクリックでそのフレームへ。ホイールで左右、Ctrl + ホイールで拡大縮小、「全体を表示」でキーの範囲に合わせる。
- 右: **補間曲線の枠**（MMD と同じく、横が時間の進み・縦が値の進みで 0〜127）。2 つの制御点（赤・青）をドラッグで動かす（1/127 刻み）。数でも入れられる。決まった形のボタン（線形・なめらか・加速・減速・段階）。
  - 曲線の番号は MMD と同じ: ボーン 4 本（移動 X・Y・Z、回転）、モーフ 1 本、カメラ 6 本（注視点 X・Y・Z、回転、距離、視野角）。「全部同じ」で全部の曲線をまとめて変える。グラフでは、編集している曲線で動く線を太く描く。

### どのキーの曲線を変えるか

- 補間曲線は MMD と同じく「前のキーからこのキーまで」の動き方で、後ろのキーが持つ。最初のキーには無い。
- 選んでいるキー（ロックしていないもの）全部に同じ曲線を当てる。**キーを選んでいなければ、今のフレームにあるキー**（MMD の補間曲線の欄と同じ）。
- 段階のキーの点を動かすと、曲線に戻る。

### 元に戻す

- ドラッグ 1 回が 1 つの「元に戻す」（ドラッグ中の右クリック・Esc で取り消し。ギズモと同じ）。数の入力は、同じ欄を続けて変えたら 1 つにまとめる。ボタンはそれぞれ 1 回分。
- 編集の部分は `CurveEditing`（`3DTheater.Editor`）にまとめた: 曲線の読み書き、前のキー、グラフに描く値、0〜127 への丸め。

### 確かめたこと・まだのこと

- テスト: 1 本だけ・全部の曲線を変える、段階から曲線に戻る、モーフ・カメラの曲線、前のキー、グラフの値が曲線に沿うこと・回転が 180° を越えても飛ばないこと、0〜127 への丸め。
- 画面（実物のモデル・測定用のモーション）: 左ひじを選んでフレーム 30 にすると「フレーム 0 → 30 の動き方（今のフレームのキー）」が出ること、「なめらか」で曲線の枠と値のグラフが S 字に変わること、数の入力（1 横 = 100）、それぞれが元に戻すに 1 回分ずつ積まれ、戻すと直線に戻ること。
- 気づいたこと: 数の入力欄は、入力中（選んだまま）だと、元に戻しても表示が前の数のまま残る（ほかの入力欄と同じ作り）。
- **曲線の点のドラッグと、グラフのキーの印のクリックは、実際のマウスではまだ試していない。** グラフの上でキーの値そのものを動かすこと、曲線のコピーと貼り付けはまだ。

## 20. モーフの拡張（確定・Phase 3 の 5 段階目）

指示書 4.3 の「段階対応：フリップ／インパルスモーフ等の PMX 2.1 拡張」「モーフ専用パネルから値変更、プリセット・キーフレーム登録、複数値の混合を行える構造にする」にあたる。

### フリップモーフ（PMX 2.1）

- 決まりは PMX エディタに付く仕様書（PMX 2.1）に従った（MMD 本体は PMX 2.1 に対応していないので、見比べる相手は PMX エディタ）。データはグループモーフと同じ形（モーフの番号と値）。
- 自分の値で、登録したモーフを **1 つだけ** 選ぶ: 番号 = `(int)((登録数 + 1) × 値) − 1`（範囲の外は端に寄せる）。値 0〜1 を（登録数 + 1）に等しく分け、最初の区切りは「どれも選ばない」。選んだモーフの値を、登録の値で **書き換える**（掛け算・足し算ではない）。選ばなかったものはそのまま。
- 求める順（仕様書のとおり）:
  1. 番号の順に、フリップモーフ（グループモーフの中のものは、グループの値 × 割合を値として）で書き換える
  2. もう一度番号の順に、グループモーフの値 × 割合を中のモーフに足す（中のフリップモーフは除く）。グループモーフの値は 1 の後のものなので、**フリップモーフでグループモーフ（表情のまとまり）を切り替えられる**
- グループモーフと違い、選び先に決まりは無い（自分自身・ほかのフリップモーフも選べる）。グループモーフの中のグループモーフは、これまでどおり効かせない（MMD・仕様書と同じ）。
- 計算は `PoseEvaluator`（`FlipIndex` と、モーフの値を求める所）。フリップモーフが無いモデルでは 1 の見回りを省く。

### インパルスモーフ（PMX 2.1）

- 剛体に勢いを与える。データは剛体の番号・ローカルかどうか・移動の速さ・回転の力。物理演算が ON のときだけ効く（焼き込みにも入る）。
- 仕様書のとおり: 値が 0 のモーフは使わない。速さと回転の力が両方 0 の項目は **「止める」**（剛体の速さ・回転の速さ・たまった力を 0 にする）。それ以外は 設定の値 × モーフの値 を、剛体ごとに「剛体の向きで回すもの（ローカル）」と「そのまま使うもの」に分けて足し、止める → 勢いを与える、の順に Bullet の `applyCentralImpulse`・`applyTorqueImpulse` で与える。ボーン追従の剛体には与えない。
- **いつ与えるか**（仕様書には書いていないので決めた）: 物理を進める直前に、**1 フレーム（タイムラインの 1 コマ）につき 1 回**。再生で何フレームか続けて進めるときはその数の分、止まっているときに落ち着かせる間は進めた時間の割合の分。焼き込みも 1 フレームずつ同じに与えるので、画面の計算と焼き込みが合う（テストあり）。
- 物理の DLL に `tp_world_apply_impulses` を足した（API 0.2）。

### モーフのパネル

- 行の右の **◆**（今のフレームにキーがあれば橙、無ければ ◇）で、そのモーフのキーを今のフレームに今の値で登録する（元に戻せる）。
- 未登録の変更があるモーフは名前に「＊」を付け（シーン一覧と同じ）、上に「＊ 未登録の変更 n 個」と「まとめて登録」（このモデルのモーフの未登録の変更を全部キーにする）を出す。
- **表情のプリセット**（下の欄）:
  - 「保存」: **今上の一覧に出ているモーフ**（分類と名前の絞り込みに合うもの）の値を、名前を付けて覚える。0 のモーフも覚えるので、当てると 0 に戻る。目だけ・口だけのプリセットは、分類か名前で絞ってから保存する。名前が空なら「表情 1」のように付け、同じ名前があれば置き換えるかを尋ねる。
  - モーフは **名前で合わせる** ので、同じ名前のモーフを持つモデルなら、別のモデルで作ったプリセットも使える（行の「2/2」は、このモデルで合うモーフの数 / 覚えている数）。
  - 置き場所: `%APPDATA%\3DTheater\UserSettings\morph-presets.json`。画面の設定と同じく利用者ごとで、プロジェクトには入れない。プリセットの一覧の変更は元に戻すの対象にしない。読めないファイル（壊れた・新しい版）は上書きしない。
- **混ぜる**（指示書の「複数値の混合」）: プリセットごとの割合（0〜100%）のつまみ・数で、すぐ当てる。値 = 基準 + Σ 割合 ×（プリセットの値 − 基準）（0〜1 に収める）。基準は混ぜ始めたときの値で、割合を全部 0 に戻すと基準に戻る（「混ぜる前に戻す」）。「当てる」はそのプリセットを 100% にする。
  - 手で値を変えた・再生位置を動かした・元に戻したなど、ほかの操作で値が変わったら、その値を新しい基準として割合を 0% に戻す（値はそのまま）。
  - 続けて変えた分は 1 つの「元に戻す」にまとめる（まだ触っていないモーフを持つプリセットを混ぜ始めたところからは、新しい 1 つ）。混ぜた値も、手で変えたのと同じく未登録の変更になる（自動キーが ON ならキーになる）。ロックしたモーフは変えない。
- 編集の部分は `MorphPreset`・`MorphPresetLibrary`・`MorphMixSession`（`3DTheater.Editor`）。

### 確かめたこと・まだのこと

- テスト: フリップの区切り方と端、選んだものだけを書き換えること、グループモーフの切り替え、グループの中のフリップ、番号の順。インパルスで剛体が押した向きへ振れ・値が大きいほど強いこと、ローカルは剛体の向きで回すこと、止める、ボーン追従の剛体は押さないこと、焼き込みと画面の計算が合うこと、物理の DLL の勢いの受け渡し。プリセットの保存（0 も覚える・名前で合わせる）・一覧の置き換え・名前の変更・保存と読み込み・壊れた項目、混ぜた値・元に戻す・ほかの操作で基準が変わること・ロック。
- 画面（実物のモデル）: まばたきを 1 にすると「＊」と「未登録の変更 1 個」が出ること、◆ でキーを登録して ◆ が橙になり、元に戻すと ◇ に戻ること、プリセットを 2 つ保存（ファイルにも書かれる）、「すべて 0」の後に「目を閉じる」50%・「口を開ける」100% で、目が半分閉じ口が開くこと、元に戻す、「当てる」、手で値を変えると割合が 0% に戻ること、確認してから消すこと。ログにエラーなし。
- **フリップ・インパルスモーフを持つ実物のモデル（PMX 2.1）では、まだ試していない**（手元に無い。テストのモデルでだけ確かめた）。インパルスの強さを PMX エディタと見比べることもまだ。
- プリセットの名前の変更（作りはあるが画面にはまだ）、並べ替え、ファイルとしての書き出し・読み込み（ほかの人と分ける）はまだ。

## 21. 元に戻す・やり直しの検証（確定・Phase 3 の 6 段階目）

指示書 Phase 3 の「Undo/Redo の検証」にあたる。

### 確かめ方（`UndoRedoVerificationTests`）

- 乱数で選んだ編集を 120 回続ける: ボーンの移動（続けた分はまとまる）・回転、モーフの値、カメラ、キーの登録、未登録の変更をすべて登録・破棄、キーの削除・移動・複製・補間・補間曲線・コピーと貼り付け、ドラッグ（確定・取り消し）、フレームの速さの変更（キーも合わせる・そのまま）、表情の混合、鍵、モーフをすべて 0、それに履歴に積まない操作（再生位置の移動・自動キーの切り替え）。
- 各時点の状態（シーンの全項目の値とキー、フレームの速さ・終わりのフレーム）を覚え、**全部元に戻すと 1 つずつ前の状態に、全部やり直すと 1 つずつ後の状態に、ぴったり（数の 1 桁も違わず）戻る** ことを確かめる。途中まで戻して新しく編集すると、やり直しの履歴が消えることも。これを 100 通りの乱数で行う（1 秒ほど）。
- キーのある項目の値は再生位置で決まり、元に戻すは再生位置を動かさない決まりなので、比べる前に、その状態を覚えたときのフレームへ移る。

### 見つかって直したこと

- **自動キーを途中で切り替えると、やり直しでキーが戻らないことがあった**: 自動キーが ON の操作（キーも写す）のすぐ後に、同じ値を OFF で変えると、2 つが 1 つの「元に戻す」にまとまり、後のほう（キーを写していない）の写しでやり直していた。キーを写したかどうかが違う操作はまとめないようにした（`EditService.Change`）。
- **ボーンの回転を元に戻すと、値がごくわずか（7 桁目）ずれることがあった**: 回転を入れるたびに長さを 1 にそろえ直していたため、写した値を戻しても同じにならなかった。長さがほぼ 1 なら、そのまま使うようにした（`BoneNode.Orientation`）。見た目には分からない差だが、「変わったかどうか」の判定や、保存したプロジェクトの差に出うる。
- どちらも、短いテストも足した。

### 範囲

- この検証は編集の部分（`3DTheater.Editor`）の操作が対象。モデルの読み込み・外す、音声の読み込み・外すは画面側の操作で、これまでの段階で画面で確かめている（14 章・18 章）。

## 22. トゥーン描画と輪郭線（確定・Phase 4 の 1 段階目）

指示書 6.1 の「トゥーン: MMD に近いトゥーンテクスチャ、セル影、輪郭線、材質単位の表現、スフィアマップ的処理」と、Phase 4 の「基本トゥーン描画・輪郭線」にあたる。影（セルフシャドウ・地面の影）と PNG の書き出しは次の段階。

### 色の計算（MMD と同じ）

- MMD の照明は「拡散」が 0 で、「環境」と「反射」が照明の色という決まりなので、材質の色は次のとおり:
  - 色 = (材質の拡散色 × 照明の色 + 材質の環境色)（0〜1 に収める）、不透明度 = 拡散色の a
  - × テクスチャ → スフィア（掛ける .sph・足す .spa） → × トゥーン → + 反射光（反射色 × 照明の色 × 強さ）
- **トゥーン**: 光の当たり方（面の向きと光の向きの内積、-1〜1）で、トゥーンの画像の上（光の当たる側）から下（反対側）を読む（`0.5 − 内積 × 0.5`）。トゥーンの無い材質には陰影を付けない（MMD と同じ。トゥーンの無い PMX は平らに見える）。
- **スフィア**: カメラから見た面の向きで、スフィアの画像を読む。追加 UV を使う「サブテクスチャ」はまだで、読み込みレポートに知らせてスフィアなしで描く。
- **材質モーフ**: テクスチャ・スフィア・トゥーンの色の掛ける値・足す値、輪郭線の色と太さも変わる（「元の色 × 掛ける + 足す」）。

### 共有トゥーン（toon01〜toon10）

- 材質が共有トゥーンを指すときは、MMD 付属の toon01.bmp〜toon10.bmp を使う決まり。**MMD 付属の画像は再配布できないのでアプリには入れない**。
  - モデルのフォルダから上へたどって、MMD のフォルダ（`Data\toon01.bmp`〜`toon10.bmp` がある所）が見つかれば、利用者の手元のその画像を使う（MMD の `UserFile` の下にモデルを置いている場合）。
  - 見つからなければ、**自前の画像**（`DefaultToons`。上半分が白、下半分が影の色で、境目を少しぼかす。影の色は灰色・肌・水色などを自前で決めた）を使う。MMD の見た目とは影の色が少し違う。
- モデルのトゥーンがファイル名だけで「toon01.bmp」などを指していて、そのファイルがモデルの横に無いときも、共有トゥーンとして扱う（MMD と同じ。古いモデルに多い）。決め方は `PmxToon`。

### 照明

- シーンの照明の項目（最初の 1 つ）を使う。向きは項目の回転で、回していないときに +Z を向く（カメラと同じ決まり）。色は MMD の初期値 154/255 × 明るさ。**照明を隠すと照明なし**（材質の環境色だけ）。
- 新しいシーンの照明は、MMD の初期の向き（光が進む向き (-0.5, -1, 0.5)。回転 X 54.7°・Y -45°）にした。前の版で保存したプロジェクトは、保存した向き（X 45°・Y -30°）のまま開く。
- 照明の色の設定、VMD の照明のキーはまだ。

### 輪郭線

- 材質の「エッジ」が ON のときに描く。モデルの材質を全部描いた後に、裏側の面だけを、**画面の上で**法線の向きへ決まったピクセルだけ広げて描く（表の面の外にはみ出した分が線になる）。遠くても近くても、画面の上で同じ太さ。
- 太さ（ピクセル）= 材質のエッジの太さ × 頂点のエッジの倍率 × 1 あたりのピクセル。1 あたりのピクセルは、画面の高さ 1080 までは 1、それより大きい画面・書き出しでは高さに比例させる（4K の書き出しでも 1080 のときと同じ割合に見えるように）。そのため、小さなプレビューでは書き出しより線が少し太く見える。
- 線の色はエッジの色。不透明度は エッジの色の a × 材質の不透明度（材質モーフで消した部分の線も消える）。
- 両面の材質を裏から見たとき、同じ奥行きの面を線の色で塗りつぶさないよう、線の奥行きを少し奥へずらしている。
- MMD 本体の線の太さとの見比べはまだ（手元に MMD が無い）。

### 描画エンジン（API 0.6）

- 材質に、トゥーン・スフィアのテクスチャ、スフィアの使い方、輪郭線の色・太さを足した。頂点ごとの輪郭線の倍率は、変形する頂点とは別の、変わらないバッファーに入れる（毎フレーム送らない）。
- 1 枚の描画の条件に、照明の向き・色と、輪郭線の 1 あたりのピクセルを足した（照明は `TT_FRAME_USE_LIGHT` のときだけ。無ければ MMD の初期の照明）。
- トゥーン・スフィアは端で止める読み方（トゥーンの上端と下端の色が混ざらないように）。

### 確かめたこと・まだのこと

- テスト（描画エンジン、ソフトウェア描画）: トゥーンで光の当たる側と反対側の色、照明の色、スフィアの掛ける・足す、輪郭線が面の外にだけ出ること・太さ 0 と材質モーフで消えること、知らないスフィアの使い方を断ること。C# からも、構造体の並びが合っていて、トゥーン・照明・輪郭線が届くこと。材質モーフ（輪郭線・スフィア・トゥーン）、トゥーンの決め方、自前のトゥーンの画像、照明の向き（新しいシーンが MMD の初期の向き）・隠したとき・輪郭線のピクセル。
- 画面（実物のモデル）: カメラを顔に寄せて、髪と目のスフィアの光沢、髪・顔の輪郭線、トゥーンの陰影が出ること。照明を横から当てると、照らした側が明るく、反対側にトゥーンの影の色が付くこと。
- **MMD 本体と並べての見比べはまだ**（手元に MMD が無い）。影（セルフシャドウ・地面の影）、PNG の書き出しは次の段階。

## 23. 影（セルフシャドウ・地面の影）（確定・Phase 4 の 2 段階目）

Phase 4 の「影」にあたる。MMD の 2 種類の影を作った。どちらもレンダリングのメニューで ON / OFF でき（初期値は ON）、プロジェクトに保存する（前の版のファイルは ON）。

### 地面の影

- 材質の「地面影」が ON の部分を、照明の向きに沿って高さ 0 の床へ押しつぶして描く（床から 0.01 だけ浮かせる）。色は半透明の黒（不透明度 0.5。自前で決めた値で、色の設定はまだ）。
- 重なった所が二重に濃くならないよう、ステンシル（画面の点ごとの印）で 1 点 1 回だけ塗る。モデルより先に描き、モデルの奥行きで隠れる所は後から描くモデルが上書きする。
- 下から・真横から照らすときは描かない。不透明度 0 の材質（材質モーフで消した部分）は描かない。

### セルフシャドウ

- 照明から見た奥行きの画像（2048 × 2048。描画の条件で 256〜8192 に変えられる。書き出しで大きくする予定）を作り、各点が照明から見てほかの面より奥にあるかで影を決める。境目は周りの 9 点を比べてぼかす。
- 範囲は自動: 照明から見た縦横は「影を落とすモデル」の囲みの箱が全部入るように、奥行きは「影を受けるモデル」も入るように（影を落とすものより照明から遠い床などを範囲の外にしないため）。MMD の「影範囲」の設定は無い。
- 影を落とすのは材質の「セルフ影マップ」（影を落とす）、受けるのは「セルフ影」（受ける）が ON の材質。不透明度 0 の材質は影を落とさない。
- **影を受ける材質は、MMD のセルフシャドウの描き方にする**: 光の当たり方（面の向きと光の向きの内積 × 3 を 0〜1 に収めた値）と、影の当たり方の小さいほうで、「影の色（色 × トゥーンのいちばん下の色）」と「光の当たる色（色 + 反射光）」を混ぜる。セルフシャドウを使うと、トゥーンの段階の画像ではなくこの決まりで陰影が付く（MMD と同じ）。そのため、トゥーンの無い材質（いちばん下が白）には影がほとんど見えない（MMD と同じ）。
- 影が自分の面に細かく落ちないよう、奥行きの画像は面の傾きに応じて奥へずらして描き、比べるときもワールドの長さで 0.08 だけ奥へずらす。
- 奥行きの画像は、描くたびに作り直す（画面が 8 区画なら 8 回）。モデル 1 体では軽いが、重くなったら 1 回の更新で 1 度だけ作るようにする。4096 にしても、試したモデルでは見た目はほとんど変わらなかった。

### 描画エンジン（API 0.7）

- 材質の旗に、地面影・影を落とす・影を受ける を足した。描画の条件に、セルフシャドウ・地面の影の旗、地面の影の色、奥行きの画像の大きさを足した。
- セルフシャドウを使わない間は、奥行き 1（何も無い）の 1 × 1 の画像を渡す（読み方の決まりに合わない画像を渡さないため）。

### 確かめたこと・まだのこと

- テスト（描画エンジン、ソフトウェア描画）: 地面の影が床を半透明の黒で暗くし、2 つの影が重なっても二重に暗くならないこと、地面影の無い材質・影を使わない描画・下からの照明では落ちないこと。セルフシャドウが受ける材質にだけトゥーンのいちばん下の色で落ち、光の当たる所は元の色のままなこと、受けない材質・使わない描画では落ちないこと。設定の保存と、前の版のファイルが初期の設定になること。
- 画面（実物のモデル）: 床に地面の影、首と胸にあごの影が落ちること。メニューで切り替えると消え、題名に「＊」が付き、閉じるときに保存を尋ねること。
- MMD 本体との見比べ（影の濃さ・境目のぼけ方・地面の影の色）はまだ。地面の影の色の設定、MMD の「影範囲」・セルフシャドウのモード 2 は無い。

## 24. PNG の書き出し（確定・Phase 4 の 3 段階目）

指示書 6.3 の「初期: PNG 静止画、透過 PNG（RGBA）、PNG 連番。解像度・フレーム範囲・背景透過を設定可能」「描画ギズモ、ボーン、グリッド、UI は通常の最終出力に映り込まない」「進捗、キャンセル、失敗理由を通知」と、Phase 4 の「カメラ、PNG／アルファ付き連番出力」にあたる。

### 画面（レンダリングのメニュー「静止画を書き出す」「連番を書き出す」、ファイルのメニューからも）

- 書き出すもの: 静止画（今のフレーム。フレームは変えられる）か、連番（フレームの範囲。初めは 0〜作品の終わり）。
- 大きさ（よく使う大きさの一覧あり）、なめらかにする（初期値 ON）、背景（透明か、#RRGGBB の色。初期値は白）、書き出し先。
- 書き出し先の初めは「ピクチャ\3DTheater\（プロジェクトの名前）.png」、連番はその名前のフォルダの中。連番は名前の後ろに「_フレームの番号」を、最後のフレームの桁数（4 桁以上）にそろえて付ける（shot_0000.png …）。同じ名前のファイルがあれば、まとめて置き換えるかを尋ねる。
- 書き出し中は進み具合（何枚目・どのフレーム）を出し、「閉じる」が「やめる」になる。やめた・失敗したときは、何枚目まで書いたかと理由を知らせ、ログにも残す。終わったら書き出し先のフォルダを開くかを尋ねる。
- 設定は次に開いたときのために覚える（利用者ごとの設定。プロジェクトには入れない）。

### 描き方

- **シーンのカメラ（カメラ視点）から描く**。映すのはモデルだけで、格子・座標軸・ボーン・ギズモ・選択の枠・**確認用の立方体**は映さない（確認用の立方体はシーンの項目だが、作品の一部ではないので書き出さない）。照明・影・輪郭線はプレビューと同じ設定で、輪郭線の太さは書き出す高さに合わせる（22 章）。セルフシャドウの奥行きの画像は 4096 にする。
- 書き出し専用の画面外の描画先を作り、1 フレームずつ「そのフレームへ移る → 変形 → 描く → 読み出す」。縮小と PNG への変換・保存は別のスレッドで行い、2 枚まで並べて進める。終わったら（やめた・失敗したときも）元のフレームに戻す。
- **なめらかにする**: 2 倍の大きさで描いて、2 × 2 点の平均で縮める（線や輪郭のギザギザが減る）。描ける大きさの上限（1 辺 16384）があるので、なめらかにするときは 1 辺 8192 まで。
- **透明**: 背景を透明で消してから描く。半透明の材質や地面の影を重ねた結果、読み出した色は「透明度をかけ合わせた値」になるので、縮めた後に色を透明度で割り戻して（透明な点は黒）、PNG の決まりに合わせる。縮めるのは割り戻す前（透明な点の色が混ざって縁が黒ずまないように）。背景が不透明なときは、透明度の無い PNG にする。
- **物理**: 書き出す間は、どのフレームも焼き込みの結果で描く（姿勢を変えた直後でも）。足りないフレームは、その場で必要なだけ計算する（17 章の「追いつく上限」を外す）。プレビューと同じ姿勢になる。
- フレームの速さは作品と同じ（1 フレーム 1 枚）。作品と違う速さでの書き出しはまだ。

### 描画エンジン（API 0.9）

- 描画の条件に、背景の色（`TT_FRAME_CLEAR_COLOR`、透明も可）を足した。

### 確かめたこと・まだのこと

- テスト: 連番のファイル名（桁数）、設定の確かめ（大きさ・上限・フレームの範囲・書き出し先）、縮小（透明な所の色が混ざらない）、透明度の割り戻し、色の文字の読み書き。描画エンジン: 決まった色・透明な背景で消せること、透明な背景に半透明の物を描くと透明度をかけ合わせた色で残ること。
- 画面（実物のモデル・測定用のモーション）: 連番（透明・640 × 360・なめらか・11 枚）と静止画（白・1280 × 720・フレーム 30）を書き出し、透明な背景に地面の影が半透明で残ること、静止画にフレーム 30 の姿勢が出ること、余計な物が映らないこと、終わったら元のフレームに戻ることを確かめた。1920 × 1080・なめらかで、1 秒に約 20 枚。途中で「やめる」と、54 枚目までで止まり、書きかけのファイルが残らないこと。
- 開いたときに書き出し先の欄が空になる誤りを、画面での確認で見つけて直した。
- 動画は 25 章。JPEG・作品と違うフレームの速さ・背景の画像・ギズモなどを映す書き出しはまだ。

## 25. 動画の書き出し（確定・Phase 4 の 4 段階目）

指示書 6.3 の「発展: H.264/MP4 動画」と、Phase 4 の「動画出力」にあたる。透明な動画（アルファ対応の透過動画）はまだ。

### 方式（持ち越し事項「動画の書き出し方法」への答え）

- Windows に入っている Media Foundation の書き手（Sink Writer）で、MP4（映像は H.264 の High、音声は AAC）を書く。ffmpeg などは同梱しない（配布の大きさと、ライセンス・特許の扱いが重いため）。GPU の符号化の部品があれば、Windows が選んで使う。
- C++ の DLL `3DTheater.Video.Native`（公開する関数は `include/tv_video.h`、API 0.1）に分けた。描画エンジン・物理とは別。C# 側は `3DTheater.Media` の `VideoWriter`（書き手と、確かめる用の読み取り）と `AudioExportSource`（動画に入れる音声）。
- 1 つの書き手は、作ったスレッドで使い続ける（COM を MTA で使う）。アプリでは書き出し専用のスレッドを 1 本立てる。

### 映像

- 描き方は 24 章と同じ（シーンのカメラ、なめらかにする、物理は焼き込みの結果）。描画と読み出しは UI のスレッド、縮小・色の変換・符号化は書き出し用のスレッドで行い、3 枚まで先に描いておける。
- **色**: BGRA を自前で YUV（NV12、BT.709、明るさ 16〜235）に変換して渡し、その決まりを動画に書き込む（H.264 の VUI と MP4 の colr）。Windows の変換に任せると、小さい動画（640 × 360 など）は BT.601 で変換され、決まりも書き込まれないため、再生ソフトが別の決まりで読むと色がずれる（赤の緑が 25 段ほど）。自前の変換にしてからは、どの大きさでも、書いた色と読み戻した色の差は 0〜3 段（H.264 そのものの分）。
- **大きさ**: 幅と高さは偶数（H.264 の決まり）、各 64〜4096、合わせて 4096 × 2304 の画素まで（縦長の 4K の 2160 × 3840 も書ける）。32 × 32 以下は、この PC の符号化の部品が受け付けなかったので、下限を 64 にした。
- 透明にはできない（動画のときは透明のチェックを使えなくする。PNG のための透明の設定は覚えたまま）。
- **画質**: 1 秒あたりのデータの量 = 幅 × 高さ × フレームの速さ × 0.1（高画質は 0.2）を、1〜100 Mbps に収める。フル HD・30 fps で約 6 Mbps（高画質は約 12 Mbps）。
- フレームの速さは作品と同じ。各フレームの時刻は「フレームの番号 ÷ フレームの速さ」。

### 音声

- 「シーンの音声を入れる」は、シーンに音声があり、見えていて（目の印）、ファイルがあるときに選べる（初期値は入れる）。選べないときは、その訳を横に出す。
- 動画の 0 秒（最初のフレーム）に、音声の「（最初のフレーム − 鳴り始めのフレーム）÷ フレームの速さ」秒目を合わせる。音声より前と、音声が終わった後は無音で埋める。音量の設定を掛ける。
- 48 kHz・2 チャンネル・16 ビットにそろえて（モノラルは両方へ、3 チャンネル以上は 2 つに混ぜる、違う周波数は変換する）、AAC（192 kbps）にする。
- 映像のフレームを書く前に、そのフレームの終わりの時刻までの音声を書く（映像と音声を交互に入れる）。音声の時刻はサンプルの数で数えるので、ずれが積み重ならない。

### 画面（レンダリングのメニュー「動画を書き出す（MP4）」）

- 書き出しの画面に「動画（MP4）」を足した。フレームの範囲（初めは 0〜作品の終わり）、大きさ、なめらかにする、背景の色、画質（標準・高画質）、シーンの音声を入れる、書き出し先（初めは「ビデオ\3DTheater\（プロジェクトの名前）.mp4」）。設定は次に開いたときのために覚える。
- 「名前.書き出し中.mp4」に書き、書き終えてから「名前.mp4」に置き換える（入れ物の形式は拡張子で決まるので .mp4 のまま）。やめた・失敗したときは書きかけを消し、同じ名前の元のファイルはそのまま残る。同じ名前のファイルがあるときは、書き出す前に置き換えるかを尋ねる。
- 進み具合は「何フレーム目 / 全部」で出す。終わったら、フレームの数・秒数・音声のあり／なしを知らせ、フォルダを開くかを尋ねる。

### 確かめたこと・まだのこと

- テスト: MP4 を書いて読み戻す（大きさ・フレームの速さ・長さ・音声の形式、上下が逆さまでないこと、色の決まりが書く側と読む側で合っていること）、音声なしの動画、奇数の大きさや対応しない音声を断ること、同じ名前のファイルを置き換えて書けること、音声の位置合わせ（前の無音・途中から・音量・周波数の変換）、動画の設定の確かめ（偶数・上限・下限・データの量）。
- 画面（実物のモデル・測定用のモーション・聞こえない確認音）: 0〜90 フレームを 1280 × 720・なめらか・音声ありで書き出し（約 4 秒かかった）、1280 × 720・30 fps・約 3.05 秒・音声 48 kHz 2 チャンネルの MP4 になった。最初のフレームは、同じフレームの静止画（PNG）と比べて平均 0.19 段の差（99% の画素は 5 段以内）。同じ名前のファイルがあるところへ 1920 × 1080 で書き始めて「やめる」と、元のファイルが残り、書きかけも残らないこと。終わったら元のフレームに戻ること。1920 × 1080・なめらかで、1 秒に約 15 フレーム。
- 色の変換が大きさで変わることは、確認のための試しで見つけて直した。
- **ほかの再生ソフト（ブラウザー・動画サイトなど）での見え方と音のずれはまだ**（この PC には ffmpeg などの調べる道具が無く、Windows の部品で読み戻して確かめた。色の決まりが書き込まれていることは、ファイルの中身を読んで確かめた）。実際の曲を入れて、耳で音と映像が合っているかもまだ。
- 透明な動画、H.265、作品と違うフレームの速さ、音声だけの書き出しはまだ。

## 26. 描画品質の設定（確定・Phase 4 の 5 段階目）

指示書 6.1 の「編集用の軽量描画と、書き出し用の高品質描画を分離する。プレビュー品質プリセットも設ける」と、持ち越し事項の「描画のなめらかさ（MSAA）」にあたる。レンダリングのメニューの「描画品質の設定」（前は「予定」）を使えるようにした。

### プレビューの品質（利用者ごとの設定。プロジェクトには入れない）

| 品質 | なめらかさ（MSAA の 1 画素あたりの点の数） | セルフシャドウの奥行きの画像 |
|---|---|---|
| 軽い | なし（1 点） | 1024 |
| ふつう（初期値） | 4 点 | 2048（今までと同じ） |
| きれい | 8 点 | 4096 |

- 選ぶとすぐに全プレビューへ反映し、終了時に利用者の設定（`settings.json` の `Rendering`）へ保存する。
- GPU が使えない点の数のときは、描画エンジンが使える中でいちばん近い少ない数にする（ログに 1 度だけ残す。設定の画面にも「この GPU で使えるなめらかさは n 倍まで」と出す）。
- MSAA の描画先（1 点ごとに色 4 バイト・奥行き 4 バイト）が 1 つの区画で 512 MiB を超える大きさでは、収まるまで点の数を半分にする（4K の 1 画面で「きれい」の 8 点は約 506 MiB で、まだ収まる）。区画を大きくして点を減らすときは、大きな描画先を作る前に減らす。

### 書き出しの品質

- プレビューの品質に関係なく、4 点・影 4096（`RenderQuality.Export`）。「なめらかにする」では、さらに 2 倍の大きさで描いて縮める。そのときは描く大きさが 2 倍になるので、上の 512 MiB の決まりで点が減ることがある（4K をなめらかにして書き出すと 8K で描くので 2 点）。作れなかったときは MSAA なしで描く。
- 書き出しの間はプレビューを描かない（`RenderLoop.IsSuspended`）。今までは、書き出しのフレームごとにプレビューまで描き直していた。終わったら描き直す。

### 描画エンジン（API 0.10）

- `tt_view_set_sample_count`（1・2・4・8）。ビューの中に MSAA の描画先と奥行きを持ち、描いた後に、表示・読み出しに使う面（D3DImage と共有する面・スワップチェーンの面）へまとめる（Resolve）。共有する面は変わらないので、WPF 側で面を渡し直さなくてよい。
- MSAA の描画先では、線（格子・座標軸・ボーン・ギズモ・選択の枠）を四角形として描く設定にして、線もなめらかにする（1 点のときより少し太く見える）。
- 作れなかったとき（メモリ不足など）は 1 点に戻して描ける状態にしてから、失敗を知らせる。GPU を作り直すときは、頼まれた点の数で作り直す（新しい GPU で使える数に合わせる）。

### 確かめたこと・まだのこと

- テスト: 斜めの四角形の縁に中間の色ができること（1 点では出ない）、使えない数の扱い、大きさを変えても・大きさ 0 の間に変えても・GPU を作り直しても保たれること、ウィンドウ用のビューでも描けること、C# から変えて読み出せること。品質ごとの値、メモリの上限での減らし方、設定が変わったときだけ知らせること。
- 画面（実物のモデル・顔の寄りのカメラ視点と自由視点）: 3 つの品質を切り替えて撮り比べ、「軽い」は線や髪の縁がギザギザ、「ふつう」「きれい」はなめらかになること。終了時に品質が保存されること。書き出しの後にプレビューが描き直されること。
- 重さ（GeForce RTX 4060 Ti。2 つのプレビューを 4 分割した 8 区画で、測定用のモーションを再生）: 1 回の描画の GPU 待ちは、軽い 1.2 ms・ふつう 2.3 ms・きれい 2.6 ms（全体では 6〜7 ms）。15 章の目安（5 ms）より小さいので、描画専用のスレッドへはまだ分けない。
- 書き出し: 連番 61 枚（1920 × 1080・なめらか・4 点）が、押してから知らせが出るまで 3.8 秒。
- 弱い GPU（内蔵の GPU など）での重さと、ソフトウェア描画（WARP）での画面の確認はまだ（WARP での MSAA と読み出しはテストで確かめた）。

## 27. 映像効果（色調補正・ブルーム・周辺減光）（確定・Phase 4 の 6 段階目）

指示書 6.1 の「リアル／シネマティック: … ブルーム … 色調補正等」と、Phase 4 の「ポストエフェクト」の最初の段階にあたる。画像から画像へ処理する仕組み（ポスト処理の土台）を作り、その上に 3 つの効果を載せた。次の「イラスト風」（色調・質感テクスチャ・ポスト処理）も、この土台を使う。

### 効果

| 効果 | 値 | 中身 |
|---|---|---|
| 色調補正 | 明るさ（段、-3〜3）・コントラスト（0〜2）・彩度（0〜2）・色温度（-1〜1） | 透明度で割り戻した色に、明るさと色温度の倍率 → コントラスト（0.5 を中心に）→ 彩度（明るさとの間を混ぜる）の順にかける |
| ブルーム | 強さ（0〜3）・光り始める明るさ（0〜1）・広がり（0〜1） | 明るい所を半分の大きさで取り出し（境目はなめらかに）、半分ずつ 6 段まで縮めてから、小さい段から順に広げて混ぜ直す（広がりは小さい段の割合）。最後に光として足す |
| 周辺減光 | 強さ（0〜1） | 画面の中心からの距離（四隅で 1）で、0.35 から外側を暗くする（縦横の比は画面に合わせる） |

- 3 つはそれぞれ ON / OFF でき、OFF の間も値は覚えておく。初期値はどれも OFF（新しいプロジェクト・前の版のファイル）。
- **プロジェクトに保存**する（描き方の `rendering.effects`。使っていなければ書かないので、前の版と同じファイルになる）。読むときは値を範囲に収める。変えるとプロジェクトは変更ありになるが、元に戻す・やり直しの対象ではない（影の ON / OFF と同じ）。
- 画面: レンダリングのメニュー「映像効果...」。つまみを動かすとすぐにプレビューへ反映する。「初期値に戻す」で全部 OFF・初期値。

### かけ方（背景と編集用の表示には、かけない）

- 映像効果を使うときは、場面（確認用の立方体・地面の影・モデル）を**透明な背景**で描き、効果をかけてから背景を後ろに置く。背景の色には色調補正・ブルームがかからない（白い背景が全部光ったり、色が変わったりしないように）。周辺減光は背景にもかかる。
- 格子・座標軸・選択の枠・ボーン・ギズモは、効果をかけた**後に**、場面の奥行きを使って重ねる（色が変わったり光ったりしない）。固定視点の「格子をいちばん奥に」は、奥行きを全部 1 にして「何も描かれていない所」だけに描く方法に替えた（効果を使わないときは、今までどおり先に描く）。このため効果を使うときだけ、半透明の材質の向こうの格子が見えない・地面の影の上に格子の線が出る、という小さな違いがある。
- MSAA（26 章）のときは、場面をまとめてから効果をかけ、結果を MSAA の描画先へ書いてから重ね描きをする（効果の結果はどの点も同じ色なので、重ね描きの線だけがなめらかに混ざる）。
- 透明な背景で書き出すとき: ブルームの光は、足した光の分だけ不透明にする（透明な所ににじんだ光も残る）。
- ブルームの広がりは画像の大きさに対する割合なので、プレビューと書き出し（大きさ・なめらかにする）で同じ見え方になる。ブルームの途中の画像は 16 ビットの浮動小数点（光が色の段階に分かれないように）。

### 描画エンジン（API 0.11）

- 描画の条件の最後に `post_flags`（`TT_POST_COLOR`・`TT_POST_BLOOM`・`TT_POST_VIGNETTE`）と値を足した。範囲の外の値は収め、数でない値は「変えない」にする。
- ビューは、効果を使うときだけ、背景なしの場面の画像とブルームの段の画像を作る（大きさが変わったら作り直す）。効果を使わないときは今までと同じ 1 回の描画で、手間は増えない。
- シェーダー: 画面全体の三角形（`PostVS`）、ブルームの取り出し・縮小・拡大（`BloomPrefilterPS`・`BloomDownPS`・`BloomUpPS`）、仕上げ（`PostCompositePS`）。

### 確かめたこと・まだのこと

- テスト（描画エンジン）: 明るさ +1 で 2 倍・彩度 0 で白黒（明るさは保つ）・色温度で赤が増えて青が減る・コントラスト 0 で中間の灰色・周辺減光で四隅だけ暗い・数でない値は変えない・MSAA でも同じ。ブルームで白い四角形の外の近くが明るくなり、遠くの隅には届かない・光り始める明るさを上げるとにじみが減る・透明な背景では光の分だけ不透明になる。背景の色・重ね描きの線・いちばん奥の格子は変わらず、格子はモデルに隠れる（1 点と 4 点の両方）。C# から渡した値が届くこと。
- テスト（C#）: 値を範囲に収めること、変わったときだけ知らせること、新しいプロジェクトで無しに戻ること、保存と読み込み（使っていなければ書かない・一部だけのものは残りを初期値に）。
- 画面（実物のモデル・全身のカメラ視点と自由視点）: 3 つの効果を 1 つずつと全部で撮り比べ、選択の枠・ギズモ・格子には効果がかからないこと、題名に「＊」が付くこと、「初期値に戻す」で全部 OFF になること、白い背景と透明な背景の書き出しにも効果がかかること。再生中（2 区画・ふつうの品質・3 つとも ON）の GPU 待ちは 1.7 ms。
- 白い背景にブルームを強くかけると、明るい肌が背景に溶けて見えにくくなる（光を足す効果なので、背景が明るいほど目立たない）。
- 被写界深度、材質の発光（光る材質だけをブルームさせる）、効果のキーフレーム、効果ごとの元に戻す、トーンマップ（明るさの広い描画）はまだ。

## 28. イラスト風の表現（線画・塗り・影の色・紙の質感）（確定・Phase 4 の 7 段階目）

指示書 6.1 の「イラスト風: 線画、塗り・影色、色調、質感テクスチャやポスト処理による 2D イラスト感」にあたる。27 章の映像効果の仕組み（場面を背景なしで描いてから画像として処理する）の上に作った。色調は 27 章の色調補正を使う。

### 表現

| 表現 | 値 | 中身 |
|---|---|---|
| 線画 | 太さ（高さ 1080 での画素、0.5〜4）・濃さ・細かさ（0〜1）・色 | 奥行きを見る向きの距離に直し、太さだけ離れた両隣（4 方向）と比べる。**段差**: どちらかが一定の割合以上奥にある。**折れ目**: 「平らな面の上でまっすぐ変わる値」（透視投影では距離の逆数、平行投影では距離）の 2 回の差が大きい。線は手前の物の側に引き、背景には引かない。細かさで、段差（奥行きの差 8%〜0.5%）と折れ目のしきい値を変える |
| 塗り | 段数（2〜8） | 明るさを段数に分け（黒と白を含む）、色合いは保つ。段の境目は少しだけなめらかにする |
| 影の色 | 色・強さ | 暗い所ほど（明るさ 0.2〜0.6 で変わる）、色に影の色の色合い（明るさを 1 にそろえたもの）を掛ける |
| 紙の質感 | 強さ・粒の大きさ（高さ 1080 での画素） | 3 つの細かさの、なめらかなむら（格子点ごとの乱数をつないだもの）を重ね、明るい所ほどわずかに暗くする。背景にもかかる |

- 順番: 色調補正 → 塗り → 影の色 → 線画 → 背景を置く → ブルーム → 紙の質感 → 周辺減光。
- MMD の輪郭線（材質のエッジ。22 章）とは別に引く（線画は、髪の重なりや目の周りなど、面の内側の段差にも引ける）。
- 線画の太さは、輪郭線と同じく高さ 1080 までは指定の画素のまま、それより大きい画像では比例して太くする。紙の粒は高さに比例させる。プレビューと書き出し（大きさ・なめらかにする）で同じ見え方になる。
- 映像効果と同じく、プロジェクトに保存する（描き方の `rendering.illustration`。使っていなければ書かない）。色は #RRGGBB にそろえ、読めない色は初期値にする。変えるとプロジェクトは変更ありになるが、元に戻す・やり直しの対象ではない。
- 画面: レンダリングのメニュー「イラスト風...」。色の欄は、読めない間は前の色のまま。

### 描画エンジン（API 0.12）

- `post_flags` に `TT_POST_LINES`・`TT_POST_POSTERIZE`・`TT_POST_SHADOW_TINT`・`TT_POST_PAPER` を足し、描画の条件の最後に値を足した。
- ビューの奥行きの画像を、描くときは深度バッファー、線画では読む画像として使えるようにした（形式を決めずに作り、ビューごとに決める。MSAA のときは 1 つ目の点を代表にする）。線画を使うときだけ、見る向きの距離を書く画像（`LinearDepthPS`・`LinearDepthMsPS`）を作る。

### 確かめたこと・まだのこと

- テスト（描画エンジン）: 外側の輪郭と、手前の物の縁に線を引き、背景と面の真ん中には引かないこと（1 点と 4 点）。小さな段差（奥行きの差 2%）は細かさを上げたときだけ線になること。平行投影でも引けること。塗りが決まった段（3 段なら黒・中間・白）になること、2 段なら暗い色は黒・明るい色は白になること。影の色で暗い所だけが青みがかること。紙の質感で一様な面にむらができること。C# から渡した線画の値が届くこと。
- テスト（C#）: 値を範囲に収めること・色をそろえること、変わったときだけ知らせること、保存と読み込み。
- 画面（実物のモデル・顔の寄り）: 4 つを 1 つずつと全部で撮り比べ、髪の重なり・目の周り・外側の輪郭に線が引かれること、色の欄で線の色を変えられること、題名に「＊」が付くこと、白い背景の書き出しにもかかること（背景に紙の質感が出る）。再生中（2 区画・4 つとも ON）の GPU 待ちは 2.3 ms。
- 塗りは明るさだけで段を分けるので、明るい肌（明るさ 0.9 ほど）は段数が少ないと白になる。線画は画素ごとに決めるので、細い線は少しギザギザする（MSAA でもなめらかにならない）。材質ごとに線画を外す設定はまだ。

## 29. 拡張材質（PBR・発光）（確定・Phase 4 の 8 段階目）

指示書 6.2 の「MMD 互換材質を保持しつつ、任意の拡張材質オーバーライドを別データとして設定可能にする」「PBR 項目候補: ベースカラー、金属度、粗さ、… 発光 …」「PMX 材質やテクスチャの破壊的変換は避ける。原本素材と拡張設定を分離」と、Phase 4 の「PBR 材質」の最初の段階にあたる。

### 材質の上書き（モデルの項目に持つ）

- モデルの項目（`ModelNode.MaterialOverrides`）に、材質の番号ごとの上書き（`MaterialOverride`）を持つ。上書きのある材質だけを持ち、値で比べる（`MaterialOverrideSet`）。PMX の材質とテクスチャは書き換えない。
- 値: 色の計算（MMD と同じトゥーン / PBR）、色合い（PBR のベースカラーに掛ける）、金属らしさ（0〜1）、粗さ（0.04〜1）、発光の色と強さ（0〜10）。範囲に収めて持ち、上書きなしと同じになったら外す。
- **元に戻す・やり直しの対象**（モデルの項目の値として写す）。つまみを続けて動かした分は、1.5 秒の間は 1 つの操作にまとめる。
- プロジェクトのモデルに `materials`（番号・名前・値。色は #RRGGBB）として保存する。上書きの無いモデルは書かない。読むときは、番号と名前が合えばその材質、合わなければ名前で探し、見つからない材質は読み込みレポートで知らせる。

### 色の計算

- **PBR**: ベースカラー = PMX の拡散色 × テクスチャ（材質モーフの掛ける・足すも効く） × 色合い。シーンの平行光 1 つに GGX の照り返しと Lambert の拡散で応え、セルフシャドウを受ける材質は影の中で光が届かない。スフィア・トゥーン・MMD の反射光は使わない。
- 環境光: 照明の色をもとにした空（上）と地面（下）の 2 色。拡散に使う分（空 0.9・地面 0.3 倍）と、映り込みに使う分（空 1.6・地面 0.45 倍）を分けた（金属は周りの映り込みで色が決まるので、暗いと沈んで見え、拡散まで明るくすると、つや消しの面が白く飛ぶため。実物のモデルの髪を金属にして決めた）。粗いほど映り込みは空と地面の中間の色になる。直接の光の強さは「照明の色 × π」（正面から当たる拡散がベースカラー × 照明の色ほど）。照明を隠すと、発光のほかは暗くなる（光を返すだけなので）。
- **発光**は、トゥーンにも PBR にも足す（1 より明るくでき、27 章のブルームで光らせられる）。
- 輪郭線・地面の影・セルフシャドウを落とす設定は、PMX の材質のまま。

### 画面（モデルのメニュー「材質の設定...」、プロパティ欄のモデルの「材質...」）

- 操作中のモデルの材質を一覧から選び（上書きのある材質に ●）、色の計算・色合い・金属らしさ・粗さ・発光を変える。変えるとすぐにプレビューへ反映する。「この材質を PMX のままに戻す」で上書きを消す。ロックしたモデルは見るだけ。

### 描画エンジン（API 0.13）

- 材質の今の値（`TtMaterialState`）の後ろに `shading`（`TT_SHADING_TOON` / `TT_SHADING_PBR`）・金属らしさ・粗さ・色合い・発光を足した（大きさが 176 → 208 バイトになった。C# 側と大きさが同じことを両方のテストで確かめる）。知らない `shading` はトゥーン、範囲の外の値は収める。
- アプリは、材質モーフがあるとき（毎回）と、材質の上書きが変わったときに、材質の今の値を送る。

### 確かめたこと・まだのこと

- テスト（描画エンジン）: 照明を消すとトゥーンは環境色で見え、PBR は暗いこと。照らすとベースカラーに応じた明るさになること。知らない値はトゥーンになること。滑らかな金属ほど正面の照り返しが強く、見る向きが光からずれると弱いこと。発光は照明に関係なく、トゥーンにも PBR にも足すこと。
- テスト（C#）: 値を範囲に収めること、上書きの組を値で比べ「なし」を外すこと、元に戻す・やり直し、保存と読み込み（名前で探す・見つからない材質を知らせる・上書きが無ければ書かない）。
- 画面（実物のモデル・顔の寄り）: 髪（Hair）を金色の金属（色合い #FFD27A・金属らしさ 1・粗さ 0.3）にして照り返しが出ること、瞳（Eye1+・Eye2+）を水色に光らせられること、元に戻すを 3 回で PMX のままの見た目にぴったり戻ること、書き出しにもかかること。
- 法線マップ・クリアコート・肌の散乱、環境の画像（HDRI）での映り込み、材質の上書きのキーフレームはまだ。材質の設定の画面は、閉じるまでプレビューを回せない。

## 30. 照明の追加（点光源・スポットライト・平行光）（確定・Phase 4 の 9 段階目）

指示書 6.1 の「リアル／シネマティック: … 環境光 …」と、Phase 4 の「ライト」にあたる。シーンのメニューの「照明を追加」（前は「予定」）を使えるようにした。

### 照明の種類と値

- シーンの最初の照明（決まった役目の「light」）は、今までどおり **MMD の照明**（平行光）。セルフシャドウ・地面の影もこの向きで決まる。外せない。新しく **色** を持つ（MMD の照明の色と同じく、154/255 × 色 × 明るさ）。
- 「照明を追加」で足す照明: **点光源**（全方向）・**スポットライト**（回転の向きへの円すい）・**平行光**（どこでも同じ向き）。種類は作るときに決め、あとから変えない。値は位置・回転・色・明るさ・届く距離（点光源・スポットライト。0.1〜1000）・広がり（スポットの全体の角度。1〜179 度）・縁のぼかし（0〜1）。
- 足すと、最初のモデルの真ん中あたりを照らす場所に置く（点光源は手前上、スポットライトは手前上からモデルへ向ける、平行光は後ろ上から＝縁を明るくする光）。名前は「点光源」「点光源 2」…。
- 足す・外す（シーンのメニュー「選んだ照明を外す」、Delete）は**元に戻せる**。値の変更もプロパティ欄から元に戻せる。新しいプロジェクトでは足した照明を外す。

### 色の計算

- 足した照明の強さ = 色 × 明るさ × 154/255（明るさ 1 で MMD の照明と同じ強さ）。点光源・スポットライトは、照明からの距離で (1 − 距離 ÷ 届く距離)² と弱め、届く距離で 0 にする。スポットライトは円すいの内側（ぼかし始め）から外側へなめらかに弱める。
- **トゥーンの材質**: 光の当たる側を「材質の色（拡散色 × テクスチャ）× 照明の強さ」で明るくする。トゥーンのある材質は境目をくっきりさせ（セル調）、無い材質はなめらかにする。
- **PBR の材質**（29 章）: メインの照明と同じ GGX の照り返しと拡散で応える。
- 影は落とさない（セルフシャドウ・地面の影は MMD の照明だけ）。描画エンジンが 1 枚で使う足した照明は 8 つまで。
- 光を足す仕組みなので、MMD の照明が明るいまま（モデルの色がもう最大に近い）だと、足した照明の色は白く飛びやすい。色の光を目立たせたいときは、MMD の照明の明るさを下げる（実物のモデルで、MMD の照明 0.35 にすると、赤いスポットライトと青い点光源で体の両側が色づくことを確かめた）。

### 画面

- シーンのメニュー「照明を追加 → 点光源 / スポットライト / 平行光」「選んだ照明を外す」。足した照明は選んだ状態になる。
- プロパティ欄の照明: 種類、色（#RRGGBB）、明るさ、届く距離、広がり、縁のぼかし（種類に合う欄だけを出す）。
- プレビューに、足した照明の目印を線で重ねる（書き出しには映らない）: 点光源は小さな球、スポットライトは小さな球と円すい（長さは届く距離か 6 の短いほう）、平行光は矢印。照明の色で描き、選んでいる照明は黄色。隠した照明は描かない。

### プロジェクト

- 足した照明はプロジェクトの `lights`（名前・種類・表示・ロック・位置・回転・色・明るさ・届く距離・広がり・ぼかし）に保存する。無ければ書かない。種類の分からない照明は読み込みレポートで知らせて飛ばす。MMD の照明の色は `nodes.light.color`（白なら書かない。無い前の版は白）。

### 描画エンジン（API 0.14）

- `TtLight`（種類・位置・向き・届く距離・色・広がり・ぼかし。64 バイト）と、描画の条件の最後に `lights`・`light_count` を足した。最大 `TT_MAX_LIGHTS`（8）。数でない値を含む照明は使わない。
- モデルのシェーダーに、足した照明の定数（b2）を足した。

### 確かめたこと・まだのこと

- テスト（描画エンジン）: 照明なし・環境色 0 の白い面が、赤い点光源で近い所だけ赤くなり、届く距離の外は暗いこと。平行光は距離に関係なく届くこと。スポットライトは円すいの中だけ明るいこと。数でない値の照明だけを飛ばすこと。一覧が NULL なのに数があれば誤りにすること。PBR の材質も点光源の色で明るくなること。
- テスト（C#）: 値を範囲に収め、元に戻すと色も戻ること。足す・外す・元に戻す・やり直し（並び順も戻る）、MMD の照明は外せないこと、名前の番号、スポットライトが目標を向くこと、新しいプロジェクトで外すこと。描くのは見えていて明るさのある照明だけで、強さが 色 × 明るさ × 154/255 になること。保存と読み込み（開く前の照明は外す・種類の分からない照明を知らせる・前の版は足した照明なしで MMD の照明は白）。
- 画面（実物のモデル・全身のカメラ視点と自由視点）: シーンのメニューからスポットライトと点光源を足し、シーン一覧とタイムラインに並ぶこと、プロパティ欄の色の欄で色を変えられること、プレビューに目印が出ること、題名に「＊」が付くこと、元に戻すで色の変更と照明の追加が戻ること、書き出しにもかかること。照明を保存したプロジェクトを開くと、照明が名前・色・位置のまま戻ること。
- 足した照明の影、照明のキーフレーム（VMD の照明のキーも）、プレビューで照明の目印をクリックして選ぶことはまだ。

## 31. 床の映り込み（確定・Phase 4 の 10 段階目）

指示書 6.1 の「リアル／シネマティック: … 反射 …」と、Phase 4 の「反射」の最初の段階にあたる。MMD でよく使われる床の鏡面（高さ 0 の床にモデルが映る）を作った。

### 描き方

- 場面を描くとき、確認用の立方体の後・地面の影の前に、各モデルを高さ 0 の床で上下に映した姿（ワールド行列 × (1, −1, 1) の拡大）を描く。上下に映すと面の表裏が入れ替わるので、裏面を描かない材質は「表を描かない」設定にして描く。両面の材質はそのまま。
- **照明・カメラの位置・セルフシャドウ・足した照明も床で上下に映す**。映した点を、映した照明とカメラで照らせば、もとの点と同じ見え方になる（鏡に映ったのと同じ）。セルフシャドウは、照明から見た奥行きの画像の座標に「上下に映す」を掛けて、もとの点の影を引く。
- 映した点は床より下にあり、床からの深さで薄くする: 不透明度 × 濃さ × (1 − 深さ ÷ 消えるまでの距離)。床より上へ出た所（もとの物の、床より下の部分）は描かない。
- 地面の影とモデルは、その上に重なる（奥行きを比べる）。輪郭線は映さない。カメラが床より下（床の裏から見る）なら描かない。
- 透明な背景で書き出すと、映り込みは半透明のまま残る。

### 設定（プロジェクトに保存）

- `FloorReflection`: ON / OFF・濃さ（0〜1、初期値 0.35）・消えるまでの距離（0.5〜100、初期値 10。人の大きさのモデルの背丈は 20 ほど）。描き方の `rendering.reflection` に保存する（使っていなければ書かない）。変えるとプロジェクトは変更ありになるが、元に戻す・やり直しの対象ではない。
- 画面: レンダリングのメニュー「床の映り込み...」。変えるとすぐにプレビューへ反映し、書き出しにもかかる。

### 描画エンジン（API 0.15）

- `TT_FRAME_FLOOR_REFLECTION` と、描画の条件の最後に `reflection_strength`・`reflection_fade` を足した。物ごとの定数に「映り込みを描いているか・濃さ・距離」を足した。

### 確かめたこと・まだのこと

- テスト（描画エンジン）: 高さ 0.5〜1.5 の赤い四角形を斜め上から見ると、映り込みなしなら床の下は背景、ありなら床の下（高さ −0.8 の所）に赤く映り、もとの四角形は変わらないこと。消えるまでの距離より深い所・濃さ 0 では映らないこと。床の下から見ると、映り込みありとなしの絵が同じになること。
- テスト（C#）: 値を範囲に収めること、変わったときだけ知らせること、保存と読み込み（使っていなければ書かない）、新しいプロジェクトで OFF に戻すこと。
- 画面（実物のモデル・全身のカメラ視点と自由視点）: ON にすると足の下に脚が映り、深くなるほど消えること、題名に「＊」が付くこと、「初期値に戻す」で OFF になること、白い背景と透明な背景の書き出しにもかかること。
- 床のぼかし（磨りガラスのような映り込み）、床の高さ・傾きの設定、モデル以外（アクセサリ・ステージ）の映り込み、PBR の材質への周りの映り込み（画面の中の反射・環境の画像）はまだ。

## 32. 被写界深度（確定・Phase 4 の 11 段階目）

指示書 6.1 の「リアル／シネマティック: … 被写界深度 …」と、27 章で残した被写界深度にあたる。カメラのピントの前後をぼかす効果を、映像効果の 1 つとして足した。

### かけ方

- 点ごとの「ぼけの大きさ」（ぼけの円の半径、画素）を、カメラから見る向きの距離で決める: ピントの距離から、ピントの合う幅の半分より離れた分に比例して大きくし、さらに「最大になるまでの距離」だけ離れると最大になる。何も描かれていない所（背景）は最大。
- 最大になるまでの距離は、ピントの距離の半分（1 より小さくはしない）。近くにピントを合わせるほど前後が急にぼけ、本物のカメラに近い見え方になる。値を 1 つ減らして、設定を分かりやすくした。
- ぼかし方: ぼけの円の中を、黄金角の渦巻きで 40 点読んで平均する。読む点は、**その点自身のぼけが真ん中まで届くときだけ使う**。ピントの合った物が、後ろのぼけた背景ににじみ出さないように（ピントの合った顔の縁が、くっきりのまま残る）。
- ぼけの大きさは高さ 1080 の画像での画素で持ち、プレビューと書き出しでは画像の高さに比例させる（大きさが違っても同じ見え方）。
- かける順番: 場面（透明な背景）をぼかしてから、ブルーム・色調補正・線画などの仕上げをかける。格子・選択の枠・ボーン・ギズモなどの重ね描きはぼかさない（27 章と同じく、効果の後に重ねる）。奥行きは、線画（28 章）と同じ「見る向きの距離」の画像を使う（線画と一緒に使っても、作るのは 1 度）。

### どこにかけるか

- 被写界深度は**シーンのカメラ**の効果なので、カメラ視点の区画と書き出しにだけかける。自由視点・固定の視点は、ピントの距離に意味が無いのでぼかさない（作業の邪魔にもなる）。
- 初期値は「カメラの注視点にピントを合わせる」。カメラの注視点までの距離（カメラのモーションの「距離」）をピントの距離にするので、カメラのモーションで寄ったり引いたりしても、ピントがついて行く。OFF にすると、決まったピントの距離（カメラから）を使う。

### 設定（プロジェクトに保存）

- 映像効果（27 章、`rendering.effects`）に足した: ON / OFF（初期値 OFF）・注視点にピント（初期値 ON）・ピントの距離（0.5〜1000、初期値 45。MMD の初期のカメラの距離と同じ）・ピントの合う幅（0〜200、初期値 4）・ぼけの大きさ（0〜32 画素、初期値 6）。前の版のファイルは OFF のまま読める。
- 画面: レンダリングのメニュー「映像効果...」の下に「被写界深度」の欄を足した。注視点に合わせる間は、ピントの距離のつまみを使えなくする。欄が増えて縦に長くなったので、画面の中をスクロールできるようにした。プロパティのカメラの説明にも、被写界深度はここで設定すると書いた。

### 描画エンジン（API 0.16）

- `TT_POST_DOF` と、描画の条件の最後に `dof_focus_distance`・`dof_focus_range`・`dof_max_blur`・`dof_transition` を足した。範囲の外の値は収め、ぼけの最大が 0.5 画素より小さければ何もしない。
- ビューは、被写界深度を使うときだけ、ぼかした場面の画像を作る（大きさが変わったら作り直す）。シェーダーは `DofPS`。

### 確かめたこと・まだのこと

- テスト（描画エンジン）: 手前（距離 3）の小さな赤い四角形と、奥（距離 8）の大きな緑の四角形で、手前にピントを合わせると奥の縁だけがぼけ、奥に合わせると手前の縁だけがぼけること。ぼけの大きさ 0・被写界深度なしでは縁がくっきりのままなこと。
- テスト（C#）: 初期値では注視点にピントを合わせ、合わせないときは決まった距離を使うこと、ぼけが最大になるまでの距離、値を範囲に収めること、保存と読み込み。
- 画面（実物のモデル・顔のカメラ視点と全身の自由視点）: 注視点にピントでは顔がくっきり、近く（距離 3）にピントでは顔がぼけること。自由視点・選択の枠・座標軸はぼけないこと、題名に「＊」が付くこと、白い背景の書き出しにもかかること。
- 線画（28 章）は、ぼかした場面の上に、ぼかす前の奥行きで引くので、ぼけた物の線はくっきりのまま。
- 手前の物のぼけが、ピントの合った物の上にかぶさる見え方（本物のカメラの前ぼけ）は弱い。ぼけの形（六角形など）、ピントの距離のキーフレーム、再生中の重さの測定はまだ。

## 33. 環境光の遮り（AO）（確定・Phase 4 の 12 段階目）

指示書 6.1 の「リアル／シネマティック: … AO …」にあたる。物の隙間や、物どうしが接する所（わきの下・脚の内側・あごの下・髪の下など）を暗くして、形の奥行きを見せる。画面の奥行きから求める方法（SSAO）にした。

### 求め方

- 奥行きの画像（線画・被写界深度と同じ「見る向きの距離」。28 章）から、点ごとの位置と面の向きを作る。面の向きは、左右・上下の隣のうち奥行きの差の小さいほうとの差から作る（物の縁で、奥の物の側を使わないように）。
- 広がり（ワールドの長さ）の円を画面に写し、その中の 16 点を見る。見た点が**面の表の側にあるほど、近いほど**光を遮ると数える（面との角度の cos から 0.1 を引いた値 × (1 − 距離² ÷ 広がり²)）。平らな面や、外へふくらんだ面の上の点は遮らない。
- 光の届く割合 = 1 − 強さ × 3 × 平均。3 倍は、直角に接する所で、強さ 1 のときに明るさが半分ほどになるようにした値（半球のうち半分が遮られるのと同じ）。
- 点ごとに見る向きを 4 x 4 の模様で回し、横と縦に 9 点ずつ（真ん中ほど重く）ならして模様を消す。ならすのは奥行きの近い点どうしだけ（手前の物と奥の物の値が混ざって、縁がにじまないように）。初めは 4 x 4 の平均だけにしたが、顔の大写しで格子の跡が残ったので、横と縦の 2 段にした。
- 画面での広がりは、画像の高さの 15% までにする。それより大きくなるほど近くから見るときは、広がりも同じ割合で縮める（見る点がまばらになって、まだらにならないように）。初めは上限を 8% にしたが、顔の大写しで広がりの値を変えても結果が同じになったので、15% に上げた。
- かける場所: 場面（背景は透明）の色に掛ける。透明度は変えないので、透明な背景の書き出しでも物だけが暗くなる。被写界深度・ブルーム・仕上げより先にかける（暗くなった所もぼける）。格子・選択の枠などの重ね描きにはかからない。
- 被写界深度と違い、すべての視点にかける（形の見え方の効果なので）。

### 設定（プロジェクトに保存）

- 映像効果（27 章、`rendering.effects`）に足した: ON / OFF（初期値 OFF）・強さ（0〜1、初期値 0.6）・広がり（0.1〜10、初期値 1。人の大きさのモデルの背丈は 20 ほど）。前の版のファイルは OFF のまま読める。
- 画面: レンダリングのメニュー「映像効果...」の、周辺減光と被写界深度の間に「環境光の遮り」の欄を足した。

### 描画エンジン（API 0.17）

- `TT_POST_AO` と、描画の条件の最後に `ao_strength`・`ao_radius` を足した。範囲の外の値は収め、強さ 0 なら何もしない。
- ビューは、使うときだけ、光の届く割合の画像 2 枚（8 ビットの 1 色）と、遮りをかけた場面の画像を作る。シェーダーは `AoPS`（求める）・`AoBlurPS`（横にならす）・`AoApplyPS`（縦にならして掛ける）。
- 平行投影でも求められる（画面の位置を、投影の値から見る向きの座標に戻す）。

### 確かめたこと・まだのこと

- テスト（描画エンジン）: 奥の壁に 60 度傾けた板が接する所の近くで、壁と板の両方が暗くなること。接する所から離れた平らな所と背景は変わらないこと。強さ 0 では変わらず、広がりを小さくすると、接する所から少し離れた点は明るくなること。
- 初めのテストは 45 度の板にしたが、135 度に開いた折れ目は、物理的にもあまり暗くならない（計算で 0.85 ほど）ので、60 度にした。
- テスト（C#）: 初期値（OFF）、値を範囲に収めること（数でない値は初期値）、保存と読み込み。
- 画面（実物のモデル・全身と顔のカメラ視点と自由視点）: 脚の内側・わきの下・あごの下・髪の下・目の周りが暗くなり、平らな所は変わらないこと。広がりを変えると暗くなる範囲が変わること。自由視点にもかかり、白い背景の書き出しにもかかること。題名に「＊」が付くこと。
- 床は格子（重ね描き）で、奥行きの画像に無いので、足元が床に接する所は暗くならない（地面の影がその代わりになる）。ステージのモデルを読み込めば、その床とは接する所が暗くなる。
- 目のように、奥まった所に描く材質も暗くなる（物理的には正しいが、アニメ調では目が暗く見えることがある）。材質ごとに外すこと、半分の大きさで求めて速くすること、再生中の重さの測定はまだ。

## 34. 霧（確定・Phase 4 の 13 段階目）

指示書 6.1 の「リアル／シネマティック: … フォグ …」にあたる。遠くの物ほど霧の色に溶けこませて、空気の奥行きを見せる。

### かけ方

- カメラからのまっすぐの距離（見る向きの距離ではないので、カメラを回しても霧の濃さが変わらない）のうち、霧の始まりより先の分で決める。霧の量 = 1 − exp(−濃さ × 霧の中を通る長さ)。
- 設定では濃さの代わりに「見通せる距離」を持つ（霧の始まりから、この距離だけ進むと 95% が霧の色になる。濃さ = 3 ÷ 見通せる距離）。数で考えやすいように。
- 地面の近くほど濃くする（地面の霧）: 濃さを高さで薄くする（高さ 0 で濃さそのまま、霧の高さだけ上がるごとに 1/e。地面より下は濃さそのまま）。光の通り道に沿って足し合わせる（式で解ける）ので、見下ろすと濃く、見上げると薄い。床の無い所を見通すと、地平線のあたりで霧の濃さが急に変わる（地面より下の向きは、どこまでも霧の中を通るため）。
- 背景（何も描かれていない所）は、どこまでも遠い所として扱う。背景が不透明なら背景も霧の色にし、透明な背景の書き出しは透明のまま（物の霧だけをかける）。
- 地面の影は奥行きを書かずに床に描くので、床（高さ 0）までの距離で霧をかける。床の映り込みは奥行きを書くので、映った姿の距離で霧がかかる。
- かける順番: 環境光の遮りの後、被写界深度・ブルーム・色調補正の前（遠くの霧もぼけ、霧の色にも色調補正がかかる）。格子・選択の枠などの重ね描きと、線画（28 章）にはかからない。
- 平行投影の固定の視点（正面・側面など）にはかけない（カメラの位置に決まりが無く、距離に意味が無いため）。カメラ視点と自由視点にかける。

### 設定（プロジェクトに保存）

- `SceneFog`: ON / OFF・色（#RRGGBB、初期値 #B4BECD の白っぽい青）・始まる距離（0〜1000、初期値 20）・見通せる距離（1〜5000、初期値 200）・地面の近くほど濃くする（初期値 OFF）・霧の高さ（0.5〜200、初期値 8）。描き方の `rendering.fog` に保存する（使っていなければ書かない）。計算で出す濃さなどは書かない。
- 画面: レンダリングのメニュー「霧...」。変えるとすぐにプレビューへ反映し、書き出しにもかかる。元に戻す・やり直しの対象ではない（ほかの描き方の設定と同じ）。
- あわせて、レンダリングのメニュー「映像効果...」の説明に、環境光の遮りと被写界深度を書き足した。

### 描画エンジン（API 0.18）

- `TT_POST_FOG` と、描画の条件の最後に `fog_color`・`fog_start`・`fog_density`・`fog_height` を足した。範囲の外の値は収め、濃さ 0 なら何もしない。
- 高さは、ビュー行列の逆から「見る向きの座標の位置 → ワールドの高さ」の値を作って渡す。画面の位置を見る向きの座標に戻す関数は、環境光の遮りと共通にした（`ViewPositionAt`）。シェーダーは `FogPS`。

### 確かめたこと・まだのこと

- テスト（描画エンジン）: 近く（距離 3）と遠く（距離 10）の赤い板で、霧の量が式どおり（0.26 と 0.63）になること。不透明な背景は霧の色になり、透明な背景は透明のままで、物の霧は背景によらないこと。霧の始まりより近い物・濃さ 0 では変わらないこと。地面の霧では下ほど濃く、地面より下は高さによらない霧と同じこと。平行投影ではかからないこと。
- テスト（C#）: 値を範囲に収めること（読めない色・数でない値は初期値）、見通せる距離で 95% になる濃さ、変わったときだけ知らせること、保存と読み込み（使っていなければ書かない・計算で出す値は書かない）、新しいプロジェクトで OFF に戻すこと。
- 画面（実物のモデル・全身のカメラ視点と自由視点）: 霧をかけると背景が霧の色になり、見通せる距離を短くするとモデルも霧に沈むこと。地面の霧では足元ほど濃いこと。色を変えられること。選択の枠・ギズモにはかからないこと。白い背景の書き出しは背景も霧の色になり、透明な背景の書き出しは背景が透明のままなこと。題名に「＊」が付き、「初期値に戻す」で OFF になること。
- 霧のキーフレーム、線画にも霧をかけること、霧の中の光の筋（照明が霧を照らす見え方）はまだ。

## 35. 柔らかな影（確定・Phase 4 の 14 段階目）

指示書 6.1 の「リアル／シネマティック: … 柔らかな影 …」にあたる。照明を大きさのある光源として扱い、影を落とす物と受ける面が離れているほど影の境目を広くぼかす（足元のように接している所はくっきり）。あわせて、持ち越し事項にあった地面の影の濃さを変えられるようにした。

### セルフシャドウのぼかし方（PCSS）

- やわらかさ 0 なら今までどおり（周りの 9 か所を比べるだけ。MMD と同じくっきりした影）。
- 0 より大きいとき:
  1. 受ける点の周り（照明の側の端までの距離 × 光源の見かけの半径の tan の円）で、照明から見た奥行きの画像を 16 か所読み、受ける点より照明に近い物（影を落とす物）の奥行きを平均する。見つからなければ光が当たる。
  2. 物と受ける点の距離 × tan を境目の幅（円の半径）にして、その円の中の 24 か所を比べて平均する。幅が奥行きの画像の 1.5 画素より狭ければ、今までの 9 か所にする。
- 幅の上限はワールドの長さで 3（奥行きの画像の座標で決めると、モデル 1 体のように範囲が狭いときに、ほとんどぼけなくなるため）。ワールドの長さで決めるので、プレビューと書き出し（奥行きの画像の大きさが違う）で同じ見え方になる。
- 読む点の並びは画素ごとに回す（境目が段々にならないように）。そのかわり、境目にわずかなざらつきが出る（書き出しの「なめらかにする」で目立たなくなる）。

### 地面の影もぼかす

- 試したモデルでは、セルフシャドウはあごの下などにしか落ちず、ぼかしてもほとんど違いが見えなかった。いちばん目立つ影は床の影だが、床へ押しつぶして描く今の地面の影は、境目をぼかせない。
- そこで、やわらかさが 0 より大きいときは、地面の影も照明から見た奥行きで描くようにした:
  - 「地面影」の材質だけで、照明から見た奥行きの画像をもう 1 枚作る（範囲は、影を落とす物と、その角から照明の向きに進んで床に届いた点が全部入るように）。
  - 床（高さ 0.01）に 1 枚の四角形を描き、セルフシャドウと同じ読み方で影の濃さを決めて、地面の影の色を重ねる。四角形は、影の届く範囲をぼけの分だけ広げた大きさ。
  - 1 枚の四角形なので、重なった所が二重に暗くなることはない（押しつぶす描き方でステンシルを使っていたのと同じ結果）。
- やわらかさ 0 なら、今までどおり押しつぶして描く（MMD と同じ見え方）。

### 設定（プロジェクトに保存）

- `ShadowStyle`: やわらかさ（0〜1、初期値 0）・地面の影の濃さ（0〜1、初期値 0.5。今までの値）。やわらかさ 1 は光源の見かけの半径の tan 0.1（約 5.7 度）。描き方の `rendering.shadowStyle` に保存する（初期のままなら書かない。計算で出す値は書かない）。
- 画面: レンダリングのメニュー「影の設定...」（影のやわらかさ・地面の影の濃さ）。セルフシャドウと地面の影の ON / OFF は、今までどおりメニューで切り替える。元に戻す・やり直しの対象ではない。

### 描画エンジン（API 0.19）

- 描画の条件の最後に `shadow_softness`（光源の見かけの半径の tan。0〜0.5）を足した。物ごとの定数に、柔らかな影の値（奥行き 1 と座標 1 がワールドでどれだけの長さか・tan）を足した。
- 奥行きの画像の読み方を `Shadow.hlsli` にまとめ、モデルと柔らかな地面の影（`GroundSoftShadowVS`・`GroundSoftShadowPS`）で共通にした。照明から見た奥行きを描く処理も、セルフシャドウと地面の影で共通にした。

### 確かめたこと・まだのこと

- テスト（描画エンジン）: 浮かせた板の影の縁で、やわらかさ 0 ならくっきり、0.1 なら広くぼけ、板を床に近づけると縁がくっきりに近づくこと（セルフシャドウと地面の影の両方）。影の真ん中は影のまま（地面の影は同じ濃さ）で、離れた所は光が当たったままなこと。
- テスト（C#）: 値を範囲に収めること、変わったときだけ知らせること、保存と読み込み（初期のままなら書かない・計算で出す値は書かない）、新しいプロジェクトで初期値に戻すこと。
- 画面（実物のモデル・全身と横から照らした顔）: 床の影は足元が濃くくっきりで、頭や腕の影ほどぼけること。顔では髪の影の境目がやわらかくなること。地面の影の濃さを変えられること。書き出しにもかかること。題名に「＊」が付くこと。
- 足した照明（30 章）の影、地面の影の色の設定はまだ。床の無い所（ステージの外など）にも地面の影を描くのは、今までと同じ。

## 36. 環境の画像（HDRI）（確定・Phase 4 の 15 段階目）

指示書 6.1 の「リアル／シネマティック: … HDRI・環境光 …」と、29 章で残した「環境の画像での映り込み」にあたる。全方向の景色の HDR 画像で、拡張材質（PBR）を照らし、景色を映し込ませる。背景にも表示できる。

### 読み込み（Radiance HDR）

- 対応する形式は Radiance HDR（.hdr。RGBE）。HDRI でいちばんよく使われる形式で、自前で読む（`HdrDecoder`。Formats）。
  - 対応すること: 行ごとの RLE 圧縮（新しい形式・古い形式）と圧縮なし、上下の向き（-Y・+Y）、`EXPOSURE`（書いたときに掛けた明るさを割り戻す）
  - 断ること: XYZE の色と、縦横を入れ替えた向き
- 画像は、全方向の景色を横 360 度・縦 180 度に広げたもの（正距円筒図法）。真ん中が +Z（MMD の初期のカメラが見る向き）、右へ 4 分の 1 進むと +X、上の端が真上。
- 横が 4096 画素を超える画像は、半分ずつ縮めて使う（2 x 2 の平均）。8K の HDRI でも GPU の記憶を使いすぎないように。環境光と映り込みには十分な細かさ。
- ファイルを変えたときだけ読み直す（明るさ・回転を変えても読み直さない。`EnvironmentImage`）。読めないときは、理由を設定の画面に出し、ログに残す。

### 描き方

- GPU には 16 ビットの浮動小数点で載せ、縮小版（ミップマップ）を作る。
- **拡散（つや消しの面）**: 作るときに画像全体から球面調和関数（2 次まで、9 個の係数）を求める。面の向きごとに、全方向から来る光を足し合わせた明るさになる。前は照明の色から作った空と地面の 2 色だった。
- **映り込み**: 反射の向きの景色を、粗いほど縮小した画像から読む（粗さ × 縮小版の数）。GGX での正確なぼかしではなく、縮小版での近似。
- トゥーンの材質には使わない（MMD と同じ見え方を保つ）。環境の画像を使わないときは、今までどおり空と地面の 2 色。
- 床の映り込み（31 章）を描くときは、景色も上下に映して読む。
- **背景**: 「背景に表示」なら、画面の点ごとのカメラからの向きの景色を、ほかの物より先に描く。描かないのは次のとき。
  - 平行投影の固定の視点（どの点も同じ向きになり、1 色になるため）
  - 透明な背景の書き出し（透明のままにする）
- 背景にも、映像効果（霧・被写界深度・色調補正など）は場面の一部としてかかる。8 ビットの画像に描くので、1 より明るい所（太陽など）は白で止まる（トーンマップはまだ）。
- 回転: 景色を Y 軸のまわりに回す（真上から見て時計回り）。拡散・映り込み・背景のすべてが同じ向きで回る。

### 設定（プロジェクトに保存）

- `SceneEnvironment` に次を持つ。描き方の `rendering.environment` に保存する（使っていなければ書かない）。
  - ON / OFF
  - ファイル
  - 明るさ（0〜4、初期値 1）
  - 回転（-180〜180 度。範囲の外は回し込む）
  - 背景に表示（初期値 ON）
- 画像の場所は、モデル・音声と同じく「プロジェクトのフォルダーから見た場所」と「保存したときの絶対パス」の両方で書く。開くときはその順に探し、フォルダーごと動かしても見つかる。
- 画面: レンダリングのメニュー「環境の画像...」。
  - 「参照...」でファイルを選ぶと、使う状態にしてすぐ読み込む。読めたかどうかと大きさを出す。
  - ファイルの欄は、長いパスでもファイル名が見えるよう終わりの側を見せる。
  - 元に戻す・やり直しの対象ではない。
- 初めは「使う」のチェックを入れるまでファイルの欄も使えなかった。選ぶ前にチェックが要るのは分かりにくいので、ファイルはいつでも選べるようにした。

### 描画エンジン（API 0.20）

- 環境の画像の作成と破棄（`tt_environment_create`・`tt_environment_destroy`）を足した。
  - 画素は直線の RGB の float。数でない値・負の値は 0 にする。
  - GPU が失われても、CPU 側に持っている画素から作り直す（テクスチャと同じ）。
- 描画の条件の最後に `environment`・`environment_intensity`・`environment_rotation` を足した。描画の旗に `TT_FRAME_ENVIRONMENT_BACKGROUND` を足した。
- シェーダー: 景色の読み方を `Environment.hlsli` にまとめ、モデル（PBR）と背景（`SkyPS`）で共通にした。足す照明の定数に、環境の画像の値と球面調和関数の係数を足した。

### 確かめたこと・まだのこと

- テスト（読み込み）: 次のことを確かめた。
  - 圧縮なし・RLE 圧縮の画素がそのまま読めること
  - 下から書いた画像の上下を入れ替え、EXPOSURE を割り戻すこと
  - HDR でないファイル・縦横を入れ替えた向き・XYZE・途中で切れたファイルを断ること
  - 縮めると 2 x 2 の平均になること
- テスト（描画エンジン）: 次のことを確かめた。
  - 照明なしの PBR の板が、一様な赤の景色で赤く照らされ、明るさ 0.5 で半分になること
  - トゥーンの材質は変わらないこと
  - 背景に見る向きの景色が出て、180 度回すと反対側の色になること
  - 平行投影には描かないこと
  - 大きさ 0・画素なしを断ること
- テスト（C#）: 次のことを確かめた。
  - 値を範囲に収めること
  - プロジェクトのフォルダーから見た場所で書き、フォルダーごと動かした先で見つかること
  - 使っていなければ書かないこと
  - 新しいプロジェクトで OFF に戻すこと
- 画面: 実物のモデルで、髪を金属・水着を PBR にした写しと、合成した HDR の景色で確かめた。
  - 「参照...」で選ぶとすぐ読み込まれること
  - 背景に景色が出て、金属の髪に周りの建物が映り、トゥーンの肌は変わらないこと
  - 回転で前の景色が変わること
  - 背景を消せること、明るさが変わること
  - 色の背景の書き出しには景色が入り、透明な背景の書き出しは透明のままなこと
  - 保存すると相対の場所で書かれ、開き直すと自動で読み込まれること
- まだのこと:
  - 映り込みを GGX で前もってぼかすこと（今は縮小版）
  - トーンマップ（明るい空や太陽が白で止まる）
  - 背景のぼかし
  - EXR などほかの形式
  - トゥーンの材質に環境光を足す設定
  - 環境の画像から照明の向きを決めること（太陽の向き）

## 37. モーションブラー（確定・Phase 4 の 16 段階目）

指示書 6.1 の「リアル／シネマティック: … モーションブラー …」にあたる。動いている物とカメラの動きをぶらす。これで 6.1 の「リアル／シネマティック」に挙がった項目には、どれも最初の版ができた（PBR 材質・HDRI と環境光・柔らかな影・反射・AO・被写界深度・ブルーム・フォグ・モーションブラー・色調補正）。

### 作り方（書き出しにだけかける）

- 1 フレームの間を何回かに分けて描き、平均する（時間をずらして重ねる方法）。画面の中の速さから作る方法（速度の画像でぼかす）よりも重いが、物の重なり・回転・物理の揺れも正しくぶれる。書き出しにだけかけるので重さは許せる。プレビューにはかけない。
- 分けて描く時刻は、ぶれの長さの真ん中がそのフレームになるよう前後に等しく広げ、それぞれの区間の真ん中を使う。0 フレームより前は 0 にする。
- 時刻ごとに次のものを合わせて描き、画素を足してから平均する。透明な背景の画素は、透明度をかけ合わせた値なので、そのまま平均してよい。
  - ボーン・モーフ・カメラの値（キーの補間をフレームの途中の時刻で読む。キーの計算はもともと小数のフレームを受け付けていた）
  - 物理（焼き込んだ前後のフレームの剛体の置き方を補間する。位置は直線、向きは球面）
- **隣り合うフレームのキーの間は補間しない**: MMD でカメラの場面を切り替えるときは、隣り合うフレーム（間隔 1）にキーを打つ。そのまま途中を補間すると、2 つの場面が重なってしまう。分けた時刻とそのフレームの間に、間隔 1 以下のキーの区間があれば、その項目はそのフレームの値にする。ボーン・モーフも同じ（瞬間的に姿勢を変える打ち方のため）。
- 描き終えたら、今のフレームの値に戻す（書き出しの後に、画面の姿勢が途中の時刻のまま残らないように）。

### 設定

- 書き出しの画面に「動き」の行を足した。
  - モーションブラー（ON / OFF）
  - ぶれの長さ（フレームの 1/4・1/2・1。1/2 は映画でよく使う 180 度のシャッター）
  - 分ける数（4・8・16・32 回）
- 書き出しの前回の値として、利用者の設定に覚える（プロジェクトには入れない。ほかの書き出しの設定と同じ）。初期値は OFF・1/2・8 回。
- 初めは 4・8・16 回だけにしたが、とても速い動き（1/3 秒で 60 度回るカメラ）では 8 回で縞（重ねた形が分かれて見える）が出たので、32 回も選べるようにした。32 回ではほぼなめらかになった。

### 確かめたこと・まだのこと

- テスト（C#）: 次のことを確かめた。
  - 分けた時刻がフレームの前後に等しく並び、0 より前は 0 になること
  - ぶれの長さ 0 では使わないこと、分ける数・長さの範囲の確かめ
  - カメラが場面を切り替える区間（隣り合うキー）では途中を補間せず、ゆっくり動く区間は補間すること
  - 途中の時刻の値を当てはめても「手で変えた」ことにならず、今のフレームの値に戻せること
  - 物理の剛体の置き方の補間（位置は半分、向きは 45 度）
- 画面（実物のモデルで写しを作った。カメラが 0〜10 フレームで 60 度回り、11 フレーム目で寄りの場面へ切り替え、センターが横へ動く）:
  - 5 フレーム目はぶれなしでくっきり、ぶれありで横にぶれること
  - 切り替えの直後の 11 フレーム目は、ぶれありでも前の場面と混ざらないこと（ぶれなしとの違いは、物理で揺れている髪の縁だけ）
  - 32 回で縞がほぼ消えること（1280 x 720・なめらかにする で 1 枚 1.4 秒）
- 動画の書き出しでの確認はまだ（静止画と同じ処理を通る）。
- 足した照明・環境の画像の回転などのキーフレームはまだ無いので、それらはぶれない。画面の中の速さで作る、軽いモーションブラー（プレビュー用）もまだ。

## 38. プレビューと書き出しの違い（確定・Phase 4 の 17 段階目。Phase 4 の完了の確かめ）

Phase 4 の完了判定「期待したフレーム範囲・解像度・背景透過で出力でき、プレビューと最終結果の違いが説明可能・検証可能であること」の後半にあたる。前半（フレームの範囲・大きさ・透明な背景で書き出せること）は 24・25 章でできている。

### カメラ視点の書き出しの枠

- 前は、カメラ視点の区画を区画の形のまま描いていた。カメラの画角は縦で決まるので、区画と書き出しの縦横の比が違うと、左右（または上下）に見える範囲が書き出しと違っていた。縦長の区画では、16:9 の書き出しの左右が見えなかった。
- 今は、カメラ視点の区画の中に、書き出しの大きさの縦横の比の枠を出す（枠の外を暗くし、枠の線を引く。見出しに「書き出し 幅 x 高さ の枠」と出す）。
- 枠の中は、書き出しとまったく同じ写り方にする（`ViewCamera.SceneCameraMatrices`）:
  - 区画が書き出しより横長: 縦の画角はそのままで、枠は左右の真ん中。
  - 区画が書き出しより縦長: 枠を横いっぱいにし、枠の高さがカメラの画角になるよう、区画の縦の画角を広げる。
  - クリックでの選択・ギズモも同じ行列を使うので、ずれない。
- 輪郭線の太さ・線画・紙の粒・被写界深度のぼけ・環境光の遮りの広がりなど、画像の高さで大きさを決めるものは、カメラ視点では枠の高さで決める（書き出しと同じ見え方にするため）。
- 枠の大きさは、書き出しの画面の幅と高さ。入れるとすぐに枠が変わり、書き出さずに閉じても覚える（次の起動でも同じ枠）。

### 見本

- 書き出しの画面に「見本を描く」を足した。今の設定（大きさ・なめらかにする・モーションブラー・背景）で、書き出すフレーム（連番・動画は最初のフレーム）を 1 枚描き、保存せずに見せる（`ImageExporter.RenderSample`。書き出しと同じ描き方を通る）。
- 見本の画面は、窓に合わせて見るか、実際の大きさ（1 画素を 1 画素で）で見るかを選べる。透明な所は市松模様で見せる。

### プレビューと書き出しの違い（一覧）

| 項目 | プレビュー | 書き出し |
|---|---|---|
| 写る範囲 | カメラ視点の区画は、書き出しの枠の中が書き出しと同じ。ほかの視点は自由 | シーンのカメラ・書き出しの大きさ |
| なめらかさ（MSAA） | 描画品質による（軽い 1・ふつう 4・きれい 8 点） | いつも 4 点。「なめらかにする」なら、さらに 2 倍の大きさで描いて縮める |
| セルフシャドウの細かさ | 描画品質による（1024・2048・4096） | いつも 4096 |
| 物理 | 止まっているときに姿勢を変えた直後は、その場の物理で揺れを見せる。それ以外は焼き込み | いつも焼き込み（0 フレーム目から順に計算した結果） |
| 背景 | 編集用の暗い色（環境の画像を背景に出すときはその景色） | 選んだ色か透明。環境の画像の背景は、色の背景のときだけ |
| 編集用の表示（格子・座標軸・ボーン・ギズモ・選択の枠・照明の目印・確認用の立方体） | 出る | 出ない |
| 被写界深度 | カメラ視点の区画だけ | かかる |
| 霧・環境の画像の背景 | 固定の視点（平行投影）にはかからない | かかる |
| モーションブラー | かからない | 選んだときだけかかる |
| 画像の高さで決まる大きさ（輪郭線・線画・ぼけなど） | カメラ視点は枠の高さで決める | 書き出しの高さで決める |
| 再生 | 間に合わなければ、とばして見せることがある | すべてのフレームを描く |

- この違いは、書き出しの画面の説明・見本・カメラ視点の枠で確かめられる。

### 確かめたこと・まだのこと

- テスト（C#）: 書き出しの画面の端に写る点が、区画の中の書き出しの枠の端に写ること（区画が縦長・横長の両方）、枠の位置と大きさ（縦長は横いっぱい・横長は縦いっぱい・比が無ければ区画そのもの）。
- 画面（実物のモデル・全身のカメラ視点）: 次のことを確かめた。
  - 1280 x 720 の枠（縦長の区画なので上下が暗い帯）の中の写り方が、書き出した絵と同じ範囲であること
  - 書き出しの大きさを 1080 x 1350 にするとすぐに枠が変わり、書き出した絵とも合うこと
  - 「見本を描く」で、白い背景の 1080 x 1350 の見本が出ること
  - 書き出さずに閉じても大きさを覚えること
- **Phase 4 の完了判定を満たした**と判断する。フレームの範囲・大きさ・透明な背景で書き出せ、プレビューとの違いを上の一覧で説明でき、枠と見本で確かめられる。
- 残っていること（持ち越し事項）: JPEG・EXR・透明な動画、トーンマップ、レンダーパスの書き出し（指示書 6.3 の「発展」「将来」）。

## 39. プラグインの土台（確定・Phase 5 の 1 段階目）

指示書 7 章（プラグイン SDK）と Phase 5 の「Plugin.Core と UI／アプリ別 SDK、管理画面、サンプルプラグイン」にあたる。プラグインを作る人向けの説明は [プラグインの作り方](プラグインの作り方.md) にまとめた。

### 分け方（3 つの契約の DLL）

| DLL | 中身 | 何に依存するか |
|---|---|---|
| `Plugin.Core` | 入口（`IPlugin`）・アプリの機能の入口（`IPluginContext`）・コマンド・設定・ログ・plugin.json の読み込みと互換性の確かめ・読み込みと管理（`PluginManager`） | .NET だけ（WPF にも 3D Theater にも依存しない） |
| `Plugin.UI.Wpf` | ドッキングパネル（`IPanelRegistry`）・メッセージ（`IPluginUi`）・配色の資源の名前（`ThemeKeys`） | WPF |
| `3DTheater.Plugin.SDK` | 3D Theater 専用の機能（今はシーンを読む・再生位置を動かす `ITheaterScene`）と、host と SDK の版 | .NET だけ |

- 指示書 7.1 のとおり、`Plugin.Core` は特定のアプリに依存しない。Drawing Canvas が同じ `Plugin.Core` と `Plugin.UI.Wpf` を使い、自分の SDK だけを足す形にできる。
- 画面の拡張（`Plugin.UI.Wpf`）は WPF に依存するので、`Plugin.Core` から分けた（指示書の「WPF 実装を分離したアダプター構成」）。
- アプリの機能は `context.GetService<T>()` で取り出す。そのアプリに無い機能なら null。`Plugin.Core` が画面やアプリ専用の型を知らなくてよいようにするため。
- 契約の DLL の版は SDK の版（この段階では 1.0。40 章で 1.1 にした）で表す。主の版が違うものは使えない。副の版は、形を壊さずに足したときに上げ、プラグインの求める副の版がアプリ以下なら使える。

### 読み込み（AssemblyLoadContext）

- プラグインのフォルダーには `plugin.json` を置く（id・名前・版・対象のアプリ（host）・SDK の版・DLL・入口の型・説明・作者・使う機能（requires））。
- プラグインごとに `AssemblyLoadContext` を 1 つ作り、プラグインの DLL と、プラグインだけが使う DLL（`*.deps.json` に従って同じフォルダーから探す）をそこに読む。
- **契約の 3 つの DLL は、アプリが読んだものを使う**（プラグインのフォルダーに同じ名前の DLL があっても読まない）。読み込みの場所が違うと、同じ名前の型でも別の型になり、`IPlugin` として扱えなくなるため（指示書 7.3「共通の SDK 契約アセンブリが重複ロードされないように」）。
- 読み込む前に、次のことを確かめる。合わなければ読み込まず、管理画面に理由を出す。
  - plugin.json が読めること（必要な項目・id に使える文字・DLL がフォルダーの中にあること）
  - 対象のアプリ（host）が 3DTheater であること
  - SDK の主の版が同じで、副の版がアプリ以下であること
  - requires の機能が、すべてこのアプリにあること
  - 同じ id のプラグインが先に見つかっていないこと
- 入口の型は `IPlugin` を実装し、引数なしで作れること（違えば「始められない」にして理由を出す）。
- `AssemblyLoadContext` は外せる形（collectible）にしない。無効にしたプラグインの DLL は、アプリを起動し直すまで読み込まれたまま。指示書 7.3 のとおり、更新・削除はアプリの起動し直しで反映する（確実に外すには、プラグインの持っている物がすべて手放される必要があり、保証できないため）。もう一度有効にすると、読み込み済みの DLL から作り直す。

### 置き場所と有効・無効

- 探す場所は 2 つ: アプリのフォルダーの `Plugins\`（アプリと一緒に配るもの。サンプルはここ）と、`%APPDATA%\3DTheater\Plugins\`（利用者が入れるもの）。それぞれの下の、plugin.json のあるフォルダーが 1 つのプラグイン。
- **初めて見つけたプラグインは無効**にしておく。プラグインはアプリと同じプロセスで動き、パソコンのファイルなどにも触れられるため、利用者が管理画面で確かめて有効にする（有効にするときに確かめの窓を出す）。
- 有効・無効とプラグインごとの設定は、利用者の設定（`settings.json` の `Plugins`）に入れる。プロジェクトには入れない（指示書 8 章「プラグイン状態はユーザー設定として分離」）。
- 無効にすると、`Shutdown` を呼び、登録したコマンド・パネル・シーンのイベントをアプリが外す（プラグインが外し忘れても残らない）。
- 同じプロセスの DLL は強い守りにならない（指示書 7.3）。requires は権限ではなく、互換性の確かめに使う。

### 異常時の扱い

- `Initialize`・`Shutdown`・コマンド・パネルの中身を作る処理・シーンのイベントの受け取りで例外が起きても、アプリは止めない。プラグインごとの「問題の記録」とアプリのログに残す。
  - 始めるときの例外: そのプラグインだけ「有効だが始められません」にし、途中で登録したものを外す。
  - コマンドの例外: メッセージで知らせる（プラグインは動いたまま）。
  - パネルの中身を作るときの例外: パネルに理由を出す。
- **始める途中でアプリが落ちたとき**: `Initialize` を呼ぶ前に「始めている途中」の印（`UserSettings\plugin-starting.txt` にプラグインの id）をファイルに書き、終わったら消す。次の起動で印が残っていれば、そのプラグインを無効にし、起動後に知らせる（同じプラグインで落ち続けないように）。
- **安全モード**: `--safe-mode` を付けるか、Shift を押しながら起動すると、有効なプラグインも始めない（題名に「（安全モード）」、管理画面に帯を出す）。プラグインのせいで起動できないときに、管理画面で無効にできるようにするため。安全モードの間に有効にしたものは、次の普通の起動から始める。

### コマンドとパネル

- コマンド: プラグインのメニューの、プラグインの名前の項目の下に並べる。`CanExecute` はメニューを開いたときに確かめる。ショートカットは Ctrl か Alt を含むものだけ受け付け（文字の入力とぶつかるため）、アプリが使ったキーは先にアプリが受け取る。ほかのプラグインのショートカットと重なるときは、後から登録したものにショートカットを付けない（問題の記録に残す）。
- パネル: アプリのドッキングに、アプリのパネルと同じ決まりで登録する（表示・タブ化・切り離し・レイアウトの保存と復元。指示書 7.2）。表示のメニュー「パネル」にも出る。レイアウトの保存の名前は `Plugin/プラグインの id/パネルの id`。
  - 起動時はレイアウトを読む前にプラグインを始めるので、前回の場所に戻る。
  - 動いているアプリで有効にしたときは、決めた側（右・左・下）に足して前に出す。
  - 中身はパネルを初めて出すときに 1 度だけ作り、レイアウトを組み直しても使い回す。

### 管理画面（プラグインのメニュー「プラグインの管理...」）

- 見つけたプラグインの一覧と、選んだものの状態・版・id・作者・説明・使う機能・場所・問題の記録。
- 有効にする／無効にする、プラグインのフォルダーを開く、プラグインを入れる場所（`%APPDATA%\3DTheater\Plugins`）を開く。
- 状態は「無効」「有効（動いています）」「有効（始めていません）」「有効だが始められません」「このアプリでは使えません」「plugin.json が読めません」「同じ id のプラグインがあります」。

### サンプルのプラグイン（`plugins/3DTheater.SamplePlugin`）

- 「サンプル: シーンの情報」。3 つの契約を一通り使う見本。
  - コマンド「今のフレームを知らせる」（Ctrl+Alt+I）: 今のフレーム・モデルの数・選択を知らせ、使った回数をプラグインの設定に覚える。
  - コマンド「先頭のフレームへ」: 0 フレーム目以外のときだけ使える。
  - パネル「シーンの情報（サンプル）」: 今のフレーム・選択・モデルの一覧を出し、シーンの知らせで出し直す。色はアプリの配色の資源に合わせる。
- アプリをビルドすると、出力の `Plugins\SceneInfo\` に写る（契約の DLL は写さない）。

### 確かめたこと・まだのこと

- テスト（C#、`Plugin.Core.Tests`）: 次のことを確かめた。テスト用のプラグインの DLL（`Plugin.TestPlugins`）を実際に読み込む。
  - plugin.json の読み込み（コメントと最後のカンマを許す）と、足りない・壊れた項目、フォルダーの外の DLL を断ること
  - 互換性（host・SDK の主と副の版・使う機能）
  - 契約の DLL をアプリと共有して読み、`IPlugin` として扱えること
  - 初めて見つけたものは無効のまま始めないこと
  - 始めるときの例外・入口の型が無い・`IPlugin` でない・引数が要る型を、そのプラグインだけの失敗にすること
  - 無効にする・また有効にする・アプリの終了で `Shutdown` を呼ぶこと、`Shutdown` の例外を記録すること
  - 安全モードで始めない（DLL も読まない）こと、始める途中の印が残っていれば無効にすること
  - 使えない・壊れた・id が重なるプラグインを始めないこと
- 画面（実物のモデルのプロジェクト）: 次のことを確かめた。
  - 管理画面でサンプルを有効にする（確かめの窓が出る）と、プラグインのメニューにコマンドが、右にパネルが出て、表示のメニュー「パネル」にも出ること
  - メニューとショートカット（Ctrl+Alt+I）でコマンドが動き、使った回数がパネルと設定に残ること
  - 「先頭のフレームへ」が 0 フレーム目では使えず、末尾では使えて、押すと 0 フレーム目に戻ること（パネルの表示もついて行く）
  - 起動し直すと、有効のままでパネルも前回の場所に戻ること
  - 無効にすると、メニューとパネルがすぐに外れ、また有効にすると戻ること
  - 安全モードでは題名に「（安全モード）」が付き、プラグインを始めず、管理画面に理由が出ること
  - 始める途中の印を残して起動すると、そのプラグインを無効にして知らせ、問題の記録に残ること
- **Phase 5 の完了判定（サンプルプラグインを有効化してコマンド／ドッキングパネルを登録でき、無効化・異常時にも本体が適切に対処する）を満たした**と判断する。
- まだのこと（Phase 5 の次の段階）: 指示書 7.2 の拡張点のうち、ツールバー・右クリックのメニュー・編集の道具・状態表示、シーンの編集（元に戻すと合わせる。40 章でボーン・モーフの値とキーはできた）、非同期の処理と進み具合、読み込み・書き出しの追加、ほかのアプリとの連携。
- 安全モードで起動して閉じると、そのときに動いていないプラグインのパネルの場所はレイアウトから外れる（次に動いたときは、決めた側に足す）。無効にしたときも同じ。

## 40. シーンの編集と元に戻す（確定・Phase 5 の 2 段階目）

指示書 7.2 の「Document（ドキュメントの取得・編集）」「Undo（履歴・トランザクション登録）」「Event（変更通知）」にあたる。7.2 の「編集処理はアプリ本体の Undo/Redo と整合する API 経由で行う」のとおり、プラグインはシーンの項目を直接さわらず、SDK の入口を通して編集する。SDK の版を 1.1 にした（1.0 のプラグインはそのまま使える）。

### 読む（`ITheaterScene` に足したもの・scene.read）

- モデルの Id（`ModelInfo.Id`）。モデルは Id で指す。名前は、同じモデルを 2 回読み込むと重なるため。Id はアプリを起動し直すと変わる（プロジェクトには保存しない）。
- 選んでいる項目の属するモデルの Id（`SelectedModelId`。モデルそのもの・そのボーン・モーフなどを選んでいるとき）。
- ボーン・モーフの名前の一覧、今の値（ボーンの移動と回転・モーフの値）、キー（フレームと値）。ボーン・モーフは名前で指す（PMX では名前が重なることがまれにあり、そのときは先のもの）。
- ボーンの値は MMD のボーンの移動・回転と同じ（初期の位置からの移動と回転、親のボーンから見た向き。VMD の値と同じ）。
- 編集の知らせ（`Edited`）: 編集の履歴が変わったとき（利用者かプラグインが編集した・元に戻した・やり直した・プロジェクトを開いた）。値やキーが変わるたびに知らせると、再生中に毎フレーム何百回も知らせることになるので、履歴の変化で知らせる。

### 編集（`ITheaterEditor`・scene.edit）

- `editor.Edit("説明", edit => { ... })` の中で、ボーンの値・モーフの値・ボーンのキー・モーフのキーを変える・消す。中の変更はまとめて **1 つの「元に戻す」** になり、編集のメニューに「元に戻す: 説明」と出る。何も変わらなければ履歴に積まない。
- 変える前の値は、その項目を初めて変えるときに写す（`EditTransaction.Include`。変える項目が前もって分からないため）。キーも写す（キーの編集のため、いつもキーまで写す）。
- **途中で例外が起きたら、始める前の値とキーに戻してから、その例外を投げ直す**（途中までの変更を残さない）。プラグインのコマンドの中なら、アプリがメッセージで知らせて問題の記録に残す（39 章）。
- ロックした項目・見つからないモデルやボーンは変えずに false を返す（利用者の状態やシーンの中身によることなので、例外にしない）。値の誤り（負のフレーム・数でない値・長さ 0 の回転）は、プラグインの誤りなので例外にする（まとめた編集ごと取り消す）。
- 値を変えると、利用者が手で変えたときと同じ扱いになる（自動キーが OFF なら未登録の変更、ON なら今のフレームのキー）。キーを置くと、今のフレームの値もキーに合わせる（未登録の変更のある項目は、手で変えた値のまま。キーの当てはめと同じ）。
- キーの補間は SDK では扱わない。同じフレームにキーがあればその動き方を引き継ぎ、無ければ直線（キーの登録と同じ）。補間はアプリのグラフエディタで変える。
- 再生中なら止めてから始める。編集の中で、もう一度 `Edit` は呼べない（外の編集の途中の状態が分かりにくくなるため）。編集の処理を抜けた後に、編集の入口を使うと例外にする。
- プラグインを無効にすると、その後の `Edit` は例外になる。
- カメラ・照明・モデルの出し入れの編集は、まだ SDK に無い。

### サンプル

- 「まばたきを入れる」: 選んだモデルの「まばたき」に、今のフレームから 0 → 3 フレーム後に 1 → 6 フレーム後に 0 のキーを打つ。3 つのキーを 1 つの編集にまとめる見本。モデルを選んでいないときは使えない。
- パネルに「選んだモデルのキー」（ボーン・モーフのキーの数と、「まばたき」のキー）を足した。編集の知らせと選択の変化で数え直す（再生中に毎フレーム数えない）。

### 確かめたこと・まだのこと

- テスト（C#、`BatchEditTests`）: 次のことを確かめた。
  - いくつもの項目の値とキーの変更が 1 つの操作になり、元に戻す・やり直しで全部が戻り・進むこと
  - 途中の例外で全部が戻り、履歴に積まず、例外をそのまま投げ直すこと
  - 負のフレーム・数でない値・長さ 0 の回転は例外で、まとめた編集ごと取り消すこと
  - ロックした項目は変えず、何も変わらなければ積まないこと
  - 同じフレームのキーの補間を引き継ぎ、新しいキーは直線、値を 0〜1 に収めること
  - キーを消す操作も元に戻せること、今のフレームのキーを置くと姿勢も変わること
  - 入れ子にできないこと、終わった後に使えないこと、再生中なら止めること
- 画面（実物のモデル）: 次のことを確かめた。
  - サンプルを有効にして「まばたきを入れる」を使うと、0・3・6 フレームにキーが入り、編集のメニューに「元に戻す: まばたきを入れる」と出ること
  - 1 回の Ctrl+Z で 3 つとも消え、Ctrl+Y で戻ること（パネルのキーの表示も編集の知らせでついて行く）
  - 3 フレーム目で目が閉じていること、タイムラインにキーの印が出ること
  - 選択を解除すると「まばたきを入れる」が使えなくなること
- まだのこと: カメラ・照明・材質・映像効果などの編集、モデルの読み込みと外す、キーの補間の SDK、選択を変える API。

## 41. ツールバー・右クリックのメニュー・状態表示（確定・Phase 5 の 3 段階目）

指示書 7.2 の「UI: メニュー、ツールバー、ドッキングパネル、ダイアログ、コンテキストメニュー、編集ツール、ステータスバー」のうち、ツールバー・コンテキストメニュー（右クリックのメニュー）・ステータスバー（状態表示）を足した。SDK の版を 1.2 にした。編集ツール（プレビューの中でドラッグして使う道具）はまだ。

### 共通の契約に置くもの・アプリの SDK に置くもの

- ツールバー（`IToolbarRegistry`）・右クリックのメニュー（`IContextMenuRegistry`）・状態表示（`IStatusBarRegistry`）の契約は、画面の契約（`Plugin.UI.Wpf`）に置いた。どのアプリにもある部品のため。
- **どのメニューに足せるかは、アプリが決める**。メニューの名前は文字（`Place`）で渡し、3D Theater の名前（`preview`・`scene-tree`）は 3D Theater の SDK（`TheaterMenuPlaces`）に置いた。共通の契約に「プレビュー」「シーンの一覧」のようなアプリの言葉を入れないため（指示書 7.1）。知らない名前は誤り（例外）にする。

### ボタンとメニューの項目はコマンドから作る

- ツールバーのボタンと右クリックのメニューの項目は、どちらも **プラグインが先に登録したコマンドを Id で指す**。名前・ショートカット・説明・今使えるか（`CanExecute`）・実行の処理を、メニュー「プラグイン」と同じ 1 つのコマンドから使う（同じ処理を 3 か所に書かせないため）。コマンドを外すと、そのボタンと項目も外す。
- ボタンは、絵の文字（Segoe Fluent Icons の 1 文字。アプリのツールバーと同じ字体）か文字で出す。説明（マウスを乗せたとき）には、コマンドの名前・ショートカット・説明・プラグインの名前を出す。アプリのボタンの後ろに、区切り線をはさんで並べる。
- ボタンを押せるかどうかは、WPF のコマンドの仕組み（画面の操作のたびに確かめ直す）に任せ、選択・編集・再生位置が変わったときにも確かめ直す（キーで再生位置を動かしたときなど、ボタンに触れなくても変わるため）。
- 右クリックのメニューの項目は、メニューを開くたびに作り、そのときに使えるかどうかを決める。アプリの項目の後ろに、区切り線をはさんで並べる。
- コマンドの実行・使えるかの確かめで起きた例外は、メニューから使ったときと同じく受け止める（39 章）。

### 足せるメニュー

| 名前 | メニュー |
|---|---|
| `preview` | プレビューの右クリックと、区画の見出しの視点のボタンのメニュー |
| `scene-tree` | シーンの一覧の行の右クリックのメニュー |

- シーンの一覧には、これまで右クリックのメニューが無かったので作った。右クリックした行を選んでから（選んでいる行の中なら選択はそのまま）、「名前を変える（F2）」とプラグインの項目を出す。プラグインのコマンドは選んでいる物に対して動くため、先に選ぶ。キーボードのアプリキーでも、選んでいる行のメニューが出る。

### 状態表示

- プラグインは文字の欄を足し、文字と説明を変えられる（`IStatusBarItem.Text`・`ToolTip`）。アプリの欄（フレーム・描画の方式など）の左に並ぶ。長い文字は途中で切る（幅 320）。空の文字なら欄を隠す。
- 欄はプラグインごとに Id で区別する。プラグインを無効にすると外れる（プラグインが後で文字を変えても、画面には出ない）。

### サンプル

- 状態表示に「時間 分:秒」（今のフレームを時間で表したもの）を足した。

### 確かめたこと・まだのこと

- 画面（実物のモデル）: 次のことを確かめた。
  - 有効にすると、ツールバーにボタンが出て（説明にコマンドの名前・説明・プラグインの名前）、状態表示に「時間 0:00.00」が出ること
  - ボタン・プレビューの視点のボタンのメニュー・シーンの一覧のメニュー（アプリキーで開いた）のどれからでも「まばたきを入れる」が使え、元に戻せること

  - 再生位置を末尾にすると、状態表示が「時間 0:10.00」になること

## 42. 時間のかかる処理とファイルの形式（確定・Phase 5 の 4 段階目）

指示書 7.2 の「Task（非同期処理、進捗、キャンセル）」と「File（追加インポーター／エクスポーター）」にあたる。どちらもアプリに依存しないので、共通の契約（`Plugin.Core`）に置いた。SDK の版を 1.3 にした。

### 時間のかかる処理（`IPluginTasks`・tasks）

- `tasks.RunAsync("題名", async task => { ... })` で、プラグインの処理を走らせる。処理には、取り消し（`task.Cancellation`）と進み具合の知らせ（`task.Report(0〜1 か null, "今していること")`）を渡す。
- 処理は画面のスレッドから始める。重い計算やファイルの読み書きは、プラグインが `Task.Run` などに分ける。`await` の後は画面のスレッドに戻るので、シーンの編集（40 章）はそこで行う。こうすると、SDK を画面のスレッドだけで使う決まり（39 章）を守ったまま、重い所だけを別のスレッドにできる。
- **0.3 秒で終わらなければ、進み具合の窓を出す**（題名・プラグインの名前・進み具合の棒・今していること・「取り消す」）。すぐに終わる処理で窓がちらつかないように、待ってから出す。進み具合が分からないときは、棒を左右に動かす。
- 窓を出している間は、アプリの操作はできない（窓はアプリの上に出て、閉じるまでほかを触れない）。処理の途中でシーンが変わると、プラグインの処理（例: 読み込んだキーの当てはめ）が、利用者の編集とぶつかるため。
- 「取り消す」（×・Esc も同じ）は取り消しを頼むだけで、処理が止まるまで窓は閉じない（止まらないうちに次の操作ができると、上と同じくぶつかるため）。
- 進み具合の知らせはどのスレッドからでもよく、何度知らせても画面の書き換えはまとめて行う（知らせを覚えておき、画面のスレッドで 1 回ずつ出す）。
- 終わり方:
  - 最後まで終わった → 状態表示に「「題名」が終わりました」
  - 取り消しを頼まれていて、`OperationCanceledException` で終わった → 「「題名」を取り消しました」
  - 例外で終わった（取り消しを頼まれていないのに出た取り消しの例外も含む） → メッセージで知らせ、問題の記録（39 章）に残す
- `RunAsync` 自身は例外を投げない（終わり方を返す）。プラグインのコマンドから、待たずに始められるようにするため。
- 状態表示は 0.5 秒ごとに「準備完了」に戻していたので、処理の結果がすぐに消えていた。プラグインの処理の結果などの知らせは、8 秒残すようにした。

### ファイルの形式（`IFileFormatRegistry`・files）

- プラグインは、名前・拡張子・読み込む処理・書き出す処理（どちらか一方でもよい）・今読み書きできるか・書き出しの最初の名前を登録する。
- 登録した形式は、ファイルのメニューの「読み込む（プラグインの形式）」「書き出す（プラグインの形式）」に出る（形式があるときだけ）。選ぶと、その形式で絞ったファイルの窓を出す。今読み書きできないとき（例: モデルを選んでいない）は、メニューを開いたときに使えなくする。
- **読み込める形式は、ウィンドウへのドラッグと、起動のときに渡したファイルでも読み込む**（アプリの形式のファイルと同じ道）。アプリの形式（PMX・VMD など）を先に読み込むので、一緒にドラッグしたモデルに使える。同じ拡張子の形式が 2 つあれば、先に登録したもの。
- 読み込み・書き出しは、時間のかかる処理と同じく、進み具合の窓・取り消し・エラーの知らせを通る。
- **書き出しは、同じフォルダーの一時ファイル（`~名前_8 桁.拡張子`）に書かせてから、選ばれた名前に置き換える**（指示書 8 章「一時ファイル書き込み後の置換」）。途中で失敗・取り消したときに、元のファイルを壊さず、書きかけを残さないため。拡張子を同じにするのは、拡張子で形を決める書き手のため。プラグインが何も書かなければエラーにする。
- 拡張子は「.csv」のような形（「.」から始まる英数字）だけを受け付ける。

### サンプル

- 「キーの CSV（サンプル）」: 選んだモデルのボーン・モーフのキーを CSV（UTF-8・BOM 付き。表計算ソフトで開ける）に書き出し、読み込む。読み込みは 1 つの編集にまとめる（1 回の「元に戻す」で消える）。モデルに無い名前のキーは飛ばして、数を知らせる。読めない行があれば、行の番号と理由を付けてエラーにする。
  - 書き出しは、キーを画面のスレッドで集めてから、ファイルを別のスレッドで書く。読み込みは、ファイルを別のスレッドで読んでから、画面のスレッドでキーを当てはめる（見本として、SDK を使う所と重い所を分けている）。
- 「時間のかかる処理の見本（5 秒）」: 0.1 秒ずつ 50 まで数える（進み具合の窓と取り消しの見本）。

### 確かめたこと・まだのこと

- テスト（C#、`PluginTaskTests`）: 次のことを確かめた。
  - 最後まで終わった・取り消した・例外の終わり方（await の前に投げた例外、Task を返さない処理、頼まれていない取り消しの例外はエラー）
  - 進み具合を 0〜1 に収め、数でなければ「分からない」にすること
  - 書き出しは、同じフォルダー・同じ拡張子の一時ファイルに書かせ、成功したら置き換えて一時ファイルを残さないこと
  - 失敗・取り消しでは元のファイルの中身を残し、書きかけを消すこと、何も書かなければエラーにすること
- 画面（実物のモデル）: 次のことを確かめた。
  - 有効にすると、ファイルのメニューに 2 つの項目が出ること
  - まばたきのキーを CSV に書き出すと、中身が正しく、一時ファイルが残らないこと
  - 元に戻してから読み込むとキーが戻り、編集のメニューに「元に戻す: キーの CSV の読み込み（キー.csv）」と出ること
  - 壊れた CSV では、行の番号と理由を付けたエラーの知らせが出て、キーは変わらないこと
  - 見本の処理で進み具合の窓が出て（19 / 50）、「取り消す」で止まり、状態表示に「取り消しました」と出ること。最後まで待つと「終わりました」と出ること
  - 起動のときにモデルと CSV を渡すと、モデルを読み込んでから CSV を読み込むこと（ドラッグと同じ道）
- まだのこと: 実際のマウスでのドラッグ（マウスを使わない確かめのため。同じ読み込みの道は、起動のときのファイルで確かめた）。進み具合を窓でなく状態表示に出して、操作を続けられる処理（ぶつからない処理のため）。いくつもの処理を同時に走らせること。

## 43. 描画の SDK・ほかのアプリとの連携・API 文書（確定・Phase 5 の 5 段階目）

指示書 7.1 の「3D Theater 専用 SDK：モデル、シーン、選択、モーション、レンダリング等を公開」のレンダリング、7.2 の「Interop（外部アプリ連携）」、Phase 5 の「API 文書」にあたる。SDK の版を 1.4 にした。

### シーンを絵にする（`ITheaterRenderer`・render.image）

- `renderer.RenderFrame(new RenderRequest { Width, Height, Frame, Transparent, Background, Smooth })` で、シーンのカメラから見たフレームを描き、画素と PNG を返す。
- **描き方は書き出しの見本（38 章）と同じ**（書き出しの品質・映像効果・イラスト風・物理の焼き込み。格子・ボーン・ギズモなどは映らない）。プラグインのために別の描き方を作ると、書き出しと見え方がずれるため。モーションブラーはかけない（1 枚を急いで欲しいときに使うため）。
- 描き終えたら、再生位置・画面の物理・描き直しを元に戻す（書き出しと同じ）。描いている間は画面が止まる（描画エンジンは画面のスレッドで使うため）。
- 画素は B・G・R・A の順で、**透明度を色にかけ合わせていない値**で渡す（ほかのアプリに渡すときに、そのまま使いやすいため。エンジンの中ではかけ合わせているので、割り戻してから渡す）。透明にしないときは、どの画素も不透明。PNG も一緒に渡す（透明にしたときは透過 PNG、しないときは色だけの PNG）。
- 1 辺は 1〜8192（なめらかにするときは 2 倍で描くので、描く大きさの上限 16384 の半分）。範囲の外は例外。
- 利用者が書き出しの画面で決めた大きさ（`ExportSize`）も読める（プラグインが同じ大きさで描けるように）。

### ほかのアプリとの連携（Interop）

- 指示書 7.4 のとおり、連携の通信の方式（Named Pipes など）は、連携の機能を作る段階で決める。この段階では、**連携に要る SDK の入口（今のフレームを透過 PNG で得る）を、特定のアプリだけのものにせずに用意した**（7.4「この例専用の API を Plugin.Core に設けない」）。描く入口は 3D Theater の SDK に置き、共通の契約には置いていない。
- サンプルの「今のフレームを画像としてコピー（透明な背景）」（Ctrl+Alt+C）は、連携の口に、どのアプリでも受け取れるクリップボードを使う見本。書き出しの大きさで描き、2 つの形で写す:
  - 透過 PNG（「PNG」の形）: 透明度を読めるアプリ（画像の編集ソフトなど）が使う
  - 白い背景に重ねた画像（ふつうの画像の形）: 透明度を読めないアプリが使う（透明な所が黒くならないように）
- 時間のかかる処理（42 章）として走らせるので、描き終えると状態表示に「終わりました」と出る。

### API 文書

- 契約の 3 つの DLL（`Plugin.Core`・`Plugin.UI.Wpf`・`3DTheater.Plugin.SDK`）に、XML の説明（API 文書）を出すようにした。アプリの出力の DLL の隣に写るので、プラグインのプロジェクトがその DLL を参照すると、Visual Studio の候補に日本語の説明が出る。
- 公開している型とメンバーには、すべて説明を書く（説明が無いとビルドの誤りになる設定）。足りなかった所（ログ・plugin.json の項目・管理の部品など）に書き足した。
- 使い方の説明は [プラグインの作り方](プラグインの作り方.md)、決めたことと理由はこの記録（39〜43 章）。

### 確かめたこと・まだのこと

- 画面（実物のモデル）: 次のことを確かめた。
  - サンプルのコマンドで、クリップボードに「PNG」とふつうの画像の 2 つの形が入ること
  - PNG は 1920 x 1080（書き出しの大きさ）で、背景は透明・モデルは不透明・地面の影とモデルの縁は半透明。ふつうの画像は白い背景で、どこも不透明
  - 写った絵が、書き出しと同じ描き方であること（格子・ギズモなどが映らない）
  - 末尾のフレームでショートカット（Ctrl+Alt+C）でも同じように写り、描いた後も再生位置が末尾のままであること
  - 確かめの前に空だったクリップボードを、終わった後に空へ戻した
- テストは足していない（描き方は書き出しの見本と同じものを使い、SDK の部分は画面で確かめた）。
- まだのこと: 連携の通信の方式（Named Pipes など）と、Drawing Canvas との連携（それぞれのアプリで連携の機能を作る段階で）。プラグインどうしの機能の受け渡し（指示書 7.3。契約の型を共有する決まりが要る）。モーションブラー付きで描く・ほかのカメラや視点から描く SDK。

## 44. 編集の道具（確定・Phase 5 の 6 段階目）

指示書 7.2 の「UI: … 編集ツール …」にあたる。これで 7.2 の表の拡張点（Plugin / Lifecycle・Command・UI・Event・Document・Undo・Settings・Task・File・Interop）に、どれも最初の版ができた。SDK の版を 1.5 にした。

### 道具の形（`IEditToolRegistry`・ui.edittools）

- プラグインは、名前・絵の文字・説明と、道具を選んだときに受け取り手（`IEditToolHandler`）を作る処理を登録する。
- 受け取り手には、プレビューの区画の **左ボタンの操作** だけを渡す: 押した（`Pressed`）・動かした（`Moved`）・放した（`Released`）・取り消した（`Cancelled`）・道具を外した（`Deactivated`）。視点の操作（中ボタン・ホイール）と右クリックのメニューは、道具を選んでいてもアプリのまま（どの道具でも視点を動かせるように）。
- `Pressed` が false を返したら、アプリの操作（クリックで選ぶ）に任せる。例えば、モデルを選んでいないときにクリックしてモデルを選び、続けてドラッグで動かせる。
- 位置は区画の左上からの WPF の画面の単位で渡す（共通の契約は 3D の言葉を持たない）。3D Theater の情報は `pointer.GetView<ITheaterView>()` で取り出す（7.1。アプリ専用のものは、そのアプリの SDK に置く）:
  - マウスの位置を通る視線（始点と向き。クリックで選ぶときと同じ視線）
  - ワールドの点が区画のどこに見えるか
  - **ドラッグの編集**（`DragEdit`。40 章の `ISceneEdit` と同じ入口）

### ドラッグ 1 回を 1 つの「元に戻す」に

- アプリは左ボタンを押したときに、まとめた編集を開き（`EditService.BeginBatch`。40 章のまとめた編集を、開いたままにできるようにしたもの）、`DragEdit` として渡す。
  - 放したら、そこまでの編集を 1 つの「元に戻す」として積む（名前は道具の名前）
  - Esc・ドラッグ中の右クリック・道具を外したときは、始める前の値とキーに戻す
  - `Pressed` が false を返したときも元に戻す
- 開く・閉じるをアプリが受け持つので、プラグインは「元に戻す」の扱いを書かなくてよい（ギズモのドラッグと同じ決まりになる。指示書 3.3「ドラッグ 1 回を 1 つの Undo に」）。
- ドラッグの途中は、元に戻す・やり直し（Ctrl+Z・Ctrl+Y）をしない（開いている編集とぶつかるため）。ほかのまとめた編集も始められない。
- 道具の例外は受け止めて記録し（39 章）、そのドラッグを元に戻して、状態表示に出す。アプリは止めない。

### 道具の選び方

- 道具はツールバーのプラグインのボタンの後ろに、押したままになるボタンで並ぶ。押すと選び、もう一度押すと外す。
- 選んでいる間は、プレビューにギズモを出さない（アプリの「選択・移動・回転」の道具から持ちかえたのと同じ扱い）。アプリの道具のボタン・Q / W / E・ギズモの方式を選ぶと、プラグインの道具は外れる。
- プラグインを無効にすると、その道具は外れる。
- ボタンは押した状態（Checked）で切り替える（マウスだけでなく、キーボードや UI Automation で押しても同じに）。

### サンプル

- 「センターを床の上で動かす」: 選んだモデルの「センター」を、床（高さ 0）の上でドラッグして前後左右に動かす。押した所から今の所までの床の上の動きを、押したときのセンターの移動に足す。モデルを選んでいない・センターが無い・床が見えない（真横からの視点など）ときは、アプリの操作に任せる。
  - 見本なので、モデルを回したり大きさを変えたりしていないときの動きにしている。PMX も 3D Theater も左手系で、センターの親が回っていなければ、床の上の動きがそのままボーンの移動になるため。
- パネルに「センター」の移動を出すようにした（編集の知らせで出し直す）。

### 確かめたこと・まだのこと

- テスト（C#、`BatchEditTests`）: 開いたままのまとめた編集について、次のことを確かめた。
  - 何度も変えてから確定すると 1 つの操作になり、元に戻す・やり直しで戻り・進むこと
  - 取り消し・終えずに Dispose したときは全部戻り、積まないこと、終わった後は使えないこと
  - 開いている間はほかのまとめた編集を始められず、何も変えなければ積まないこと
- 画面（実物のモデル）: 次のことを確かめた。
  - 有効にすると道具のボタンが出て、押すと選んだ状態になり、プレビューのギズモが消えること
  - Q でアプリの道具に戻り、ボタンが戻ること
  - 選んだままプラグインを無効にすると、ボタンが消えること
- **まだのこと: プレビューの上での実際のドラッグ**（センターが動く・放すと 1 つの元に戻すになる・Esc で戻る）は、画面では確かめられなかった。マウスを使わずに確かめるため、マウスの知らせを窓に直接送ったが、WPF は受け付けなかった（本物のマウスが窓の上にないときの知らせは捨てているとみられる。41 章の右クリックと同じ）。ドラッグの編集の部分はテストで確かめた。実際のマウスで確かめる。
- まだのこと: 道具がプレビューに線や印を描くこと（今は描けない）、ホイール・キーの受け取り、プレビュー以外（タイムラインなど）の道具。

## 46. レンダーパスの書き出し（確定・Phase 5 の映像品質の 1 段階目）

指示書 6.3 の「将来：Beauty／Alpha／Depth／Normal／Shadow／Emission／Object ID／Material ID 等のレンダーパス出力」と、Phase 5 の「高品質レンダーパス」にあたる。合成ソフトで仕上げるための画像を、普通の絵（Beauty）と一緒に書き出す。描画エンジンの API を 0.21 にした。

### 書き出せるパス

| パス | ファイル | 中身 |
|---|---|---|
| アルファ | 名前_alpha.png | 物の形の白黒（8 ビット。白 = 物）。なめらかにする。輪郭線も含む。透明な背景にしなくても書ける |
| 奥行き | 名前_depth.png | カメラから見る向きの距離の白黒（**16 ビット**）。手前ほど白く、奥ほど黒い。何も無い所は黒 |
| 法線 | 名前_normal.png | カメラから見た面の向き（右・上・奥を -1〜1 から 0〜1 にして赤・緑・青に）。裏の面は手前へ向ける |
| 物の ID | 名前_objectid.png | 物（モデル）ごとの色 |
| 材質の ID | 名前_materialid.png | 物と材質ごとの色 |
| 影 | 名前_shadow.png | 影の白黒（8 ビット。白 = 影の中）。セルフシャドウと地面の影（それぞれ ON のとき） |

- 連番は「名前_パスの語_フレーム.png」。ファイルの名前に付ける語は、合成ソフトで扱いやすいよう英語にした。
- 静止画と連番のとき。動画では書かない（パスは合成用で、1 枚ずつの画像のほうが扱いやすいため）。
- 書き出しの画面に「パス」の行を足し、選んだパスを利用者の設定に覚える。

### 描き方

- 描画エンジンは、パスのときに、モデルを色の計算の代わりにパスの値で描く（シェーダーの中で分ける）。映像効果・背景・床の映り込み・格子は描かない（パスの値に混ざらないように）。輪郭線はアルファのときだけ描く。
- **奥行き・法線・ID・影・発光は、なめらかにしないで描く**（MSAA なし・2 倍で描いて縮めることもしない）。縁で値が混ざると、ID の色が対応表に無い色になり、奥行きも手前と奥の間の値になって使えないため。アルファだけは普通の絵と同じくなめらかにする（縁の半透明が要るため）。
- 材質とテクスチャの不透明度が 0.5 より小さい所は、アルファのほかは物の形に含めない（髪の透けた所などで、ID や奥行きが中途半端にならないように）。
- 奥行きは 0〜1 を 65535 倍した整数を、エンジンの出力の赤（上位 8 ビット）と緑（下位）に分けて出し、書き出しで 16 ビットの白黒にする（8 ビットの色の出力のままで 16 ビットの精度を得るため）。
- 奥行きの範囲（0 と 1 にする距離）は、最初のフレームで物を囲む箱から決め、全部のフレームで同じにする（連番で明るさがちらつかないように）。動いても収まるよう、手前へ幅の 1/4、奥へ幅の 1/2 のゆとりを持たせる。
- ID の色は、番号を整数で混ぜて決める（エンジンのシェーダーと C# で同じ式）。どの成分も 64 以上なので、黒い背景と区別できる。物の番号は描く物の並び順（1 から）、材質は「物の番号 × 4096 + 材質の番号 + 1」。
- パスにはモーションブラーをかけない。

### 説明のファイル（名前_passes.json）

- 書いたパス、奥行きの範囲（カメラから見る向きの距離の near・far と、白黒の読み方）、物と材質の色の対応表（番号・名前・色）を書く。合成ソフトで ID の色から物や材質を選ぶ・奥行きを距離に戻すのに使う。

### 確かめたこと・まだのこと

- テスト:
  - 描画エンジン（C#、WARP）: 物・材質の ID の色が C# の式と 1 の位まで同じこと、奥行きの値（カメラから 5 先が 0〜10 の真ん中）、法線の色、アルファの白、発光の無い材質の黒、何も無い所が透明な黒になること。ID の色が 200 番まで違う色で、どれも明るいこと
  - Editor: パスのファイルの名前（静止画・連番・説明のファイル。動画では書かない）、奥行きの範囲のゆとり、奥行きの画素から 16 ビットの白黒への変換と、透明度の取り出し
- 画面（実物のモデル 2 体・モーション）: 60 フレーム目を 7 つのパスと一緒に書き出し、8 枚と説明のファイルができること、連番（3 フレーム）で 9 枚と説明のファイルができることを確かめた。中身は次のとおり。
  - 奥行きは 16 ビットの白黒、アルファと影は 8 ビットの白黒
  - 物の ID の色（2 色）と材質の ID の色（22 色）が、どれも対応表にある色
  - 並べて見て、アルファ・奥行き・法線・ID・影（セルフシャドウと地面の影）・発光（黒）が期待どおり
- まだのこと: EXR（浮動小数点）での奥行きなどの書き出し、動きのベクトル（モーションブラーを合成でかけるため）、なめらかな縁の ID（Cryptomatte のような形）、照明ごとのパス、動画でのパス。

## 47. 床の映り込みのぼかし（確定・Phase 5 の映像品質の 2 段階目）

Phase 5 の「発展的な反射・レイトレーシング等を必要に応じて追加」の最初の段階で、31 章の持ち越し「床の映り込みのぼかし」にあたる。磨いた木の床のような**つやのある床**では、床に接する所はくっきり映り、床から離れた所ほどぼやけて映る。これを床の映り込みに足した。描画エンジンの API を 0.22 にした。

### 設定（プロジェクトに保存）

- `FloorReflection.Blur`: ぼかし（0〜1、初期値 0 = 今までどおりのくっきりの鏡）。範囲の外は収め、数でない値は 0 にする。描き方の `rendering.reflection` の中に一緒に保存する（前の版のファイルは 0 として読む）。
- 画面: 「床の映り込み...」の窓に「ぼかし」の行を足した。変えるとすぐにプレビューへ反映し、書き出しにもかかる。
- ぼけの半径は「床からの深さ × 0.2 × ぼかし」（ワールドの長さ。人の大きさのモデルの背丈は 20 ほど）。ぼかし 1 なら、くるぶし（深さ 1）で 0.2、ひざ（深さ 5）で 1 ほどぼける。画面の上の大きさは、映った点までの距離で変わる（遠い物ほど小さくぼける）。

### 描き方

- ぼかすときは、映り込みを場面に直接描かず、**別の画像（ビューごと）へくっきり描いてから、ぼかして重ねる**。
  1. 映したモデルを、色（透明度をかけ合わせた値）と「床からの深さ × 不透明度」の 2 つの画像へ同時に描く（モデルのシェーダーに 2 つ目の出力を足した。2 つ目の描画先が無いときは捨てられる）。
  2. 半分ずつ縮めた段（ミップ）を作る（最大 8 段）。縮めるときは 4 × 4 画素をなだらかに平均するので、段を重ねるとガウスのぼかしに近くなる。色と深さを同じ重みで縮める。
  3. 背景（環境の画像）のすぐ後に、画面全体へ重ねる。画素ごとに床からの深さを求め、映った点までの距離からぼけの半径（画素）を出し、その大きさに合う段（段 k のぼけはおよそ 2^k 画素。間の値は前後の段を混ぜる）を、まわりの 9 点でなだらかに読む。
- 床からの深さは、段ごとの「深さ × 不透明度」と「不透明度」を細かい段ほど重くして（1 段ごとに 1/8）足し合わせ、割って出す。映り込みの中ではその場所の深さ、外のぼけて広がる所では近くの映り込みの深さになり、場所によってなめらかに変わる。最初は「映り込みのある、いちばん細かい段」の深さを使ったが、段が切り替わる所でぼけの大きさが急に変わり、映り込みのまわりに輪のような筋が出たので、この形にした。
- 段の色は 16 ビットの浮動小数点で持つ（8 ビットでは、ぼかした薄い色が段階に分かれるため）。
- 格子・確認用の立方体・地面の影・モデルは、ぼかした映り込みの上に描く。
- ぼかした映り込みは奥行きを書かない（地面の影と同じ）。映像効果では、霧は床までの距離でかかり（くっきりの映り込みは映った姿までの距離）、被写界深度では背景と同じ扱いになり、線画の線は引かない（ぼけた縁に線が出ないように）。
- 映り込みの画像は MSAA を使わずに描く（ぼかすので、ギザギザは目立たない。書き出しの「なめらかにする」では 2 倍で描いて縮める）。
- 使うときだけ画像を作り、ぼかしをやめたら手放す。大きさは描画先と同じで、1 画素あたり 17 バイトほど（1920 × 1080 で 35 MB ほど）。

### 描画エンジン（API 0.22）

- 描画の条件の空きの欄（`reserved8` の 1 つ目）を `reflection_blur`（0〜1）にした。構造体の大きさと並びは変わらないので、前の版の呼び出し（0 が入る）は今までどおりくっきり描く。
- `View` が `ReflectionTargets`（色と深さの段・奥行き）を持ち、`DrawScene` へ渡す。シェーダーを 2 つ（縮める・重ねる）と、透明度をかけ合わせた色の合成の設定を足した。

### 確かめたこと・まだのこと

- テスト:
  - 描画エンジン（WARP）: 高さ 0.5〜1.5 の赤い四角形の映り込みで、ごく小さいぼかしでは、別の画像に描いて重ねる道を通っても、くっきりの映り込みと全部の画素で 3 以内しか違わないこと（位置がずれない・濃さが変わらない）。ぼかし 1 では、もとの四角形は変わらず、映り込みの真ん中は赤いまま、縁の 4 画素外へ、床から深い所（深さ 1.4）ほど大きく広がること（浅い所より 5 以上赤い）。映像効果を使う道でも同じにぼかすこと
  - Editor: ぼかしの範囲（1 より大きい・負・数でない値）と、プロジェクトの保存と読み込み
- 画面（実物のモデル・床が広く見えるカメラ）: 「床の映り込み...」の窓にぼかしの行が出て、値が表示されること、プレビューの 2 つの視点ですぐにぼけること。ぼかし 0・0.5・1 の書き出し（暗い色の背景と透明な背景）を並べて、足元はくっきりで、脚の下へ行くほどぼけること、透明な背景では映り込みが半透明で残ることを確かめた。最初の形で見つけた、ぼかしが強すぎることと、映り込みのまわりの輪のような筋は、上のとおり直して、直ったことを書き出しで確かめた。
- まだのこと: 床の高さと傾き、画面の中の反射（SSR）、環境の画像での映り込み、床の場所ごとのぼかし（床の材質）、縦に伸びるぼけ方（実際のつやのある床では、映り込みは縦に長くぼける）、ぼかした映り込みの奥行き（霧・被写界深度を映った姿の距離にする）。プレビューでの重さは測っていない。

## 48. 画面の中の反射（SSR）（確定・Phase 5 の映像品質の 3 段階目）

Phase 5 の「発展的な反射」の 2 つ目で、31 章の持ち越し「画面の中の反射（SSR）」にあたる。拡張材質（29 章）で PBR にした、つやのある材質（磨いた床・金属の飾りなど）に、**画面に映っているほかの物**を映す。今までの PBR の映り込みは、空と地面の 2 色か環境の画像（36 章）だけだった。描画エンジンの API を 0.23 にした。

### 設定（プロジェクトに保存）

- 映像効果（`VisualEffects`）に、画面の中の反射の ON / OFF・強さ（0〜1、初期値 1）・探す距離（1〜200、初期値 30。ワールドの長さ）を足した。範囲の外は収め、数でない値は初期値にする。映像効果の画面に「画面の中の反射」の段を足した。すべての視点と書き出しにかかる。
- 映るのは PBR の材質だけ。トゥーンの材質（MMD のままの材質）には映さない。粗い材質ほど弱くし、粗さ 0.65 より上では映さない（ぼけた映り込みは、今までの環境の映り込みのまま）。

### 描き方

- **下準備（モデルを描くとき）**: 色と一緒に、3 つの画像へ「映り込みの強さ（フレネル）」「環境の映り込み（強さを掛けた色）」「見る向きの座標での面の向き × (1 + 粗さ)」を書く（モデルのシェーダーの 2〜4 番目の出力。描画先と同じ大きさ・MSAA の点の数）。このとき PBR の材質は、**環境の映り込みを色に入れずに分けて書く**。どの値も色と同じ合成（不透明度 a と 1 − a）で重ねるので、半透明の材質・輪郭線（下の面の値を線の不透明度だけ消す）とも合う。粗さは面の向きの長さに入れた（合成で重ねる値は、a の欄を不透明度に使うため、1 つの画像に 3 つしか値を入れられない）。
- **画面の中の反射（映像効果の段。環境光の遮りの後・霧と被写界深度の前）**: 画素ごとに、面の向きで見る向きを折り返した光線を、探す距離だけ画面の上で 48 歩に分けて進め、画面の奥行き（見る向きの距離）の手前から奥へ入った所を探し、前の点との間を 6 回半分ずつ詰めて交わる所を決める。そこの色（モデルの色 + そこで分けて書いた環境の映り込み）に映り込みの強さを掛け、見つかった分だけ環境の映り込みと置き換えて足す。
  - 見つからない所（画面の外へ出た・探す距離より遠い・物の裏を通った）、カメラの方へ戻る光線、物の裏に当たった光線は、環境の映り込みのまま（画面の端の近く・探す距離の終わりの近くは、なめらかに置き換えを弱める）。
  - 粗いほど、遠い物ほど、当たった所の周りの 4 点も混ぜてぼかす。
  - 下準備を書いたときは、効果を使えないとき（強さ 0・奥行きの準備が無いなど）も、分けて書いた環境の映り込みを必ず戻す（戻すだけなら、今までと 3 以内しか違わないことをテストで確かめた）。
- **自分の面に当たったことにしない**: 斜めに見る床では、1 画素の中でも奥行きが大きく変わるので、画素の真ん中の奥行きで比べると、光線がすぐ自分の床の奥へ入ったことになり、何も映らない所が暗い筋になった（テストで見つけた）。画面の奥行きは周りの 4 画素から補って比べ、始めの 1 画素の中は比べないようにした。
- 足りない形式: この GPU で、今の MSAA の点の数が下準備の画像の形式で使えないときは、反射なしで描く（ログに出す）。
- 使うときだけ画像を作り、やめたら手放す。MSAA の点の数を変えたときも作り直す（テストで見つけた。作り直さないと、点の数の違う描画先を一緒に使えず、何も映らなかった）。1 画素あたり 24 バイトほど（MSAA 4 倍では、点の分も合わせて 100 バイトほど）。

### 描画エンジン（API 0.23）

- `TT_POST_SSR` と、描画の条件の最後に `ssr_strength`（0〜1）・`ssr_max_distance`（0.1 以上）を足した（構造体の大きさが変わった。C# 側も合わせた）。
- `View` が下準備の画像（`SurfaceTargets`）と、反射をかけた場面の画像を持つ。物ごとの定数に「下準備を書くか」を足した。

### 見つけて直した不具合

- モデルのシェーダーで、トゥーンと PBR を条件の演算子（? :）で分けていたため、トゥーンの材質でも PBR の計算が走り、分けて返すようにした環境の映り込みがトゥーンの色に足されていた（トゥーン・スフィア・影など 6 つのテストが落ちて分かった）。if で分けるようにした。

### 確かめたこと・まだのこと

- テスト:
  - 描画エンジン（WARP）: 滑らかな金属（PBR）の床の奥に赤い四角形を立て、反射を使うと、床の手前に赤が映ること（周りの色の映り込みが赤に置き換わる）。四角形そのもの（トゥーン）は変わらないこと。四角形から離れた床（映る物が無い所）は反射なしと同じなこと。探す距離が短く何にも当たらなければ、反射なしと全部の画素で 3 以内しか違わないこと。MSAA（4 倍）でも映ること。トゥーンの床には映らないこと
  - Editor: 画面の中の反射の値の範囲と、プロジェクトの保存と読み込み

## 49. レイトレーシングでの映り込み（確定・Phase 5 の映像品質の 4 段階目）

Phase 5 の「レイトレーシング等を必要に応じて追加」にあたり、48 章の持ち越し「画面に映っていない物の映り込み（レイトレーシング）」を足した。画面の中の反射（48 章）は、画面に映っている物しか映せない（画面の外・物の裏・カメラの方へ戻る向きは環境の映り込みのまま）。その足りない所を、**光線をモデルの三角形に当てて**探し、当たった物を映す。描画エンジンの API を 0.24 にした。

### なぜこれにしたか

- レイトレーシングの使い道は、映り込み・影・環境光の遮りが考えられる。影（奥行きの画像。23・35 章）と環境光の遮り（画面の奥行き。33 章）は今の方法で一通り描けている。映り込みは、48 章で画面の外が映らないことがはっきり目に見える欠けとして残っていたので、映り込みから始めた。
- Direct3D 11 には GPU のレイトレーシングの仕組み（DXR）が無い（Direct3D 12 だけ）。三角形を箱の入れ子にまとめる所は CPU で、光線をたどる所はピクセルシェーダーで書いた。どの GPU でも動き、WARP でテストできる。

### 設定（プロジェクトに保存）

- 映像効果の「画面の中の反射」の中に「レイトレーシングで、画面に映っていない物も映す（画面の外・物の裏。重い）」を足した（`VisualEffects.SsrRayTracing`。初期値 OFF）。画面の中の反射が ON のときだけ使える（画面では、画面の中の反射を切ると項目も使えなくなる）。強さ・探す距離は、画面の中の反射と同じ値を使う。

### 描き方

- **箱の入れ子（BVH）**: メッシュごとに、材質の範囲にある三角形を、モデルの座標で箱の入れ子にまとめる。分け方は、軸ごとに三角形の中心を 12 の区画へ振り分け、「箱の表面積 × 三角形の数」の合計（光線が通るときの手間の目安）がいちばん小さい境目で分ける。端の箱には三角形を 4 枚まで入れる。初めて使うときに作る。
- **動くモデル**: 頂点が変わったら（モーション・物理・モーフ）、作り直さずに箱の大きさだけを合わせ直す（速い）。動いて箱がふくらみ、調べる箱の多さの目安が作ったときの 1.6 倍を超えたら作り直す。
- **GPU へ送る**: 描く物（先頭から 64 個）の箱・三角形・頂点・材質を、全部の物でまとめたバッファーに入れる。前と同じ物は送り直さない（頂点・材質・箱の版を比べる。同じ場面を 2 つの視点で描くときも、送るのは 1 回）。同じメッシュを複数の物で使うときは中身を 1 回だけ送り、物ごとの置き方（ワールドの行列）は GPU で掛ける。
- **テクスチャ**: 全部を 256 × 256 に縮めて、1 つのテクスチャの配列に並べる（Direct3D 11 のシェーダーは、数の決まっていないテクスチャを選んで読めないため）。縮める割合に合った縮小版を読んで縮め、配列にも縮小版を作る。使うメッシュが無くなった枚は使い回し、足りなければ倍の枚数で作り直す。
- **光線をたどる（映像効果の段。画面の中の反射と同じ段）**: 画面の中で見つからなかった分（見つかった割合の残り）を、同じ光線（面から少し浮かせた所から、探す距離まで）でたどる。物ごとに、ワールドで囲む箱に当たるかを見てから、光線をモデルの座標へ移し、光線が先に入る子の箱から順にたどる（後回しの箱は 40 段まで覚え、戻るときは、今いちばん近い当たりより奥の箱は飛ばす。1 本の光線で調べる箱は 4096 まで）。
- **通り抜ける所**（モデルを描くときに見えない所）: 両面でない材質の裏の面、不透明度が 0.5 より小さい所（テクスチャの透明な所を含む。透明な所のあるテクスチャだけ、当たった所の透明度を読む）。材質モーフで消した物は映らない。
- **当たった所の色**（簡単な計算）: トゥーンの材質は「(拡散色 × 照明の色 + 環境色) × テクスチャ × トゥーン（光の当たり方で読む）」。PBR の材質は、拡散（照明と、空・地面の 2 色の環境光）と、周りの映り込みのおおよその明るさ。どちらも発光を足す。影・スフィア・反射光・足す照明・輪郭線・環境の画像は無い。これに映り込みの強さを掛ける。
- **テクスチャの細かさ**: 光線の太さ（画素 1 つ分の広がり × 面までの距離と映ってから進んだ距離の合計。粗いほど太くする）を、当たった三角形のテクスチャの細かさで画素の数に直し、合った縮小版を読む（遠くの映り込みのちらつきを防ぐ）。
- **画面の中の反射との組み合わせ**: 画面の中で見つかった所は、そちらを使う（影・輪郭線まで含めた、実際に描いた色のため）。見つからない分だけをレイトレーシングの色にする。カメラの方へ戻る光線は、画面の中では弱めるが、レイトレーシングではそのまま映す。探す距離の終わりの近くは、なめらかに弱める。

### 描画エンジン（API 0.24）

- `TT_POST_RAYTRACED_REFLECTIONS` を足した（`TT_POST_SSR` と一緒に使う。それだけでは何もしない。構造体の大きさは変わらない）。
- `RayTracing.h/.cpp`（`RayBvh` = メッシュごとの箱の入れ子、`RayScene` = 1 枚の描画で光線を当てる物。エンジンに 1 つで、全部のビューで使い回す）、`RayTrace.hlsli`（光線をたどる・当たった所の色）、`RayTextureCopyPS.hlsl`（テクスチャを縮めて配列へ写す）を足した。メッシュに、番号と頂点・材質の版を足した。テクスチャに「透明な所があるか」を足した。
- GPU を作り直したときは手放して、次に使うときに作り直す。

### 確かめたこと・まだのこと

- テスト:

  - Editor: 初期値は OFF、プロジェクトの保存と読み込み
- 画面（Release。実物のモデルと、40 × 40 の床を拡張材質で PBR の滑らかな金属にしたもの。カメラを床の近くで下へ向け、モデルは足首から下だけが画面に入るようにした）:
  - 画面の中の反射だけでは、床に映るのは画面に入っている足首まで。レイトレーシングを使うと、画面の外にある脚・水着・手まで逆さに映る（画面の中の反射とのつなぎ目は目立たない）。プレビュー（カメラ視点・自由視点）でも頭まで映る。

- まだのこと: 当たった所の影・スフィア・反射光・足す照明・輪郭線・環境の画像、粗い材質のぼけ（光線 1 本だけ）、半透明の材質の重なり（0.5 で通り抜けるかを決めるだけ）、床（格子）と確認用の立方体には当たらない、65 個目からの物には当たらない、頂点の多いモデルで箱を作る時間と作り直す回数を測る、光線をたどる処理を速くする工夫、レイトレーシングでの影・環境光の遮り。

## 2. C# と C++ のつなぎ方（確定・Phase 0）

指示書の未決定事項「ネイティブ Interop の具体方式と ABI・所有権ルール」への答え。公開する関数は [`tt_engine.h`](../src/3DTheater.Engine.Native/include/tt_engine.h) だけ。

- **方式:** C の関数として公開し、C# は `LibraryImport`（P/Invoke）で呼ぶ。C++ のクラスや例外は境界を越えさせない。
- **呼び出し規約・文字:** `__cdecl`、文字列は UTF-16（`wchar_t`）。
- **版の確認:** `tt_get_api_version()` の大きな版が違う DLL とは組まない（C# 側が起動時に確認）。
- **構造体:** 先頭に `struct_size` を置き、C# と C++ で大きさが食い違ったら `TT_E_INVALID_ARG` にする。
- **結果の返し方:** 0 以上は成功（`TT_OK`、`TT_S_NOT_READY`）、負の値は失敗。失敗の説明は `tt_get_last_error_message()` で、失敗した呼び出しと同じスレッドから取り出す。C# 側では `NativeEngineException` に変換する。
- **所有と破棄の順番:** ビュー → エンジンの順に破棄する。ビューが残っているとエンジンの破棄は `TT_E_INVALID_STATE` で断る。
- **スレッド:** エンジンとビューは作ったスレッドからだけ呼べる。他のスレッドからは `TT_E_WRONG_THREAD`。
- **ファイナライザーは使わない:** GPU とウィンドウの資源は作ったスレッドでしか安全に解放できないため。`Dispose` を必ず呼ぶ。
- **ログ:** C++ 側のログはコールバックで C# へ渡し、アプリのログファイルにまとめる。コールバックはどのスレッドから来てもよいように受ける。

## 3. WPF への 3D の埋め込み方式（比較済み・Phase 1 開始時に確定）

指示書の未決定事項「WPF 上の D3D ビュー埋め込み方式」。Phase 0 では 2 つの方式を同じ画面に並べて比べた。

- **方式 A（HwndHost）:** ネイティブの子ウィンドウを WPF に埋め込み、そこへスワップチェーンで直接表示する。
- **方式 B（D3DImage）:** Direct3D 11 で画面外のテクスチャに描き、Direct3D 9Ex と共有して WPF の `D3DImage` として表示する。

### 測った結果（2026-11-04、RTX 4060 Ti、拡大率 100%、Windows 11）

| 項目 | 方式 A | 方式 B |
|---|---|---|
| 1 枚あたりの UI スレッドの時間 | 約 0.06 ms | 約 0.8〜1.0 ms（GPU の完了待ちを含む） |
| WPF の部品を 3D の上に重ねる | **できない**（子ウィンドウの下に隠れる） | できる |
| ソフトウェア描画（WARP） | 動く | 動かない（共有できない。理由を画面に表示） |
| ウィンドウの大きさ変更への追従 | 追従する | 追従する |
| 終了処理 | 固まらず終了（終了コード 0） | 同左 |

方式 A は、最初の作りでは表示待ちのため 1 枚に約 11 ms、UI スレッドが止まっていた。表示完了の合図を待てるスワップチェーン（`FRAME_LATENCY_WAITABLE_OBJECT`）にし、準備ができていないときは待たずに次の機会に描くようにして解消した。

### まだ測っていないこと

入力の遅れ、4 画面同時の負荷、拡大率の変更・複数モニター間の移動、ドッキングでのタブ切替・フローティング、リモートデスクトップ、GPU が 2 つあるノート PC。

### 推奨（Phase 1 の開始時に確定する）

**方式 B（D3DImage）を本採用し、方式 A は比較用に残す**ことを推す。理由:

1. 参考画像では、各ビューの上に「上 (Top)」などの見出しとボタンが 3D に重ねて置かれている。方式 A ではこれを WPF で作れない。
2. 指示書のドッキングには「自動非表示」がある。自動非表示のパネルは中央の領域の上に滑り出てくるため、方式 A では 3D の下に隠れてしまう。
3. 方式 B なら、中ボタンドラッグなどのマウス操作も普通の WPF 部品として受け取れる。方式 A は子ウィンドウに入力が届くため、別に橋渡しが要る。

方式 B の弱点と対策の案:

- GPU の完了待ちが UI スレッドに乗る。ビューが増えたら、全部描いてから 1 回だけ待つようにまとめる。
- 画面につながっていない GPU（ノート PC の高性能 GPU など）や WARP では共有できない。その場合は方式 A に切り替える逃げ道として、方式 A のコードを残す。

## 4. 描画ループ（仮・Phase 0）

- WPF の画面更新（`CompositionTarget.Rendering`）に合わせて、UI スレッドで描く。
- アニメーションが止まっていて描き直しも要らないときは、購読をやめて GPU と CPU を休ませる（「編集時は軽く」）。
- **見直し予定:** 指示書は「レンダリングスレッドと UI スレッドを適切に分離」としている。モデル描画で重くなる Phase 2 までに、描画専用スレッドへの分離を検討する。

---

## 5. 座標系（仮・Phase 0）

- Phase 0 の確認用の場面は、MMD と同じ **左手系・Y 軸が上**、カメラは −Z 側から +Z 方向を見る形で描いている。
- **未確定:** 単位（MMD の 1 単位 = 約 8 cm と言われる）、各ファイル形式からの変換方針、「右側面」がモデルの右半身か、Blender と同じく画面右から見る向きか。指示書 2.4 と 2.5 で食い違っているため、Phase 1 で固定視点を作る前に決める。

## 6. ログ（確定・Phase 0）

- 置き場所: `%LOCALAPPDATA%\3DTheater\Logs\3DTheater_年月日.log`（UTF-8、14 日より古いものは起動時に消す）
- 異常終了でも直前まで残るよう、書くたびにファイルへ出す。毎フレームの出力はしない。
- 起動時に版、.NET、OS、GPU、機能レベル、拡大率を記録する。
- メニュー「ヘルプ → ログフォルダーを開く」から開ける。

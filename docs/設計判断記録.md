## 1. 開発環境とソリューション構成（確定・Phase 0、Phase 1 で追加）

| 項目 | 決め | 理由 |

| C++ | C++20、Visual Studio 2026（ツールセット v145）、Windows SDK 10.0.26100 | 開発機に入っている最新の組み合わせ |

## 2. C# と C++ のつなぎ方（確定・Phase 0、Phase 1 で API 0.2）

指示書の未決定事項「ネイティブ Interop の具体方式と ABI・所有権ルール」への答え。公開する関数は [`tt_engine.h`](../src/3DTheater.Engine.Native/include/tt_engine.h) だけ。

- **方式:** C の関数として公開し、C# は `LibraryImport`（P/Invoke）で呼ぶ。C++ のクラスや例外は境界を越えさせない。
- **呼び出し規約・文字:** `__cdecl`、文字列は UTF-16（`wchar_t`）。
- **版の確認:** `tt_get_api_version()` の大きな版が違う DLL とは組まない（C# 側が起動時に確認）。Phase 1 で 0.2 に上げた（描画の条件を C# から渡すようにしたため）。
- **構造体:** 先頭に `struct_size` を置き、C# と C++ で大きさが食い違ったら `TT_E_INVALID_ARG` にする。
- **行列:** 「行ベクトル × 行列」の並びの 16 個の float。System.Numerics と DirectXMath がどちらもこの並びなので、そのまま渡せる。
- **結果の返し方:** 0 以上は成功（`TT_OK`、`TT_S_NOT_READY`）、負の値は失敗。失敗の説明は `tt_get_last_error_message()` で、失敗した呼び出しと同じスレッドから取り出す。C# 側では `NativeEngineException` に変換する。「この環境では使えない（`TT_E_NOT_SUPPORTED`）」は呼び出し側が別の方法へ切り替える前提なので、ログは警告にとどめる。
- **所有と破棄の順番:** ビュー → エンジンの順に破棄する。ビューが残っているとエンジンの破棄は `TT_E_INVALID_STATE` で断る。
- **スレッド:** エンジンとビューは作ったスレッドからだけ呼べる。他のスレッドからは `TT_E_WRONG_THREAD`。
- **ファイナライザーは使わない:** GPU とウィンドウの資源は作ったスレッドでしか安全に解放できないため。`Dispose` を必ず呼ぶ。
- **ログ:** C++ 側のログはコールバックで C# へ渡し、アプリのログファイルにまとめる。
- **描く内容:** エンジンはシーンを持たない。視点の行列と「何を表示するか」を毎回 C# から渡す（`TtFrameParams`）。シーンの状態を 1 か所（C# 側）に保つため。

## 3. WPF への 3D の埋め込み方式（確定・2026-11-04）

指示書の未決定事項「WPF 上の D3D ビュー埋め込み方式」。Phase 0 で 2 方式を並べて比べ、Phase 1 の開始時に**方式 B（D3DImage）**を本採用した（利用者の了承済み）。

- **方式 A（HwndHost）:** ネイティブの子ウィンドウを WPF に埋め込み、そこへスワップチェーンで直接表示する。
- **方式 B（D3DImage）:** Direct3D 11 で画面外のテクスチャに描き、Direct3D 9Ex と共有して WPF の `D3DImage` として表示する。

### Phase 0 で測った結果（2026-11-04、RTX 4060 Ti、拡大率 100%、Windows 11）

| 項目 | 方式 A | 方式 B |
|---|---|---|
| 1 枚あたりの UI スレッドの時間 | 約 0.06 ms | 約 0.8〜1.0 ms（GPU の完了待ちを含む） |
| WPF の部品を 3D の上に重ねる | **できない**（子ウィンドウの下に隠れる） | できる |
| ソフトウェア描画（WARP） | 動く | 共有はできない（下の予備の方式で動かす） |

### 方式 B を選んだ理由

1. 参考画像では、各ビューの上に「上 (Top)」などの見出しとボタンが 3D に重ねて置かれている。方式 A ではこれを WPF で作れない。
2. 指示書のドッキングには「自動非表示」がある。自動非表示のパネルは中央の領域の上に滑り出てくるため、方式 A では 3D の下に隠れてしまう。
3. マウス操作を普通の WPF 部品として受け取れる。方式 A は子ウィンドウに入力が届くため、別に橋渡しが要る。

### 方式 B の弱点への対策（Phase 1 で実装）

- **GPU の完了待ち:** 区画ごとに待たず、「全区画の描画を頼む → 1 回だけ待つ → 全区画を表示に反映」の 3 段階にした（`tt_engine_wait_for_gpu`）。
- **共有できない環境**（WARP、画面につながっていない GPU など）: 描いた絵を読み出して `WriteableBitmap` で表示する**予備の方式**に自動で切り替える。指示書は「毎フレームの不要な GPU→CPU 読み戻し」を禁じているが、これは共有できない環境に限った必要な読み戻しとして扱う。状態表示に「読み出し方式」と出る。
- 方式 A のネイティブ側（子ウィンドウへの描画）はテスト付きで残している。WPF 側の部品（HwndHost）は Phase 1 で外した（Git の履歴に残っている）。

### まだ測っていないこと

入力の遅れ、拡大率の変更・複数モニター間の移動、リモートデスクトップ、GPU が 2 つあるノート PC。

## 4. 描画ループ（仮・Phase 1）

- WPF の画面更新（`CompositionTarget.Rendering`）に合わせて、UI スレッドで描く。
- 変化のあった区画だけを描く（シーンの値・選択・再生位置が変わると全区画、視点や大きさが変わるとその区画だけ）。
- 隠れている区画（裏のタブ、最大化で隠れた区画、1/2 画面で使わない区画）は描かず、GPU の資源も作らない。
- 何も変わらず再生もしていないときは購読をやめて GPU と CPU を休ませる（「編集時は軽く」）。
- **決定（Phase 2 の 9 段階目）:** 指示書は「レンダリングスレッドと UI スレッドを適切に分離」としている。実物のモデルで測った結果、今は UI スレッドで描くままにした（理由と見直す目安は 15 章）。

## 5. 座標系と視点（確定・2026-11-04、単位などは仮）

- 座標は MMD と同じ**左手系・Y 軸が上**。モデルの前は −Z 側。
- 回転は度で、X = 上下の向き（正で見下ろす）、Y = 左右の向き、Z = 傾き。Z → X → Y の順に回す。
- **「右側面」は Blender と同じ向き**（画面の右側 = +X 側から見る。こちらを向いたモデルでは左半身が映る）。指示書 2.4 の「モデル基準」と 2.5 の「Blender 準拠のショートカット」が食い違っていたため、利用者に確認して決めた。

| 視点 | ショートカット | 見る向き | 画面の右 | 画面の上 |
|---|---|---|---|---|
| 正面 | Num1 | −Z 側から +Z へ | +X | +Y |
| 背面 | Ctrl+Num1 | +Z 側から −Z へ | −X | +Y |
| 右側面 | Num3 | +X 側から −X へ | +Z | +Y |
| 左側面 | Ctrl+Num3 | −X 側から +X へ | −Z | +Y |
| 上面 | Num7 | 真上から | +X | +Z |
| 下面 | Ctrl+Num7 | 真下から | +X | −Z |

- 固定視点は平行投影で始まる。中ボタンで回すと自由視点（透視投影）へ移る。平行移動とズームでは固定視点のまま（指示書 2.5）。
- カメラ視点では、どの操作でもカメラの位置から自由視点へ移る（シーンのカメラそのものは動かさない）。
- 固定視点では、格子を画面に平行な面（正面・背面 = XY、側面 = YZ、上下 = XZ）に描き、その面の 2 本の軸に色を付ける。
  - 格子と軸は、固定視点では**いちばん奥**に描く（奥行きを比べも書きもしない。格子の面はモデルを貫くので、奥行きどおりだとモデルの上に線が出るため。2026-11-10、利用者の指摘で変えた）。自由視点・カメラ視点では床として奥行きどおりに描く。描画エンジンの `TT_FRAME_GRID_BEHIND`（API 0.8）。
- **未確定:** 単位（MMD の 1 単位 = 約 8 cm と言われる）、各ファイル形式からの変換方針。Phase 2 の PMX 読み込みで決める。

## 6. 画面の作り（確定・Phase 1）

### ドッキング部品: Dirkster.AvalonDock 4.74.1（Ms-PL）

- 候補のうち、無料で Visual Studio 型の操作（タブ化・フローティング・自動非表示・複数モニター）がそろい、.NET 10 向けの版がある。
- 最新は 5.0.1（2026-10 公開）だが、作りを大きく変えた直後の版で、レイアウトの保存方法も変わっていたため見送った。4.x の最新 4.74.1（2026-04 公開、.NET 10 向けあり）を使う。5.x は落ち着いたら検討する。
- 配色は付属の `Vs2013DarkTheme`。

### 標準部品の配色: WPF の Fluent テーマ（`ThemeMode="Dark"`）

- 入力欄・メニュー・スクロールバーなどの暗色化を自前で書かずに済む。.NET 10 では警告なしで使えた。
- ただしタイトルバーの一番上のメニュー項目は、Fluent の見た目だと文字が上下につぶれて表示されたため、その段だけ自前の見た目（`TitleMenuItemStyle`）にした。開いた中身は Fluent のまま。
- `TextBox` を継いだ部品（数値入力欄）には Fluent の見た目が自動では付かないので、`Theme.xaml` で明示的に当てている。

### タイトルバー（指示書 2.2）

- `WindowChrome` で標準のタイトルバーを消し、アイコン・メニュー・最小化/最大化/閉じるを自前で並べた。空いた所はドラッグで移動できる。
- Windows 11 のスナップレイアウト（最大化ボタンにマウスを乗せると出る配置の候補）を残すため、最大化ボタンの上では OS に「最大化ボタン」と答える。WPF の `WindowChrome` が先に答えてしまうので、ウィンドウをサブクラス化して WPF より手前で受け取っている（`TitleBarHelper`）。
- 最大化すると枠の分だけ画面の外にはみ出すので、その分だけ中身を内側に寄せる。

### レイアウトの保存と復元（指示書 2.3・8 章）

- 置き場所: `%APPDATA%\3DTheater\UserSettings\`（`layout.xml` = ドッキングの並び、`settings.json` = プレビューの分け方・視点とウィンドウの位置）。プロジェクトとは別。
- 保存は一時ファイルに書いてから置き換える（途中で止まっても壊れない）。
- 保存したレイアウトに知らないパネル（無効になったプラグインのパネルなど）があれば、そのパネルだけ外して起動する（実際に差し込んで確認済み）。読めないときは初期配置で起動する。
- `settings.json` の形式の版（`Version`）が合わなければ読まずに初期状態にする。

## 7. PMX の読み込み（確定・Phase 2 の 1 段階目）

指示書 4.1〜4.4 のうち「読み込み」と「読み込みレポート」まで。表示・変形・物理は次の段階以降。

### 読むもの

- PMX 2.0 のすべての要素（頂点・面・テクスチャ・材質・ボーン・IK・モーフ・表示枠・剛体・ジョイント）と、PMX 2.1 の QDEF・フリップ／インパルスモーフ・2.1 のジョイントの種類・材質の頂点色／点／線の指定。
- 名前（日本語・英語）、コメント、材質のメモ、番号の大きさ・文字コードなど、元ファイルの情報は捨てずに持つ（指示書 4.1・4.4）。
- 座標は PMX も 3D Theater も左手系・Y が上なので変換しない。角度はラジアンのまま。
- 番号の読み方: 頂点の番号は 1・2 バイトのとき符号なし（0〜255、0〜65535）、それ以外の番号は符号付き（-1 =「なし」）。
- 古い書き出し器で表示枠から後ろが無いファイルは、無い部分を 0 個として読む（情報としてレポートに載せる）。
- PMX 2.1 のソフトボディは中身を読まず、数だけ数えて「未対応」と知らせる。
- PMD（古い形式）は「後日対応」と理由を出して読まない。

### 壊れたファイルへの備え

- 数の欄が残りのバイト数に収まらなければ、大きな配列を確保する前に止める（壊れたファイルで固まったりメモリを使い果たしたりしない）。
- 読み途中で終わったら、どの部分の何バイト目かを添えて「途中で切れているか壊れている可能性」と伝える。
- 形式の誤りは例外を外へ出さず、エラー入りの読み込みレポートとして返す。

### 読み込みレポート

- 区分: 形式・未対応・参照の誤り・素材が見つからない・補足。重さ: エラー（読めない）・注意（読めたが元と違う可能性）・情報。
- 範囲外の参照（存在しないボーン・頂点・テクスチャなど）はデータを直さずに知らせる。使う側（描画・変形）で無視する前提。
- 同じ種類の問題はまとめて 1 行（件数と最初の 3 つの例）にする。
- テクスチャはモデルのファイルの場所からの相対パスで探す（区切りの `\` と `/` の両方を受け付ける）。材質が使っていないテクスチャは調べない。`toon01.bmp`〜`toon10.bmp` が手元に無いときは、MMD 付属の共有トゥーンとして扱う（情報）。
- 同じ名前のボーン・モーフは、モーションを名前で当てはめるときに区別できないので注意として出す。
- 「読み込めた」ことと「MMD と同じ見た目・動きになる」ことは別に確かめる（指示書 4.1）。レポートの窓にもそう書いた。

### 画面からの使い方

- 「ファイル → モデルを読み込む」「モデル → PMX を読み込む」（Ctrl+I）、ウィンドウへのドラッグ、起動時の引数（「プログラムから開く」）。
- 読み込みは別のスレッドで行い、画面を止めない。読めたモデルはシーンの「モデル」に加わり、プロパティで形式・数・コメント・レポートを見られる。
- ファイルの中身（`PmxDocument`）はアプリ側（`EditorContext.Models`）に持ち、シーンの項目（`ModelNode`）には場所と概要だけを持つ。プロジェクトにはモデルの場所だけを保存する（12 章）。

### 測った速さ（2026-11-06、開発機）

合成した頂点 30 万・面 50 万・ボーン 200・頂点モーフ 100 個（各 2,000 頂点）、26 MB のデータで、点検を含めて 1 回 約 74 ms（ファイルの読み出し時間は含まない）。

### テストの方針

- 実在のモデルは使わない（権利の確認が要らないよう、テストの中でデータを組み立てる）。
- テスト用の書き出し器（`PmxTestWriter`）で全要素入りのデータを作って読み戻すほか、仕様の並びどおりに手でバイト列を組んだテストも置き、書き出し器と読み込み側が同じ思い込みで間違えていないことを確かめる。
- 実物のモデルでの確認は、利用条件の確かな検証用モデルを用意してから行う（まだしていない）。

## 8. モデルの表示（確定・Phase 2 の 2 段階目）

読み込んだ PMX を全プレビューに描く。ボーンとモーフでの変形は 9 章、トゥーン・スフィア・輪郭線・影は Phase 4。

### 描画エンジンの公開関数（API 0.3）

- `tt_texture_create` / `tt_mesh_create` でテクスチャとメッシュ（頂点・面・材質）を GPU に載せる。描く内容は毎回 `TtFrameParams.items`（メッシュと置き方の一覧）で渡す。エンジンはシーンを持たない決まりはそのまま（2 章）。
- メッシュは作るときに面の頂点番号と材質の範囲を確かめ、範囲外なら断る（GPU に壊れたデータを渡さない）。
- メッシュはテクスチャの中身を参照し続けるので、テクスチャの入れ物は作った直後に破棄してよい。
- ビュー・テクスチャ・メッシュが残っている間はエンジンを破棄できない。アプリは終了時に「プレビュー → モデル → エンジン」の順に片付ける。

### 描き方（MMD に合わせた点）

| 点 | 決め | 理由 |
|---|---|---|
| 表裏 | 時計回りの面が表。両面描画の材質以外は裏面を描かない | MMD（Direct3D 9 の既定）と同じ |
| 描く順 | 材質の並び順のまま、半透明は重ね合わせ（アルファブレンド）、深度は書く | MMD と同じ。並べ替えると作者の意図と変わる |
| 色の扱い | テクスチャも画面も sRGB の補正をしない | MMD は補正しないため、同じ見た目に近づける |
| 照明 | MMD の初期値（向き (-0.5, -1, 0.5)、明るさ 154/255）に固定 | 照明の項目の反映は Phase 4 |
| 陰影 | `(環境色 + 拡散色 × 0.6)` × テクスチャ × 明るさ（0.62〜1.0、光の当たり方で変える） | 形が分かる程度の簡単なもの。トゥーンは Phase 4 |
| テクスチャ | 縮小版（ミップマップ）を作り、繰り返しで貼る | 遠くでちらつかないように |

### テクスチャの読み込み

- PNG・BMP・JPG・GIF・TIFF・DDS は Windows 標準の画像機能（WIC）で、TGA は自前（`TgaDecoder`：フルカラー 16/24/32 ビット・グレースケール・パレット、それぞれの RLE 圧縮）で読む。スフィア（.spa/.sph）は中身が BMP なので WIC で読める。
- 拡張子と中身が違うときは、最後に TGA として試す。読めなければ読み込みレポートに「読めなかった」と載せ、テクスチャなしで描く。
- 今は材質の基本のテクスチャだけを読む（スフィア・トゥーンは Phase 4 で使い始める）。

### 壊れたデータの扱い（描く側）

- 存在しない頂点を指す面は、3 点とも 0 番にして大きさ 0（描かれない）にする。材質の範囲は面の数で切る。どちらも読み込みレポートの「表示しません」と対応する。元の `PmxDocument` は書き換えない。

### 選択と画面に収める

- クリックでの選択は、モデルの三角形（今の姿勢の頂点。9 章）に視線を当てて調べる。先に囲む箱で外れを除く。いちばん手前に当たったものを選ぶ。
- 選択中のモデルは、囲む箱の線を強調色で描く。
- **画面に収めるとき・選択の枠・ボーンの印の大きさには「見た目の箱」を使う**（`DisplayBounds`）。MMD のモデルには、使わない部品（眼鏡など）を足元のずっと下に隠しておく作りがあり、すべての頂点を囲むと箱が大きくなりすぎて、モデルが見えないほど引いてしまうため（実物のモデルで、高さ −983 に眼鏡の頂点 1,287 個がある例で起きた）。
  - 決め方: 面に使われている頂点の真ん中（座標ごとの中央の値）からの距離で、8 割の頂点が入る距離を目安にし、その 4 倍より遠い頂点を除く。隠した部品が頂点の 2 割より少なければ除ける。体から伸びる長い物（剣など）は、ほかから離れていないので残る。
  - 除いた頂点があれば、読み込みレポートに情報として載せる。クリックでの選択（当たり判定）は、これまでどおりすべての頂点で調べる。
- 最初のモデルを読み込んだときは、全プレビューの区画（カメラ視点を除く）をそのモデルに合わせる。MMD のモデル（高さ約 20）は確認用の立方体（1 辺 1）よりずっと大きいため。シーンのカメラは動かさない（シーンのデータを勝手に変えない）。
- 床の格子は ±50（1 目盛り = 1、太線は 5 ごと）に広げた。

### 確かめたこと・まだのこと

- 合成した人形（高さ約 20、TGA と BMP のテクスチャ、半透明で両面描画のマント）で、全区画の表示・選択の箱・自動で合わせる動き・予備の方式（読み出し）での表示を確かめた。
- **実物の PMX ではまだ確かめていない。** 面の表裏の向きは MMD の決まりに合わせたが、実物で裏表が逆に見える材質がないかは、検証用モデルで確かめる必要がある。

## 9. ボーンとモーフ（確定・Phase 2 の 3 段階目）

指示書 4.2・4.3 の「ボーン・モーフ・IK は適切な評価順で」「計算処理をユニットテスト可能に」に合わせ、計算は `3DTheater.Animation` に分けた（画面にもエンジンにも依存しない）。

### 計算の順番（`PoseEvaluator`）

1. モーフの値を求める。グループモーフは中のモーフに「値 × 割合」を足す（グループの中のグループと自分自身は MMD と同じく効かせない）。
2. ボーンモーフの回転・移動を、そのボーンの回転・移動に重ねる。
3. 各ボーンの回転・移動を決める。軸固定のボーンは、その軸まわりの成分だけを残す。親から子へ置き方を積み上げる。
4. **変形の順番（物理後かどうか → 変形階層 → 番号）**に、ボーンごとに「付与 → その下の置き方を更新 → IK を解く」を行う。全ボーンを一度に処理しない。
5. 頂点モーフ・UV モーフ・材質モーフを求める。材質モーフは乗算をすべて掛けてから、加算をすべて足す（並び順によらない）。

| 点 | 決め | 理由・出どころ |
|---|---|---|
| 付与（回転・移動を受け継ぐ） | 元のボーンの回転を「重み」倍する（負の重みも可）。元のボーンも付与を受けていれば、その付与の分を受け継ぐ。元が IK で動くボーンなら IK の回転も含める | MMD の結果に合わせる実装として広く使われている saba（MIT）の考え方に合わせた。足 D などが IK に従う |
| IK | 繰り返し法（CCD）。1 回に回す角度は IK の「単位角」まで。前より遠ざかったら、いちばん近かった状態に戻して終える | PMX の項目（繰り返し回数・単位角・角度制限）をそのまま使う |
| 1 軸だけ制限のあるリンク（ひざ） | その軸まわりの角度だけを動かす。最初の 1 回で制限の外へ向かうなら逆向きに曲げる | 足がまっすぐなときにひざが逆に曲がったり止まったりしないように（saba と同じ方法） |
| 複数の軸に制限のあるリンク | X・Y・Z の角度に分けて制限し、前回の角度に近い分け方を選ぶ | 角度が飛ばないように |
| IK が最初から届いているとき | 解かない | 初期の姿勢で、ひざが勝手に少し曲がらないように |
| 物理後のボーン | 今は続けて計算する | 物理演算は Phase 3 |
| PMX 2.1 の追加 UV・フリップ・インパルスモーフ | 今は効かせない（一覧には「今は効きません」と出す） | 指示書 4.3「段階対応」 |

### 頂点の変形（スキニング、`Skinner`）

- BDEF1・BDEF2・BDEF4 は重みで混ぜた行列で動かす。重みの合計が 1 でないモデルや、ボーンが欠けた頂点は、残りのボーンに割り振る。
- SDEF は 2 本のボーンの回転を球面で補間し、回転の中心（C）まわりに回す。曲げても関節からの距離が変わらない（テストで確かめている）。ボーンが欠けた SDEF は BDEF2 として扱う。QDEF（PMX 2.1）は今は BDEF4 として扱う。
- **変形は CPU で行う。** 選択の当たり判定（今の姿勢の形に当てる）とテストに同じ計算を使えるため。頂点が多いときは複数の CPU に分ける。
  - 測った速さ（2026-11-06、開発機・24 スレッド、Release）: 頂点 15 万・ボーン 500 で、ボーンの計算 約 2.3 ms、頂点の変形 約 3.3 ms。
  - 再生やモーションで重くなったら、GPU での変形（シェーダーでのスキニング）を測ってから検討する。
- 変形した頂点は `tt_mesh_update_vertices`、材質モーフの結果は `tt_mesh_update_materials` で描画エンジンへ送る（API 0.4）。値を変えたモデルだけを、次の描画の直前に 1 回だけ計算し直す（`PoseUpdater`）。

### シーンでの持ち方と操作

- ボーンとモーフはシーンの項目（`BoneNode` / `MorphNode`）としてモデルの下に置く。名前・親子関係・順番はモデルのファイルのままで変えない（指示書 2.7）。
- シーン一覧では、ボーンを PMX の表示枠（MMD のボーン一覧の分け方）ごとに、モーフを種類（目・まゆ・口・その他）ごとにまとめる。表示枠に無いボーンは「表示枠にないボーン」にまとめる。数が多いので、シーン一覧とタイムラインでは最初は閉じておく。
- ボーンの値は、初期の位置からの移動と、回転（度。シーンの項目と同じく Z → X → Y の順）で、どちらも親のボーンから見た向き。プロパティ欄では、移動できないボーンには移動の欄を、回転できないボーンには回転の欄を出さない。
  - 回転は四元数で持ち、プロパティ欄では度で見せる（10 章。最初は角度で持っていたが、モーションの段階で変えた）。
- モーフの値は 0〜1。プロパティ欄と「モーフ」パネル（分類と名前で絞り込み、つまみで変える）で変えられる。「ポーズを初期化」はボーンとモーフをすべて戻す（ロックした項目は変えない）。
- 値を変えると再生を一時停止する（指示書 3.4）。

### ボーンの表示と選択

- 今操作しているモデル（選んだモデル、または選んだボーン・モーフの持ち主）のボーンだけを、モデルより手前に線で描く。プレビューごとに切り替えられ、書き出しには映らない（指示書 5 章）。
- 色: 回転だけ = 水色、移動もできる = 緑、IK = 橙、動かせない = 灰、選択中 = 黄。長さの無いボーンは小さな十字で描く。MMD で非表示のボーンと、シーン一覧で隠したボーンは描かない。
- プレビューでボーンの線の 6 ピクセル以内をクリックすると、モデルより先にそのボーンを選ぶ。

### 確かめたこと・まだのこと

- 合成した人形（ボーン 27・IK 2・付与・軸固定・SDEF と BDEF2 の腕・頂点/グループ/ボーン/UV/材質モーフ・表示枠）で、ひじの曲げ・足 IK・付与・モーフを画面で確かめた（GPU 共有方式と読み出し方式の両方）。
- **実物の PMX ではまだ確かめていない。** MMD と同じポーズになるかは、検証用モデルと MMD で同じ値を入れて見比べる必要がある。
- プレビューでのボーンのクリック選択は、計算をテストで確かめ、利用者が実際のマウスでも確かめた（2026-11-07）。

## 10. モーションとキーフレーム（確定・Phase 2 の 4 段階目）

### 読み込めるもの

| 形式 | 読むもの | 今は使わないもの |
|---|---|---|
| VMD（モーション） | ボーンのキー（移動・回転・4 本の補間曲線）、モーフのキー、カメラのキー（14 章） | 照明・セルフ影のキー（読んで数を知らせる）、表示と IK の切り替えのキー |
| VPD（ポーズ） | ボーンの移動・回転、モーフの値 | ― |

- 古い VMD（モーフの後ろの区切りが無い・モデル名が 10 バイトの版 1）も読む。後ろの区切りが途中で切れているときは、注意を出してそこまでを使う。
- 元のファイルは読むだけで書き換えない。読み込みレポートは PMX と同じ窓で見せる。
- 書き出し（VMD・VPD）は次の段階。

### 名前の対応

- VMD の名前は Shift-JIS の決まった長さ（ボーン・モーフ 15 バイト、モデル 20 バイト）で、長い名前は途中で切れている。**MMD と同じく、モデルの名前を Shift-JIS にして同じ長さで切ったバイト列で比べる。** 文字列にして比べると、2 バイト文字の途中で切れた名前が合わなくなるため。
- モデルに無いボーン・モーフは、使わずにレポートで知らせる。モーションのボーンの半分以上が合わないときは「別のモデル用かもしれない」と注意にする（少しだけ合わないのは普通なので、情報にとどめる）。

### キーと補間（`Theater3D.Domain`）

- キーはボーン・モーフの項目が持つ（`BoneNode.Keys` / `MorphNode.Keys`）。同じフレームには 1 つだけ。
- 補間は MMD と同じく「前のキーからこのキーまで」の動き方を後ろのキーが持つ。ボーンは移動の X・Y・Z と回転で別々の 3 次ベジェ曲線。直線（線形）はベジェの特別な形として扱い、段階（次のキーまで値を変えない）は別の種類として持つ（指示書 3.1 のステップ・線形・ベジェ）。VMD には段階が無いので、書き出しのときの扱いは書き出しの段階で決める。
- 回転は四元数の球面補間。最初のキーより前は最初のキー、最後のキーより後ろは最後のキーの値を使う。
- **ボーンの回転は四元数で持つように変えた**（9 章の仮の決めを確定）。角度は同じ回転にいくつもの表し方があり、キーの補間がずれるため。プロパティ欄では度で見せ、度で入れた値は四元数に直す。
- VMD は 30 fps で作られている。作品のフレームの速さが違うときは、読み込むときにキーの位置を合わせる（60 fps なら 2 倍）。読み込んだ後にフレームの速さを変えたときは、キーの位置も合わせるか尋ねる（15 章）。
- 読み込んだキーは、同じボーン・モーフ・フレームのキーだけを置き換え、ほかのキーは残す（読み込みそのものは 11 章のとおり元に戻せる）。モーションの最後のキーが終わりのフレームより後ろなら、終わりのフレームを延ばす。

### 再生とキーの登録（`AnimationService`）

- 再生位置が変わると、キーのあるボーン・モーフにそのフレームの値を当てはめる。停止中・再生中・（将来の）書き出しで同じ計算を使う（指示書 3.4）。
- **自動キーは初期値 OFF**（指示書 3.3）。OFF のときに手で値を変えると「未登録の変更」になる。
  - フレームを動かしても、再生しても、その値を保つ（**黙って捨てない**）。
  - タイムラインの上に「未登録の変更 n 件」と出し、「すべて登録」（今のフレームのキーにする）か「破棄」（キーの値、キーが無ければ初期の値に戻す）を選ぶ。シーン一覧では「＊」、タイムラインでは名前を橙色にして示す。
  - 指示書の「破棄・登録・保持の扱いを明示する」は、「保持して状態を表示し、登録か破棄をいつでも選べる」形にした。フレームを動かすたびに確認の窓を出すと、スクラブ（再生位置のドラッグ）の邪魔になるため。
- 「キーを登録」（I キー）は、選んだボーン・モーフを今のフレームのキーにする。モデルやまとまりを選んでいるときは、その中の未登録の変更だけを登録する（動かしていない全ボーンにキーを作らない）。ロックした項目は登録しない。
- 新しいキーの補間は直線。同じフレームにキーがあれば、その補間を引き継ぐ。
- ポーズ（VPD）は今の値として置くので、未登録の変更になる（キーにするかは利用者が決める）。
- 自動キーが ON なら、値を変えたときに今のフレームへキーを登録する。

### タイムライン

- ボーン・モーフの行にキーを◆で描く。まとまり（モデル・表示枠など）の行には、中のキーをまとめて薄く描く。今のフレームのキーは強調色。
- キーの選択・移動・複製・削除・コピーは 11 章。補間曲線の細かい編集はグラフエディター（Phase 3）。

### 確かめたこと・まだのこと

- 合成した人形と確認用のモーション（ひじ・腕・センター・足 IK・まばたき・口・材質モーフ、モデルに無いボーンとモーフ、カメラのキー）で、フレーム移動・再生（30 fps で進む）・補間曲線・未登録の変更の保持と登録・ポーズの読み込みを画面で確かめた。
- **実物の VMD・VPD ではまだ確かめていない。** MMD と同じ動きになるかは、検証用のモデル・モーションで見比べる必要がある。
- 元に戻す/やり直しは 11 章。

## 11. 元に戻す/やり直しとキーの編集（確定・Phase 2 の 5 段階目）

### 元に戻す/やり直し（`UndoService` / `EditService`）

- 画面からのシーンの編集は、すべて `EditService.Change` を通す（プロパティ欄・シーン一覧の名前・表示・ロック・モーフのつまみ・ポーズの初期化・キーの登録と破棄・モーションとポーズの読み込み・キーの編集）。
- 1 つの操作で変わる項目について、**変える前と後の値の写し**（`NodeState`）を残す。元に戻すときは前の写し、やり直すときは後の写しに書き戻す。
  - 操作ごとに「元に戻す処理」を書く方法より、書き漏れが起きにくい。項目の種類が増えても、写しの取り方を足すだけで済む。
  - キーの写しは大きくなることがあるので、キーを変える操作（登録・読み込み・キーの編集、自動キーが ON のときの値の編集）のときだけ写す。
  - 「未登録の変更」の印も写しに入れる。キーの登録を元に戻すと、登録前の「未登録」に戻る。
- 書き戻すときは、キーの当てはめと「手で変えた」判定を止める。書き戻した後に、今のフレームのキーを当てはめ直す（操作したときとフレームが違うことがあるため）。
- 同じ項目の同じ値を 1.5 秒以内に続けて変えたとき（つまみのドラッグ、ホイールでの増減）は 1 つの操作にまとめる（指示書 3.3「ドラッグ 1 回を 1 つの Undo に」）。元に戻した後の操作は、前の操作とまとめない。
- 履歴は 300 個まで。新しい操作をすると、やり直しの履歴は消える。
- 何も変わらなかった操作は積まない。
- 元に戻せないもの: 選択、視点、再生位置・終わりのフレーム。（モデルの読み込みは 14 章、フレームの速さの変更は 15 章で戻せるようにした）
- ショートカット: Ctrl+Z = 元に戻す、Ctrl+Y / Ctrl+Shift+Z = やり直し。文字を入力している欄では、その欄の元に戻すが働く。メニューとツールバーのボタンには、何を戻すかを出す。

### キーの編集（`KeyEditing` / タイムライン）

| 操作 | 動き |
|---|---|
| キーをクリック | そのキーを選ぶ（Ctrl で追加・解除、Shift で追加） |
| 帯の空いている所からドラッグ | 範囲の中のキーを選ぶ |
| 選んだキーをドラッグ | 動かす（Ctrl を押しながらだと複製）。1 回のドラッグが 1 つの操作 |
| キーをダブルクリック | そのキーのフレームへ移動 |
| 帯の空いている所をクリック | キーの選択を外し、そのフレームへ移動 |
| 目盛りをドラッグ | 再生位置を動かす |
| 右クリック | 補間（線形・なめらか・段階）、コピー、貼り付け、削除、そのフレームへ移動 |
| Delete / Ctrl+C / Ctrl+V | 選んだキーを削除 / コピー / 今のフレームに貼り付け |

- これまでは帯の上のドラッグでも再生位置が動いたが、キーの範囲選択に使うため、再生位置のドラッグは目盛りだけにした（帯のクリックでの移動は残した）。
- まとまり（モデル・表示枠など）の行の◆は、中のキーをまとめたもの。選ぶと中のキーすべてを選び、動かすとまとめて動く。
- キーを動かした先に、選んでいないキーがあれば、動かしたキーで置き換える。フレームが 0 より前にならないよう、ずれを抑える。
- 貼り付けは、コピーしたキーのうち最も前のキーが今のフレームに来るように、同じ項目へ貼る（アプリの中だけのコピー）。
- 補間の「なめらか」は、MMD の補間曲線の (64, 0)・(64, 127)。曲線の細かい編集はグラフエディター（Phase 3）で行う。
- ロックした項目のキーは動かさない・消さない・貼らない。

### 確かめたこと・まだのこと

- 元に戻す・やり直し・キーの編集の計算は、テストで確かめた。
- 画面では、値の変更 → Ctrl+Z → Ctrl+Y、キーの登録の取り消し（「未登録」に戻る）、モーションの読み込みの取り消しとやり直し（タイムラインの◆が消えて戻る）を、キーボードで確かめた。
- タイムラインのマウス操作（キーのクリック・範囲選択・ドラッグ・右クリック）は、利用者が実際のマウスで確かめた（2026-11-07）。

## 12. プロジェクトの保存と VMD・VPD の書き出し（確定・Phase 2 の 6 段階目）

### プロジェクトファイル（`.3dtproj`）

- 拡張子は指示書の候補どおり **`.3dtproj`**。中身は **UTF-8 の JSON** で、先頭に形式の名前 `"format": "3DTheater.Project"` と版 `"version": 1` を持つ（指示書 8 章「内部フォーマットはバージョン管理可能に」）。
  - 文字の形式にしたのは、壊れたときに中を見て直せること、版の違いを足しやすいこと、差分が読めることのため。
  - キーの数が多いと大きくなるので、キーは数の並びで短く書き、字下げもしない。ボーンのキーは「フレーム・移動 3・回転 4（四元数）・種類」の 9 個。曲線が直線でなければ 16 個を足す。モーフのキーは 3 個（曲線があれば 7 個）。
  - 新しい版の 3D Theater で保存したファイル（版の数が大きい）は開かずに、新しくするよう知らせる。
- 保存するもの: 再生の設定（フレームの速さ・終わりのフレーム・今のフレーム・ループ）、自動キー、カメラ・照明・確認用の立方体・床の値と表示・ロック、モデル（場所・名前・置き方・表示・ロック・中のまとまりの表示とロック）、ボーン・モーフのキーと今の値。
  - **未登録の変更もそのまま保存し、開いたときに「未登録」の印ごと戻す**（黙って捨てない）。
  - ボーン・モーフは、初期のまま（キーなし・動かしていない・ロックも非表示もなし）なら書かない。
  - カメラ・照明などは名前を変えられるので、名前ではなく役目（`camera`・`light` など）で書く。
- 保存しないもの: 選択、視点、パネルの並べ方（ユーザーの設定として別に保存。指示書 8 章）。
- モデルは**場所だけ**を書き、中身は元のファイルから読み直す（原本は書き換えない。指示書 4.4）。
  - 場所はプロジェクトのフォルダーから見た相対パスで書き、予備として保存したときの絶対パスも書く。開くときは相対パス → 絶対パスの順に探す（指示書 8 章「相対参照を優先」）。ドライブが違うときと、無題のときは絶対パス。
  - ボーン・モーフは番号と名前が合えばそれを、合わなければ名前で探す（モデルのファイルが変わったとき）。見つからないものは知らせる。
- **見つからないモデルは消さない。** 開いたときに見つからない（読めない）モデルは、知らせたうえで設定とキーを覚えておき、保存し直してもそのまま書き戻す。ファイルを戻して開き直せば元に戻る。
- 保存は一時ファイルに書いてから置き換える（指示書 8 章「安全な更新方式」）。

### 新規・開く・保存と、保存していない変更

- 新規（Ctrl+N）・開く（Ctrl+O）・保存（Ctrl+S）・名前を付けて保存（Ctrl+Shift+S）。プロジェクトはウィンドウへのドラッグ・起動時の引数でも開ける。
- 変更があると題名に「＊」を付ける。変更とみなすのは、元に戻せる操作・モデルの読み込み・再生の設定（フレームの速さ・終わりのフレーム・ループ）の変更。
- 閉じる・新規・開くの前に、保存していない変更があれば保存するか尋ねる（はい・いいえ・キャンセル）。
- 新規・開くでは、元に戻す/やり直しの履歴を消す。

### 自動保存と復旧（指示書 8 章）

- 変更があれば **2 分ごとに** `%LOCALAPPDATA%\3DTheater\AutoSave\autosave_<プロセス番号>.3dtproj` に書く（元のプロジェクトの場所も入れる）。保存したとき・新規にしたとき・閉じると決めたとき（保存した／保存しないを選んだ）に消す。
- 起動したときに、もう動いていないアプリの自動保存が残っていれば、開くかどうかを尋ねる（はい = 開く・いいえ = 捨てる・キャンセル = 次に起動したときにまた尋ねる）。開いた作業は保存していない扱い（題名に「＊」）で、保存先は元のプロジェクト。
- 同時に複数のアプリを動かしても、ファイル名にプロセスの番号を入れて互いに上書きしない。

### VMD・VPD の書き出し

- モーション（VMD）: 今操作しているモデルのボーン・モーフのキーを書く。補間の曲線は MMD と同じ 64 バイトの並び（最初の 16 バイトに 4 本の曲線、後ろは 1 バイトずつずらした写し）。
  - 作品のフレームの速さが 30 でなければ、30 fps に直す（重なったキーは注意で知らせる）。
  - **段階の補間は VMD に無いので、1 つ前のフレームに前の値のキーを足して表す。** モーフの曲線も VMD に無いので線形になる（知らせる）。
  - 名前は Shift-JIS にして決まった長さ（15 バイト）で切る（MMD と同じ）。
  - 未登録の変更は書かない（注意で知らせる）。
- ポーズ（VPD）: 今のフレームの、動かしているボーンと値の入ったモーフを書く（MMD と同じ書き方。小数 6 桁）。
- 書き出したモーションを読み込み直すと、曲線も含めて同じキーに戻ることをテストで確かめた。
- 元の情報をできるだけ残す（指示書 4.1）点で、読み込んだ VMD の補間の 64 バイトの後ろの部分（MMD の物理の切り替えなどに使われることがある）は今は残していない。必要になったら残し方を考える。

### 確かめたこと・まだのこと

- 合成した人形とモーションで、名前を付けて保存 → 変更の印 → VMD の書き出し → 閉じるときの確認 → 開き直し（キーと題名が戻る）→ 自動保存からの復旧、を画面で確かめた。
- 2 分ごとの自動保存そのもの（時間が来たときに書くこと）は、画面ではまだ確かめていない（書く中身は保存と同じ処理）。
- **実物のモデルでの保存と開き直しは、まだ確かめていない。**

## 13. ギズモ（確定・Phase 2 の 7 段階目）

指示書 2.6 の「MMD 方式と Blender 方式（XYZ 軸ギズモ）の両方を搭載し、切り替えられる」に合わせた。

### 2 つの方式

| 方式 | 出す取っ手 | 道具の切り替え |
|---|---|---|
| **MMD 方式**（初期設定） | 選んだ物に、移動の矢印と回転の輪を一緒に出す。移動できないボーンには矢印を、回転できないボーンには輪を出さない | 使わない（ツールバーの道具のボタンは押せない） |
| **Blender 方式** | ツールバーで選んだ道具の取っ手だけを出す（移動 = XYZ の矢印、回転 = XYZ の輪、選択 = 何も出さない） | ツールバー、または Q（選択）・W（移動）・E（回転）。キーを押すと Blender 方式に切り替わる |

- 「MMD 方式」は、MMD のボーン操作（選んだボーンに回転の輪と移動の軸が出る）に近づけたもの。MMD と同じ見た目・細かな動きをそのまま再現したものではない。
- 方式・道具・座標は全プレビューで共通で、ユーザーの設定として保存する（指示書 2.6「初期設定は全ビュー共通」、8 章）。プレビューごとに別の方式にする機能はまだ無い。
- 方式を切り替えても、モデルの位置・姿勢・キーは変えない（元に戻すの履歴にも積まない）。

### 操作

- 取っ手を左ボタンでドラッグする。Ctrl を押しながらだとスナップ（移動 0.5・回転 5°）。
- ドラッグ中に右クリックか Esc で取り消して、つかむ前に戻す。
- **ドラッグ 1 回を 1 つの「元に戻す」にする**（`EditService.Begin` で始めて、離したときに 1 つの操作として積む。指示書 3.3）。
- 座標はワールド（シーンの XYZ）とローカル（選んだ物の向き。ボーンなら今の姿勢でのボーンの向き）を切り替えられる。
- 操作の優先順: 左クリックは「ギズモの取っ手 → ボーンの線 → モデル」の順。視点の操作は中ボタンなので、ぶつからない（指示書 2.6）。
- ギズモを出すのは、選んでいる物が 1 つで、ロックされておらず、見えているときだけ。ボーン・モデル・確認用の立方体・カメラ・照明に出せる。

### 計算（`GizmoMath`、テストあり）

- 取っ手の大きさは、画面の上でいつも同じ大きさ（矢印の長さ 90 ピクセル。両方出すときは、矢印の先が輪の外に出るよう輪を少し小さくする）。
- 当たり判定は画面の上で、取っ手の線から 7 ピクセル以内。近さが同じなら矢印を優先する。
- 移動の量は、マウスの視線と軸の線が最も近づく所から求める。軸がこちらを向いているときは、画面に写った軸の向きへの動きで求める。
- 回転の量は、輪の面とマウスの視線の交わりの角度から求める（少しずつ足すので 180° を超えても回せる）。輪を真横から見ているときは、つかんだ所の接線（見えなければ画面に写った軸に直角な向き）への動き 100 ピクセルで 90°。
- ボーンへの直し方: ワールドの動きを、親のボーンの向き（モデルの回転を含む）とモデルの拡大で割り戻して、ボーンの値（親から見た移動・回転）にする。回転は「親の向きの中で見た回転」を今の回転の外側から掛ける。
  - 付与・IK・ボーンモーフが重なったボーンでは、見た目の回転とつかんだ輪の向きが少しずれることがある（値は利用者が入れる回転に掛かるため）。

### 確かめたこと・まだのこと

- 合成した人形で、MMD 方式（回転だけのボーンには輪だけ、移動もできるボーンには矢印と輪）、ローカルの座標（輪がボーンの向きに傾く）、Blender 方式の道具の切り替え（移動できないボーンでは何も出ない）を画面で確かめた。
- マウスでのドラッグは、利用者が実際のマウスで確かめた（2026-11-07）。ドラッグの量の計算と、1 つの操作にまとめること・取り消しは、テストでも確かめている。
- 拡大の取っ手・平面の移動（2 つの軸をまとめて動かす）・画面に平行な回転の輪・数値を打ち込んでのギズモ操作は、まだ無い（数値はプロパティ欄で入れられる）。

## 14. カメラのモーションとモデルを外す操作（確定・Phase 2 の 8 段階目）

### カメラのキー

- シーンのカメラ（`CameraNode`）は今までどおり位置・回転（度）・視野角で置き、**キーは MMD と同じく「注視点・回転・距離・視野角」で持つ**（`CameraKey`）。キーの間はこの形のまま補間する。
  - 位置を直線で補間すると、注視点のまわりを回るカメラが注視点に近づいてしまうため。回転は四元数ではなく角度を成分ごとに直線で動かす（MMD と同じ。1 周を超える回転も表せる）。
  - 補間の曲線は MMD と同じ 6 本（注視点 X・Y・Z、回転、距離、視野角）。段階の補間も使える。
- カメラに「注視点までの距離」（`TargetDistance`）を足した。キーを登録するときの注視点は「位置から見ている向きへこの距離だけ進んだ所」。プロパティ欄で変えられる。MMD と同じく、注視点より奥に置く（負の距離）こともできる。
- **キーの無いカメラを手で動かしても「未登録の変更」にしない**（置くたびに未登録が残らないように）。キーのあるカメラの手の変更は、ボーンと同じく未登録の変更として保つ。自動キーが ON なら、キーが無くても登録する。
- カメラを選んで「キーを登録」（I）でカメラのキーになる。タイムラインのカメラの行にもキーが出て、移動・複製・削除・コピー・補間の切り替えができる。プロジェクトにも保存する。

### VMD のカメラ（`MmdCamera`・`CameraMotion`）

- MMD のカメラの位置 = 注視点 + 回転 × (0, 0, 距離)。距離は負の数で注視点の手前。回転は Z → X → Y の順に掛ける（saba と同じ）。
- **回転の向き（符号）は、シーンのカメラ（X が正なら見下ろす）と X・Y が逆**とした。saba と three.js の MMD の扱いから導いたもので、MMD 本体との見比べはまだ。変換はこの 1 か所にまとめてあり、違っていたらここだけを直せばよい。
- 補間は 24 バイト（6 本 × 各 4 バイト: x1・x2・y1・y2）。すべて 0 のもの（古い書き出し器）は直線とみなす。
- 読み込み: カメラ用のモーション（ボーン・モーフのキーが無く、カメラか照明のキーがある）か、カメラを選んで読み込んだ VMD は、シーンのカメラへ当てはめる（モデルを選んでいなくてよい）。モデル用のモーションのカメラのキーは、モデルには当てはめない（知らせる）。
  - 30 fps 以外の作品では位置を合わせる。そのとき、**元で 1 フレームしか離れていないキー（カメラの切り替え）は段階の補間にする**（60 fps にすると 2 フレームの間に途中の絵が出てしまうため）。
  - パース OFF（平行投影）は今は透視投影で表示する（キーには残して書き戻す）。照明・セルフ影のキーは今は使わない（陰影の描画は Phase 4）。
- 書き出し: モーションメニュー「カメラのモーションを書き出す（VMD）」。モデル名は MMD と同じ「カメラ・照明」。30 fps に直し、段階の補間は 1 つ前のフレームにキーを足して表す。
- 書き出したカメラのモーションを読み込み直すと、曲線・720° の回転も含めて同じキーに戻ることをテストで確かめた。

### モデルを外す・読み込みを元に戻す

- モデルメニュー「選んだモデルを外す」、または Delete（キーを選んでいないとき）。ボーン・モーフを選んでいれば、その持ち主のモデルを外す。ロックしたモデルは外さない。モデルのファイルは消さない。
- 外す操作もモデルの読み込みも、元に戻せる（`ModelPresenceAction`）。**外している間も GPU に載せた形を手放さずに持っておき、戻すときにそのまま使う**（読み直さない）。
- 履歴から消えたとき（古くなった・新しいプロジェクトにした・終了した）に、外したままのモデルだけを手放す。そのため、履歴の操作が `IDisposable` なら、捨てるときに破棄するようにした。終了するときは、描画エンジンより先に履歴を消して手放す。

### 確かめたこと・まだのこと

- 合成した人形と確認用のカメラのモーション（半周してから顔の寄りに切り替わる）で、カメラ視点の区画の動き（正面 → 横 → 背中側 → 寄り → 少し上から）を画面で確かめた。
- モデルを外す（Delete）→ 元に戻す（ツールバー）で、シーン一覧と描画から消えて戻ることを確かめた。
- **実物のカメラのモーションを、MMD 本体と見比べてはいない。** 回転の向きが逆に見えたら、`MmdCamera` の符号を直す。

## 15. 描画の土台（確定・Phase 2 の 9 段階目）

### 描画の重さ（実物のモデルで測った・2026-11-07）

- 条件: YYB式鏡音レン水着（頂点 23,547・材質 16・ボーン 163・モーフ 129）に、主なボーン 10 本と表情 2 つを毎フレーム動かす測定用のモーションを当てて 30 fps で再生。RTX 4060 Ti、Debug ビルド。
- 8 区画（プレビュー 2 枚 × 4 画面）で、1 回の描画にかかる UI スレッドの時間は **約 3.4 ms**（変形 0.3・描画の依頼 1.7・GPU の完了待ち 1.1・表示への反映 0.0 ms）。
- 状態表示の「描画 N 回/秒・X ms」にマウスを乗せると、この内訳が出る（`RenderLoop.Breakdown`）。

### 描画専用スレッドは、今は作らない

- 60 Hz の 1 回分（16.7 ms）に対して 3.4 ms で、UI の操作を妨げるほどではない。重い計算（頂点の変形）は、頂点が 2 万を超えると既に複数の CPU で分けている。
- 分けるには、「エンジンは作ったスレッドからだけ使う」「D3DImage は UI スレッドで開け閉めする」という決まりがあるため、描いた絵の受け渡し（描画先を 2 つ持って交互に使う）と、シーンの値の写しが要る。作りが大きく複雑になるわりに、今は得るものが少ない。
- 見直す目安: GPU の完了待ちが 1 回 5 ms を超えたとき（Phase 4 の影・輪郭線・効果）か、UI の操作中に再生がかくつくとき。内訳の表示で見分けられる。

### GPU が使えなくなったとき（取り外し・ドライバーの更新・応答なし）

- **気づく所:** 描画・GPU の完了待ち・資源の作成で、Direct3D 11 が「デバイスが取り除かれた」と返したとき。WPF へ渡す側（Direct3D 9Ex）が失われたときも同じに扱う。
- **使えない間:** GPU を使う操作は `TT_E_DEVICE_LOST` を返す。変形した頂点・材質の値・区画の大きさの変更は受け取って覚えておく。
- **作り直し（`tt_engine_recover`）:** デバイスを作り直し、ビュー・テクスチャ・メッシュの GPU の資源を全部作り直す。**C# 側の持ち手（`NativeView`・`NativeMesh` など）はそのまま使える**ので、アプリはモデルを読み直さなくてよい。
  - そのため、GPU へ送った中身（テクスチャの画素・頂点・面）を CPU 側にも持っておく。テクスチャの画素の分だけメモリを余分に使う（2048 × 2048 の画像 1 枚で 16 MB）。
  - メッシュを作った後にテクスチャの持ち手を破棄しても、メッシュが使っている画素は残り、作り直しで戻る。
  - D3DImage に渡す面は別の物になる。作り直す前に古い面を D3DImage から外し、作り直した後に新しい面を渡し直す（`DeviceResetting`・`DeviceRestored`）。
- **アプリ側（`RenderLoop`）:** 描画が「GPU が使えない」で失敗したら、区画を止めずに描画を止め、その画面更新を終えてから作り直す。作り直せなければ 1・2・4・8 秒、その後は 15 秒ごとに試し、10 回（約 2 分）で諦めて「作業を保存して、アプリを再起動してください」と出す。再生位置は進み続ける。
  - モデルを GPU に載せる途中で気づいたときは、作り直してから 1 度だけ載せ直す。
  - 状態表示に「作り直しています（n 回目）」「作り直して、描画を再開しました」「作り直せませんでした」を出す。
- **ヘルプ「GPU を作り直す（表示がおかしいとき）」:** 使えなくなったときと同じ手順（気づく → 面を外す → 作り直す → 描き直す）を通す。作り直せずに止まっているときは、もう一度試す。
- **確かめたこと:** 本物の取り外しは起こせないため、試験・診断用に「使えなくなったことにする」関数（`tt_engine_simulate_device_lost`）を足した。C++ と C# のテストで、作り直した後もテクスチャ（持ち手を破棄した物も）・使えない間に送った頂点・大きさの変更が戻ることを確かめた。本物の GPU（D3DImage の共有方式）でも、実物のモデルを出したままヘルプのメニューから作り直し、同じ絵に戻って再生が続くことを確かめた。
- **まだ:** 本物のドライバーの更新・GPU の応答なし（TDR）での確認。

### シーンのカメラの初期位置

- MMD の初期のカメラと同じにした: 注視点 (0, 10, 0)、距離 45、回転 0、視野角 30。人の大きさのモデルなら全身が収まる（確認用の立方体は小さく映る）。

### 作品のフレームの速さを変えたとき

- キーがあれば尋ねる。「はい」= キー・終わりのフレーム・今のフレームを同じ割合で動かし、動きの秒数を保つ。「いいえ」= キーはフレームの番号のまま（動きの速さが変わる。Blender と同じ）。キーが無ければ尋ねずに変える。
- 縮めて同じフレームに重なったキーは後ろのものを使い、数を知らせる。広げるときは、1 フレームしか離れていなかったカメラのキー（切り替え）を段階の補間にする（VMD の読み込みと同じ）。
- フレームの速さの変更は元に戻せる（キーの位置を合わせたときは、そのキーも戻る）。

## 16. 物理演算（確定・Phase 3 の 1 段階目）

### Bullet の取り込み方

- **Bullet Physics 3.25**（2023 年の、今ある中で最新の版。zlib ライセンス）。MMD 本体は Bullet 2.75 を使っているが、使う部品（剛体と、6 自由度のばね付きジョイント `btGeneric6DofSpringConstraint`）は 3.x にも同じものがある。
- 衝突・剛体・数学の 3 つのフォルダだけを `external/bullet3` に**そのまま写した**（約 4 MB、cpp 153 個。入手元と確かめ方は `external/README.md`）。外の道具（vcpkg など）やネットにつながらずにビルドでき、版も固定できるため。最初のビルドが 30 秒ほど長くなる。
- 物理は描画エンジンとは**別の DLL**（`3DTheater.Physics.Native`、公開する関数は `include/tp_physics.h`）。GPU に関係なく、どのスレッドからでも使える（1 つの世界は同時に 1 つのスレッドから）。後で物理を前もって計算しておく（キャッシュ）とき、画面とは別のスレッドで回せる。
- C# 側は `3DTheater.Physics`（`PhysicsWorld` = Bullet の世界、`ModelPhysics` = PMX の剛体とジョイントからモデルの物理を作る）。

### 計算のしかた（saba・three.js の MMD の物理と同じ考え方）

- 物理の世界は**モデルごとに 1 つ**で、モデルの座標で計算する。重力は 98（9.8 × 10。saba・three.js と同じ値）。モデルを傾けて置いたら、重力も傾ける。**モデルどうしの剛体はぶつからない。床（地面）との当たりも無い**（持ち越し）。
- 剛体の種類（PMX）:
  - ボーン追従: ボーンの置き方に合わせて外から動かす（ほかの剛体を押すが、押されない）。
  - 物理: 計算の結果でボーンを置く。
  - 物理＋ボーン位置合わせ: 向きだけ物理に従い、位置はボーン（動かした値）のまま。
- 衝突: 16 個のグループと、「ぶつかる相手」のビット。PMX の仕様では「非衝突グループフラグ」と書かれているが、実際のファイルには「ぶつかる相手」のビット（PMXEditor で「非衝突」に印を付けたグループが 0）が入っている（saba・three.js と同じ扱い）。読み込みの名前を `CollisionMask` に直した。
- ジョイント: 6 自由度のばね付き（PMX 2.0 の標準）と、PMX 2.1 の 6 自由度（ばねなし）。PMX 2.1 の点・円錐・スライダー・蝶番は、まだ使わない（読み込みレポートで知らせる）。
- 剛体とジョイントの回転は、ボーンと同じく Z → X → Y の順。座標は MMD と同じ左手系のまま Bullet に渡す（Bullet の計算は座標系の向きに依らない）。
- 1 フレームを 1/120 秒ずつに分けて進める（30 fps なら 4 回）。ボーン追従の剛体は、前のフレームの置き方から今の置き方まで少しずつ動かす（急に動いたときに、髪が体を突き抜けにくくする）。
- **姿勢の計算の順番（MMD と同じ）:** 物理後でないボーンまで（モーフ・回転・付与・IK）→ 物理 → 物理で動いたボーンの子（物理なし）を求め直す → 物理後のボーン（付与・IK）→ 頂点の変形。
  - 物理で動いたボーンを付与の元にするときは、物理で決まった回転を受け継ぐ。saba は動かした値を受け継ぐが、それでは物理後のボーンが物理に付いていかないため（MMD 本体とは見比べていない）。

### いつ進めるか（`PhysicsClock`）

物理は前の結果に続けて計算するので、フレームが続いているときだけ進め、飛んだときは置き直す。17 章の焼き込みができてからは、焼き込みがまだのフレームと、止まっているときに姿勢を変えた直後だけ、この進め方で計算する。

- 再生中・1 フレーム送り: 進んだフレームの分だけ進める（4 フレームまで）。
- フレームを飛ばした・戻した・ループで先頭へ戻った: 剛体を今の姿勢へ置き直し、ボーンを止めたまま 1 秒分計算して落ち着かせる（置き直すたびに髪が跳ねないように）。
- 止まっているときに姿勢を変えた: 2 秒間、実際の時間で動かして落ち着かせる。その間は描画を続け、その後は止めて休ませる（「編集時は軽く」）。
- 物理の ON / OFF: モデルメニューとツールバーの「物理」。初期値は ON で、プロジェクトに保存する（変えたら題名に「＊」）。「物理をリセット」で剛体を今の姿勢に置き直す。
- 物理の計算に失敗したモデルは、そのモデルの物理をやめて続ける（ログに残す）。物理の DLL が使えなくても、モデルは物理なしで読み込む。

### 重さ

- 実物のモデル（剛体 34 個・うち物理で動くもの 15 個、ジョイント 15 個）を 8 区画に出して再生して、1 回の描画が約 7.8 ms（そのうち変形と物理で 4.4 ms。Debug ビルド）。

### 確かめたこと・まだのこと

- テスト: 自由落下、振り子、衝突のグループ、置き直し、横に伸ばした髪が垂れる・その子（物理なし）が付いていく・物理後のボーンが付与で付いていく、頭を動かすと髪の付け根が付いていく、位置合わせの種類、物理なしのときに計算の結果が変わらないこと、進め方の決め方。
- 実物のモデルで、頭を 70° 傾けたポーズのとき、物理 ON なら前髪などが重力で垂れ、OFF なら頭と一緒に傾くこと、ON に戻すと同じ形に落ち着くこと、暴れないことを画面で確かめた。このモデルは髪が短く、揺れは小さい。
- **MMD 本体と揺れ方を見比べてはいない。長い髪・スカートのモデルでも、まだ試していない。**
- 物理の結果を前もって計算して覚えておくこと（焼き込み）と、フレームを往復しても同じ姿勢に戻ることは、17 章で作った。

## 17. 物理の焼き込み（確定・Phase 3 の 2 段階目）

指示書 Phase 3 の「物理キャッシュ」「スクラブ整合性（再生位置を往復しても姿勢が戻る）」にあたる。

### 何を覚えるか（`PhysicsBake`）

- モデルごとに、**0 フレーム目から 1 フレームずつ順に計算した全剛体の置き方**を、フレームごとに覚える（フレーム × 剛体 × 28 バイト。実物のモデルの 34 剛体・301 フレームで約 0.3 MB）。
- 計算は画面用とは**別の物理の世界**で行う。0 フレーム目は剛体を置き直して 1 秒落ち着かせ、その後は 1 フレームずつ進める（再生と同じやり方）。
- 各フレームのボーン・モーフの値は `PoseSampler` で求める。決まりは `AnimationService` と同じ（未登録の変更がある項目とキーの無い項目は今の値、それ以外はキーの値）で、シーンの値は書き換えない。

### いつ作るか

- 画面の手が空いたとき（WPF の Dispatcher の Background）に、1 回 8 ms ずつ、終わりのフレームまで作る。**UI スレッドで小分けに作る**のは、シーンの値（キーやボーン）を別のスレッドから読まないため（別スレッドにするなら、値の写しを取る仕組みが要る。持ち越し）。
- 実物のモデルで、301 フレームを約 0.8〜1.5 秒で作り終えた（Debug ビルド）。状態表示に「物理を計算中 n / N」と出る。

### 表示のしかた

- 作り終えたフレームは、焼き込みの結果を当てはめる。**どの順で再生位置を動かしても、同じフレームなら同じ姿勢**になる。再生中も物理を計算しないので軽くなった（実物のモデルで、1 回の描画の「変形」が 4.4 ms → 約 3 ms）。
- 足りないときは、少しなら（再生中 10 フレーム・止まっているとき 90 フレームまで）その場で作って追いつく。それより多ければ、画面の物理（16 章の進め方）で見せておき、そのフレームができたら切り替える。

### 作り直すとき

- キー・未登録の印の変更、キーの無い項目と未登録の変更がある項目の値の変更（その値は全フレームに効くため）、モデルの向き（重力の向き）、フレームの速さ、「物理をリセット」、物理を ON にしたとき。
- **キーのある項目の値の変化（再生位置を動かしたときのキーの当てはめ）では作り直さない**（キーから決まる値なので）。
- 今は、変えるたびに 0 フレーム目から作り直す（途中から作り直すには、そのフレームの剛体の速さなども覚える必要がある。持ち越し）。
- 止まっているときに手で姿勢を変えたら、2 秒は画面の物理で揺れを見せ、その後で焼き込みの結果に切り替える（そのとき形が少し変わることがある）。

### 確かめたこと

- テスト: 焼き込みの結果が、最初から続けて計算した結果と同じこと、行き来しても同じ姿勢になること、作り直し、`PoseSampler` の決まり（キー・今の値・未登録の変更）と、どの変更で作り直すか。
- 画面: 実物のモデルで 40 → 10 → 200 → 39 → 40 フレームと動かして、最初に見たフレーム 40 と**画素が完全に一致**した（違う画素 0。比べるための目安として、フレーム 40 と 10 では 7,367 画素違う）。
- 確かめる途中で直したこと:
  - フレームの移動（キーの当てはめ）を「姿勢を変えた」と受け取り、2 秒間画面の物理で見せていたため、行き来すると少し違う絵になっていた。手で変えたときだけ揺らすようにした。
  - ツールバーの「物理」ボタンが、押した状態そのものではなくクリックの知らせで切り替えていたため、キーボードや支援技術から切り替えると表示と中身がずれた。状態で切り替えるようにした。
  - 16 章の「物理 ON・OFF の見比べ」は、このときの確かめ方の誤りで OFF に切り替わっていなかった。正しく切り替えて確かめ直し、ON では前髪などが重力で垂れ、OFF では頭と一緒に傾くことを確かめた。
- 焼き込みの結果は、書き出し（連番・動画。24・25 章）でも使う。

## 18. 音声（確定・Phase 3 の 3 段階目）

指示書 3.1 の「音声のトラック」「音声波形・再生との同期（正確な同期には再生時刻の単一管理が必要）」にあたる。

### 部品: NAudio 2.4.0（`NAudio.Core` と `NAudio.Wasapi`、MIT）

- 最新の 3.x は 2026 年 8 月に出たばかりで、その後 2 か月で 3 回版が上がっている（落ち着いていない）。2.x も 2026 年 8 月に 2.4.0 が出ていて保守が続いているので、2.4.0 を使う。3.x は落ち着いたら見直す（持ち越し）。
- 読み方: WAV（PCM・浮動小数）は直接読み、それ以外（MP3・AAC/M4A・WMA・FLAC）は Windows の Media Foundation で読む。鳴らすのは WASAPI の共有モード（遅れ 60 ms）。
- 部品は `3DTheater.Media`（画面に依存しない）にまとめた: `AudioClip`（長さ・形式・波形）、`AudioPlayer`（鳴らす・鳴っている位置）。

### シーンでの扱い

- シーン一覧の「音声」のまとまりに、音声を 1 つまで置く（MMD と同じく 1 つ）。読み込み（ファイルメニュー・ウィンドウへのドラッグ）・入れ替え・外す（ファイルメニュー・Delete）は元に戻せる。元のファイルは書き換えない。
- プロパティ欄で、鳴り始めのフレーム（負なら音声の頭を飛ばす）と音量（0〜100%）を変えられる（元に戻せる）。シーン一覧の目の印を切ると音を消す。**音を消しても音量 0 で流し続け、時計としては使い続ける**（音を消すとタイミングが変わる、ということが起きないように）。
- 作品が音声より短ければ、音声の終わりまで終わりのフレームを伸ばす。

### 再生の時計（再生時刻を 1 か所で決める）

- `PlaybackService` に外の時計（`IPlaybackClock`）を渡せるようにした。再生中に音声が鳴っていれば、**鳴っている位置（音の出る装置の時計で数えた位置）からフレームを決め、実際の時間を足していかない**。映像と音がずれていかない。
- 時計が少し遅れて見えても（鳴らし始めの直後など）、フレームは戻さない。
- 鳴り始めのフレームより前と、音声が終わった後は、今までどおり実際の時間で進める。
- ループで先頭へ戻ったとき・再生中に位置を飛ばしたとき（鳴っている位置と 3 フレーム以上ずれたとき）は、その位置から鳴らし直す。再生を止めると止める。
- 音の出る装置が無いときは、音なしで再生する（時計は実際の時間）。プロパティ欄に注意を出す。

### 波形

- 1/100 秒ごとのいちばん大きな振れ幅を、別のスレッドで求めておく（20 秒の WAV で数 ms）。
- タイムラインの音声の行と、上の目盛りの帯（薄く）に描く。目盛りの帯にも描くのは、音声の行がスクロールで隠れていても、拍の位置が見えるようにするため。

### 保存

- プロジェクトに、音声の場所（プロジェクトから見た場所と絶対パス）・名前・鳴り始め・音量・鳴らすか・ロックを保存する。見つからなければ知らせ、保存し直しても消さない（モデルと同じ）。

### 確かめたこと・まだのこと

- 音の出る装置で: 頼んだ位置から鳴り始め、実際の時間どおりに進むこと（装置の遅れは約 15 ms で一定）、鳴っている途中で別の位置から鳴らし直せること、最後まで鳴った知らせ。
- テスト: 再生位置が時計に従う・戻さない・時計が答えなければ実際の時間・時計で終わりを越えたらループか止まる、音声の項目（終わりのフレーム・元に戻す・新しいプロジェクトで外す）、保存（相対の場所・見つからなかった音声を書き戻す）、WAV の情報と波形、壊れたファイル。
- 画面（聞こえない 8 Hz の確認音、20 秒）: 波形の山が毎秒（30 フレームごと）の目盛りにそろうこと、3 秒再生して止めたとき、鳴っていた位置（3.122 秒 = 93.6 フレーム）と表示していたフレーム（93）が 1 フレーム以内で合うこと、読み込みを元に戻す・やり直すこと、音声の入ったプロジェクトを開くこと。
- **実際の曲を、耳で聞いての確認はまだ**（利用者の確認を待つ）。止まっているときに再生位置を動かしたときの音（スクラブ）、複数の音声、100% より大きな音量はまだ。

## 19. グラフエディタ（確定・Phase 3 の 4 段階目）

指示書 3.1 の「キーの補間はステップ・線形・ベジェ。グラフエディタをドッキングパネルとして追加」にあたる。

### パネル

- 「グラフ」パネル（初めは下の段の、タイムライン・ログと同じ場所のタブ）。前の版で保存した画面の並びには無いので、起動したときにタイムラインと同じ場所へ足す。
- 対象: タイムラインで選んだキーの項目。キーを選んでいなければ、シーン一覧で選んだボーン・モーフ・カメラ。
- 左: **値のグラフ**。横がフレーム、縦が値。ボーンは移動 X・Y・Z と回転 X・Y・Z（度。1 周を越えても飛ばないようにつなぐ）、モーフは値、カメラは注視点 X・Y・Z・回転 X・Y・Z・距離・視野角。線ごとに出す・隠すを切り替えられる。キーの点、下の帯のキーの印（選んだキーは橙）、今のフレームの線、編集しているキーの範囲（前のキーからこのキーまで）の薄い色を描く。
  - 下の帯のキーの印をクリックでそのキーを選ぶ（Ctrl で足す）。ほかの所をクリックでそのフレームへ。ホイールで左右、Ctrl + ホイールで拡大縮小、「全体を表示」でキーの範囲に合わせる。
- 右: **補間曲線の枠**（MMD と同じく、横が時間の進み・縦が値の進みで 0〜127）。2 つの制御点（赤・青）をドラッグで動かす（1/127 刻み）。数でも入れられる。決まった形のボタン（線形・なめらか・加速・減速・段階）。
  - 曲線の番号は MMD と同じ: ボーン 4 本（移動 X・Y・Z、回転）、モーフ 1 本、カメラ 6 本（注視点 X・Y・Z、回転、距離、視野角）。「全部同じ」で全部の曲線をまとめて変える。グラフでは、編集している曲線で動く線を太く描く。

### どのキーの曲線を変えるか

- 補間曲線は MMD と同じく「前のキーからこのキーまで」の動き方で、後ろのキーが持つ。最初のキーには無い。
- 選んでいるキー（ロックしていないもの）全部に同じ曲線を当てる。**キーを選んでいなければ、今のフレームにあるキー**（MMD の補間曲線の欄と同じ）。
- 段階のキーの点を動かすと、曲線に戻る。

### 元に戻す

- ドラッグ 1 回が 1 つの「元に戻す」（ドラッグ中の右クリック・Esc で取り消し。ギズモと同じ）。数の入力は、同じ欄を続けて変えたら 1 つにまとめる。ボタンはそれぞれ 1 回分。
- 編集の部分は `CurveEditing`（`3DTheater.Editor`）にまとめた: 曲線の読み書き、前のキー、グラフに描く値、0〜127 への丸め。

### 確かめたこと・まだのこと

- テスト: 1 本だけ・全部の曲線を変える、段階から曲線に戻る、モーフ・カメラの曲線、前のキー、グラフの値が曲線に沿うこと・回転が 180° を越えても飛ばないこと、0〜127 への丸め。

## 20. モーフの拡張（確定・Phase 3 の 5 段階目）

指示書 4.3 の「段階対応：フリップ／インパルスモーフ等の PMX 2.1 拡張」「モーフ専用パネルから値変更、プリセット・キーフレーム登録、複数値の混合を行える構造にする」にあたる。

### フリップモーフ（PMX 2.1）

- 決まりは PMX エディタに付く仕様書（PMX 2.1）に従った（MMD 本体は PMX 2.1 に対応していないので、見比べる相手は PMX エディタ）。データはグループモーフと同じ形（モーフの番号と値）。
- 自分の値で、登録したモーフを **1 つだけ** 選ぶ: 番号 = `(int)((登録数 + 1) × 値) − 1`（範囲の外は端に寄せる）。値 0〜1 を（登録数 + 1）に等しく分け、最初の区切りは「どれも選ばない」。選んだモーフの値を、登録の値で **書き換える**（掛け算・足し算ではない）。選ばなかったものはそのまま。
- 求める順（仕様書のとおり）:
  1. 番号の順に、フリップモーフ（グループモーフの中のものは、グループの値 × 割合を値として）で書き換える
  2. もう一度番号の順に、グループモーフの値 × 割合を中のモーフに足す（中のフリップモーフは除く）。グループモーフの値は 1 の後のものなので、**フリップモーフでグループモーフ（表情のまとまり）を切り替えられる**
- グループモーフと違い、選び先に決まりは無い（自分自身・ほかのフリップモーフも選べる）。グループモーフの中のグループモーフは、これまでどおり効かせない（MMD・仕様書と同じ）。
- 計算は `PoseEvaluator`（`FlipIndex` と、モーフの値を求める所）。フリップモーフが無いモデルでは 1 の見回りを省く。

### インパルスモーフ（PMX 2.1）

- 剛体に勢いを与える。データは剛体の番号・ローカルかどうか・移動の速さ・回転の力。物理演算が ON のときだけ効く（焼き込みにも入る）。
- 仕様書のとおり: 値が 0 のモーフは使わない。速さと回転の力が両方 0 の項目は **「止める」**（剛体の速さ・回転の速さ・たまった力を 0 にする）。それ以外は 設定の値 × モーフの値 を、剛体ごとに「剛体の向きで回すもの（ローカル）」と「そのまま使うもの」に分けて足し、止める → 勢いを与える、の順に Bullet の `applyCentralImpulse`・`applyTorqueImpulse` で与える。ボーン追従の剛体には与えない。
- **いつ与えるか**（仕様書には書いていないので決めた）: 物理を進める直前に、**1 フレーム（タイムラインの 1 コマ）につき 1 回**。再生で何フレームか続けて進めるときはその数の分、止まっているときに落ち着かせる間は進めた時間の割合の分。焼き込みも 1 フレームずつ同じに与えるので、画面の計算と焼き込みが合う（テストあり）。
- 物理の DLL に `tp_world_apply_impulses` を足した（API 0.2）。

### モーフのパネル

- 行の右の **◆**（今のフレームにキーがあれば橙、無ければ ◇）で、そのモーフのキーを今のフレームに今の値で登録する（元に戻せる）。
- 未登録の変更があるモーフは名前に「＊」を付け（シーン一覧と同じ）、上に「＊ 未登録の変更 n 個」と「まとめて登録」（このモデルのモーフの未登録の変更を全部キーにする）を出す。
- **表情のプリセット**（下の欄）:
  - 「保存」: **今上の一覧に出ているモーフ**（分類と名前の絞り込みに合うもの）の値を、名前を付けて覚える。0 のモーフも覚えるので、当てると 0 に戻る。目だけ・口だけのプリセットは、分類か名前で絞ってから保存する。名前が空なら「表情 1」のように付け、同じ名前があれば置き換えるかを尋ねる。
  - モーフは **名前で合わせる** ので、同じ名前のモーフを持つモデルなら、別のモデルで作ったプリセットも使える（行の「2/2」は、このモデルで合うモーフの数 / 覚えている数）。
  - 置き場所: `%APPDATA%\3DTheater\UserSettings\morph-presets.json`。画面の設定と同じく利用者ごとで、プロジェクトには入れない。プリセットの一覧の変更は元に戻すの対象にしない。読めないファイル（壊れた・新しい版）は上書きしない。
- **混ぜる**（指示書の「複数値の混合」）: プリセットごとの割合（0〜100%）のつまみ・数で、すぐ当てる。値 = 基準 + Σ 割合 ×（プリセットの値 − 基準）（0〜1 に収める）。基準は混ぜ始めたときの値で、割合を全部 0 に戻すと基準に戻る（「混ぜる前に戻す」）。「当てる」はそのプリセットを 100% にする。
  - 手で値を変えた・再生位置を動かした・元に戻したなど、ほかの操作で値が変わったら、その値を新しい基準として割合を 0% に戻す（値はそのまま）。
  - 続けて変えた分は 1 つの「元に戻す」にまとめる（まだ触っていないモーフを持つプリセットを混ぜ始めたところからは、新しい 1 つ）。混ぜた値も、手で変えたのと同じく未登録の変更になる（自動キーが ON ならキーになる）。ロックしたモーフは変えない。
- 編集の部分は `MorphPreset`・`MorphPresetLibrary`・`MorphMixSession`（`3DTheater.Editor`）。

### 確かめたこと・まだのこと

- テスト: フリップの区切り方と端、選んだものだけを書き換えること、グループモーフの切り替え、グループの中のフリップ、番号の順。インパルスで剛体が押した向きへ振れ・値が大きいほど強いこと、ローカルは剛体の向きで回すこと、止める、ボーン追従の剛体は押さないこと、焼き込みと画面の計算が合うこと、物理の DLL の勢いの受け渡し。プリセットの保存（0 も覚える・名前で合わせる）・一覧の置き換え・名前の変更・保存と読み込み・壊れた項目、混ぜた値・元に戻す・ほかの操作で基準が変わること・ロック。
- 画面（実物のモデル）: まばたきを 1 にすると「＊」と「未登録の変更 1 個」が出ること、◆ でキーを登録して ◆ が橙になり、元に戻すと ◇ に戻ること、プリセットを 2 つ保存（ファイルにも書かれる）、「すべて 0」の後に「目を閉じる」50%・「口を開ける」100% で、目が半分閉じ口が開くこと、元に戻す、「当てる」、手で値を変えると割合が 0% に戻ること、確認してから消すこと。ログにエラーなし。
- **フリップ・インパルスモーフを持つ実物のモデル（PMX 2.1）では、まだ試していない**（手元に無い。テストのモデルでだけ確かめた）。インパルスの強さを PMX エディタと見比べることもまだ。
- プリセットの名前の変更（作りはあるが画面にはまだ）、並べ替え、ファイルとしての書き出し・読み込み（ほかの人と分ける）はまだ。

## 21. 元に戻す・やり直しの検証（確定・Phase 3 の 6 段階目）

指示書 Phase 3 の「Undo/Redo の検証」にあたる。

### 確かめ方（`UndoRedoVerificationTests`）

- 乱数で選んだ編集を 120 回続ける: ボーンの移動（続けた分はまとまる）・回転、モーフの値、カメラ、キーの登録、未登録の変更をすべて登録・破棄、キーの削除・移動・複製・補間・補間曲線・コピーと貼り付け、ドラッグ（確定・取り消し）、フレームの速さの変更（キーも合わせる・そのまま）、表情の混合、鍵、モーフをすべて 0、それに履歴に積まない操作（再生位置の移動・自動キーの切り替え）。
- 各時点の状態（シーンの全項目の値とキー、フレームの速さ・終わりのフレーム）を覚え、**全部元に戻すと 1 つずつ前の状態に、全部やり直すと 1 つずつ後の状態に、ぴったり（数の 1 桁も違わず）戻る** ことを確かめる。途中まで戻して新しく編集すると、やり直しの履歴が消えることも。これを 100 通りの乱数で行う（1 秒ほど）。
- キーのある項目の値は再生位置で決まり、元に戻すは再生位置を動かさない決まりなので、比べる前に、その状態を覚えたときのフレームへ移る。

### 見つかって直したこと

- **自動キーを途中で切り替えると、やり直しでキーが戻らないことがあった**: 自動キーが ON の操作（キーも写す）のすぐ後に、同じ値を OFF で変えると、2 つが 1 つの「元に戻す」にまとまり、後のほう（キーを写していない）の写しでやり直していた。キーを写したかどうかが違う操作はまとめないようにした（`EditService.Change`）。
- **ボーンの回転を元に戻すと、値がごくわずか（7 桁目）ずれることがあった**: 回転を入れるたびに長さを 1 にそろえ直していたため、写した値を戻しても同じにならなかった。長さがほぼ 1 なら、そのまま使うようにした（`BoneNode.Orientation`）。見た目には分からない差だが、「変わったかどうか」の判定や、保存したプロジェクトの差に出うる。
- どちらも、短いテストも足した。

### 範囲

- この検証は編集の部分（`3DTheater.Editor`）の操作が対象。モデルの読み込み・外す、音声の読み込み・外すは画面側の操作で、これまでの段階で画面で確かめている（14 章・18 章）。

## 22. トゥーン描画と輪郭線（確定・Phase 4 の 1 段階目）

指示書 6.1 の「トゥーン: MMD に近いトゥーンテクスチャ、セル影、輪郭線、材質単位の表現、スフィアマップ的処理」と、Phase 4 の「基本トゥーン描画・輪郭線」にあたる。影（セルフシャドウ・地面の影）と PNG の書き出しは次の段階。

### 色の計算（MMD と同じ）

- MMD の照明は「拡散」が 0 で、「環境」と「反射」が照明の色という決まりなので、材質の色は次のとおり:
  - 色 = (材質の拡散色 × 照明の色 + 材質の環境色)（0〜1 に収める）、不透明度 = 拡散色の a
  - × テクスチャ → スフィア（掛ける .sph・足す .spa） → × トゥーン → + 反射光（反射色 × 照明の色 × 強さ）
- **トゥーン**: 光の当たり方（面の向きと光の向きの内積、-1〜1）で、トゥーンの画像の上（光の当たる側）から下（反対側）を読む（`0.5 − 内積 × 0.5`）。トゥーンの無い材質には陰影を付けない（MMD と同じ。トゥーンの無い PMX は平らに見える）。
- **スフィア**: カメラから見た面の向きで、スフィアの画像を読む。追加 UV を使う「サブテクスチャ」はまだで、読み込みレポートに知らせてスフィアなしで描く。
- **材質モーフ**: テクスチャ・スフィア・トゥーンの色の掛ける値・足す値、輪郭線の色と太さも変わる（「元の色 × 掛ける + 足す」）。

### 共有トゥーン（toon01〜toon10）

- 材質が共有トゥーンを指すときは、MMD 付属の toon01.bmp〜toon10.bmp を使う決まり。**MMD 付属の画像は再配布できないのでアプリには入れない**。
  - モデルのフォルダから上へたどって、MMD のフォルダ（`Data\toon01.bmp`〜`toon10.bmp` がある所）が見つかれば、利用者の手元のその画像を使う（MMD の `UserFile` の下にモデルを置いている場合）。
  - 見つからなければ、**自前の画像**（`DefaultToons`。上半分が白、下半分が影の色で、境目を少しぼかす。影の色は灰色・肌・水色などを自前で決めた）を使う。MMD の見た目とは影の色が少し違う。
- モデルのトゥーンがファイル名だけで「toon01.bmp」などを指していて、そのファイルがモデルの横に無いときも、共有トゥーンとして扱う（MMD と同じ。古いモデルに多い）。決め方は `PmxToon`。

### 照明

- シーンの照明の項目（最初の 1 つ）を使う。向きは項目の回転で、回していないときに +Z を向く（カメラと同じ決まり）。色は MMD の初期値 154/255 × 明るさ。**照明を隠すと照明なし**（材質の環境色だけ）。
- 新しいシーンの照明は、MMD の初期の向き（光が進む向き (-0.5, -1, 0.5)。回転 X 54.7°・Y -45°）にした。前の版で保存したプロジェクトは、保存した向き（X 45°・Y -30°）のまま開く。
- 照明の色の設定、VMD の照明のキーはまだ。

### 輪郭線

- 材質の「エッジ」が ON のときに描く。モデルの材質を全部描いた後に、裏側の面だけを、**画面の上で**法線の向きへ決まったピクセルだけ広げて描く（表の面の外にはみ出した分が線になる）。遠くても近くても、画面の上で同じ太さ。
- 太さ（ピクセル）= 材質のエッジの太さ × 頂点のエッジの倍率 × 1 あたりのピクセル。1 あたりのピクセルは、画面の高さ 1080 までは 1、それより大きい画面・書き出しでは高さに比例させる（4K の書き出しでも 1080 のときと同じ割合に見えるように）。そのため、小さなプレビューでは書き出しより線が少し太く見える。
- 線の色はエッジの色。不透明度は エッジの色の a × 材質の不透明度（材質モーフで消した部分の線も消える）。
- 両面の材質を裏から見たとき、同じ奥行きの面を線の色で塗りつぶさないよう、線の奥行きを少し奥へずらしている。
- MMD 本体の線の太さとの見比べはまだ（手元に MMD が無い）。

### 描画エンジン（API 0.6）

- 材質に、トゥーン・スフィアのテクスチャ、スフィアの使い方、輪郭線の色・太さを足した。頂点ごとの輪郭線の倍率は、変形する頂点とは別の、変わらないバッファーに入れる（毎フレーム送らない）。
- 1 枚の描画の条件に、照明の向き・色と、輪郭線の 1 あたりのピクセルを足した（照明は `TT_FRAME_USE_LIGHT` のときだけ。無ければ MMD の初期の照明）。
- トゥーン・スフィアは端で止める読み方（トゥーンの上端と下端の色が混ざらないように）。

### 確かめたこと・まだのこと

- テスト（描画エンジン、ソフトウェア描画）: トゥーンで光の当たる側と反対側の色、照明の色、スフィアの掛ける・足す、輪郭線が面の外にだけ出ること・太さ 0 と材質モーフで消えること、知らないスフィアの使い方を断ること。C# からも、構造体の並びが合っていて、トゥーン・照明・輪郭線が届くこと。材質モーフ（輪郭線・スフィア・トゥーン）、トゥーンの決め方、自前のトゥーンの画像、照明の向き（新しいシーンが MMD の初期の向き）・隠したとき・輪郭線のピクセル。
- 画面（実物のモデル）: カメラを顔に寄せて、髪と目のスフィアの光沢、髪・顔の輪郭線、トゥーンの陰影が出ること。照明を横から当てると、照らした側が明るく、反対側にトゥーンの影の色が付くこと。
- **MMD 本体と並べての見比べはまだ**（手元に MMD が無い）。影（セルフシャドウ・地面の影）、PNG の書き出しは次の段階。

## 23. 影（セルフシャドウ・地面の影）（確定・Phase 4 の 2 段階目）

Phase 4 の「影」にあたる。MMD の 2 種類の影を作った。どちらもレンダリングのメニューで ON / OFF でき（初期値は ON）、プロジェクトに保存する（前の版のファイルは ON）。

### 地面の影

- 材質の「地面影」が ON の部分を、照明の向きに沿って高さ 0 の床へ押しつぶして描く（床から 0.01 だけ浮かせる）。色は半透明の黒（不透明度 0.5。自前で決めた値で、色の設定はまだ）。
- 重なった所が二重に濃くならないよう、ステンシル（画面の点ごとの印）で 1 点 1 回だけ塗る。モデルより先に描き、モデルの奥行きで隠れる所は後から描くモデルが上書きする。
- 下から・真横から照らすときは描かない。不透明度 0 の材質（材質モーフで消した部分）は描かない。

### セルフシャドウ

- 照明から見た奥行きの画像（2048 × 2048。描画の条件で 256〜8192 に変えられる。書き出しで大きくする予定）を作り、各点が照明から見てほかの面より奥にあるかで影を決める。境目は周りの 9 点を比べてぼかす。
- 範囲は自動: 照明から見た縦横は「影を落とすモデル」の囲みの箱が全部入るように、奥行きは「影を受けるモデル」も入るように（影を落とすものより照明から遠い床などを範囲の外にしないため）。MMD の「影範囲」の設定は無い。
- 影を落とすのは材質の「セルフ影マップ」（影を落とす）、受けるのは「セルフ影」（受ける）が ON の材質。不透明度 0 の材質は影を落とさない。
- **影を受ける材質は、MMD のセルフシャドウの描き方にする**: 光の当たり方（面の向きと光の向きの内積 × 3 を 0〜1 に収めた値）と、影の当たり方の小さいほうで、「影の色（色 × トゥーンのいちばん下の色）」と「光の当たる色（色 + 反射光）」を混ぜる。セルフシャドウを使うと、トゥーンの段階の画像ではなくこの決まりで陰影が付く（MMD と同じ）。そのため、トゥーンの無い材質（いちばん下が白）には影がほとんど見えない（MMD と同じ）。
- 影が自分の面に細かく落ちないよう、奥行きの画像は面の傾きに応じて奥へずらして描き、比べるときもワールドの長さで 0.08 だけ奥へずらす。
- 奥行きの画像は、描くたびに作り直す（画面が 8 区画なら 8 回）。モデル 1 体では軽いが、重くなったら 1 回の更新で 1 度だけ作るようにする。4096 にしても、試したモデルでは見た目はほとんど変わらなかった。

### 描画エンジン（API 0.7）

- 材質の旗に、地面影・影を落とす・影を受ける を足した。描画の条件に、セルフシャドウ・地面の影の旗、地面の影の色、奥行きの画像の大きさを足した。
- セルフシャドウを使わない間は、奥行き 1（何も無い）の 1 × 1 の画像を渡す（読み方の決まりに合わない画像を渡さないため）。

### 確かめたこと・まだのこと

- テスト（描画エンジン、ソフトウェア描画）: 地面の影が床を半透明の黒で暗くし、2 つの影が重なっても二重に暗くならないこと、地面影の無い材質・影を使わない描画・下からの照明では落ちないこと。セルフシャドウが受ける材質にだけトゥーンのいちばん下の色で落ち、光の当たる所は元の色のままなこと、受けない材質・使わない描画では落ちないこと。設定の保存と、前の版のファイルが初期の設定になること。
- 画面（実物のモデル）: 床に地面の影、首と胸にあごの影が落ちること。メニューで切り替えると消え、題名に「＊」が付き、閉じるときに保存を尋ねること。

## 24. PNG の書き出し（確定・Phase 4 の 3 段階目）

指示書 6.3 の「初期: PNG 静止画、透過 PNG（RGBA）、PNG 連番。解像度・フレーム範囲・背景透過を設定可能」「描画ギズモ、ボーン、グリッド、UI は通常の最終出力に映り込まない」「進捗、キャンセル、失敗理由を通知」と、Phase 4 の「カメラ、PNG／アルファ付き連番出力」にあたる。

### 画面（レンダリングのメニュー「静止画を書き出す」「連番を書き出す」、ファイルのメニューからも）

- 書き出すもの: 静止画（今のフレーム。フレームは変えられる）か、連番（フレームの範囲。初めは 0〜作品の終わり）。
- 大きさ（よく使う大きさの一覧あり）、なめらかにする（初期値 ON）、背景（透明か、#RRGGBB の色。初期値は白）、書き出し先。
- 書き出し先の初めは「ピクチャ\3DTheater\（プロジェクトの名前）.png」、連番はその名前のフォルダの中。連番は名前の後ろに「_フレームの番号」を、最後のフレームの桁数（4 桁以上）にそろえて付ける（shot_0000.png …）。同じ名前のファイルがあれば、まとめて置き換えるかを尋ねる。
- 書き出し中は進み具合（何枚目・どのフレーム）を出し、「閉じる」が「やめる」になる。やめた・失敗したときは、何枚目まで書いたかと理由を知らせ、ログにも残す。終わったら書き出し先のフォルダを開くかを尋ねる。
- 設定は次に開いたときのために覚える（利用者ごとの設定。プロジェクトには入れない）。

### 描き方

- **シーンのカメラ（カメラ視点）から描く**。映すのはモデルだけで、格子・座標軸・ボーン・ギズモ・選択の枠・**確認用の立方体**は映さない（確認用の立方体はシーンの項目だが、作品の一部ではないので書き出さない）。照明・影・輪郭線はプレビューと同じ設定で、輪郭線の太さは書き出す高さに合わせる（22 章）。セルフシャドウの奥行きの画像は 4096 にする。
- 書き出し専用の画面外の描画先を作り、1 フレームずつ「そのフレームへ移る → 変形 → 描く → 読み出す」。縮小と PNG への変換・保存は別のスレッドで行い、2 枚まで並べて進める。終わったら（やめた・失敗したときも）元のフレームに戻す。
- **なめらかにする**: 2 倍の大きさで描いて、2 × 2 点の平均で縮める（線や輪郭のギザギザが減る）。描ける大きさの上限（1 辺 16384）があるので、なめらかにするときは 1 辺 8192 まで。
- **透明**: 背景を透明で消してから描く。半透明の材質や地面の影を重ねた結果、読み出した色は「透明度をかけ合わせた値」になるので、縮めた後に色を透明度で割り戻して（透明な点は黒）、PNG の決まりに合わせる。縮めるのは割り戻す前（透明な点の色が混ざって縁が黒ずまないように）。背景が不透明なときは、透明度の無い PNG にする。
- **物理**: 書き出す間は、どのフレームも焼き込みの結果で描く（姿勢を変えた直後でも）。足りないフレームは、その場で必要なだけ計算する（17 章の「追いつく上限」を外す）。プレビューと同じ姿勢になる。
- フレームの速さは作品と同じ（1 フレーム 1 枚）。作品と違う速さでの書き出しはまだ。

### 描画エンジン（API 0.9）

- 描画の条件に、背景の色（`TT_FRAME_CLEAR_COLOR`、透明も可）を足した。

### 確かめたこと・まだのこと

- テスト: 連番のファイル名（桁数）、設定の確かめ（大きさ・上限・フレームの範囲・書き出し先）、縮小（透明な所の色が混ざらない）、透明度の割り戻し、色の文字の読み書き。描画エンジン: 決まった色・透明な背景で消せること、透明な背景に半透明の物を描くと透明度をかけ合わせた色で残ること。
- 画面（実物のモデル・測定用のモーション）: 連番（透明・640 × 360・なめらか・11 枚）と静止画（白・1280 × 720・フレーム 30）を書き出し、透明な背景に地面の影が半透明で残ること、静止画にフレーム 30 の姿勢が出ること、余計な物が映らないこと、終わったら元のフレームに戻ることを確かめた。1920 × 1080・なめらかで、1 秒に約 20 枚。途中で「やめる」と、54 枚目までで止まり、書きかけのファイルが残らないこと。
- 開いたときに書き出し先の欄が空になる誤りを、画面での確認で見つけて直した。
- 動画は 25 章。JPEG・作品と違うフレームの速さ・背景の画像・ギズモなどを映す書き出しはまだ。

## 25. 動画の書き出し（確定・Phase 4 の 4 段階目）

指示書 6.3 の「発展: H.264/MP4 動画」と、Phase 4 の「動画出力」にあたる。透明な動画（アルファ対応の透過動画）はまだ。

### 方式（持ち越し事項「動画の書き出し方法」への答え）

- Windows に入っている Media Foundation の書き手（Sink Writer）で、MP4（映像は H.264 の High、音声は AAC）を書く。ffmpeg などは同梱しない（配布の大きさと、ライセンス・特許の扱いが重いため）。GPU の符号化の部品があれば、Windows が選んで使う。
- C++ の DLL `3DTheater.Video.Native`（公開する関数は `include/tv_video.h`、API 0.1）に分けた。描画エンジン・物理とは別。C# 側は `3DTheater.Media` の `VideoWriter`（書き手と、確かめる用の読み取り）と `AudioExportSource`（動画に入れる音声）。
- 1 つの書き手は、作ったスレッドで使い続ける（COM を MTA で使う）。アプリでは書き出し専用のスレッドを 1 本立てる。

### 映像

- 描き方は 24 章と同じ（シーンのカメラ、なめらかにする、物理は焼き込みの結果）。描画と読み出しは UI のスレッド、縮小・色の変換・符号化は書き出し用のスレッドで行い、3 枚まで先に描いておける。
- **色**: BGRA を自前で YUV（NV12、BT.709、明るさ 16〜235）に変換して渡し、その決まりを動画に書き込む（H.264 の VUI と MP4 の colr）。Windows の変換に任せると、小さい動画（640 × 360 など）は BT.601 で変換され、決まりも書き込まれないため、再生ソフトが別の決まりで読むと色がずれる（赤の緑が 25 段ほど）。自前の変換にしてからは、どの大きさでも、書いた色と読み戻した色の差は 0〜3 段（H.264 そのものの分）。
- **大きさ**: 幅と高さは偶数（H.264 の決まり）、各 64〜4096、合わせて 4096 × 2304 の画素まで（縦長の 4K の 2160 × 3840 も書ける）。32 × 32 以下は、この PC の符号化の部品が受け付けなかったので、下限を 64 にした。
- 透明にはできない（動画のときは透明のチェックを使えなくする。PNG のための透明の設定は覚えたまま）。
- **画質**: 1 秒あたりのデータの量 = 幅 × 高さ × フレームの速さ × 0.1（高画質は 0.2）を、1〜100 Mbps に収める。フル HD・30 fps で約 6 Mbps（高画質は約 12 Mbps）。
- フレームの速さは作品と同じ。各フレームの時刻は「フレームの番号 ÷ フレームの速さ」。

### 音声

- 「シーンの音声を入れる」は、シーンに音声があり、見えていて（目の印）、ファイルがあるときに選べる（初期値は入れる）。選べないときは、その訳を横に出す。
- 動画の 0 秒（最初のフレーム）に、音声の「（最初のフレーム − 鳴り始めのフレーム）÷ フレームの速さ」秒目を合わせる。音声より前と、音声が終わった後は無音で埋める。音量の設定を掛ける。
- 48 kHz・2 チャンネル・16 ビットにそろえて（モノラルは両方へ、3 チャンネル以上は 2 つに混ぜる、違う周波数は変換する）、AAC（192 kbps）にする。
- 映像のフレームを書く前に、そのフレームの終わりの時刻までの音声を書く（映像と音声を交互に入れる）。音声の時刻はサンプルの数で数えるので、ずれが積み重ならない。

### 画面（レンダリングのメニュー「動画を書き出す（MP4）」）

- 書き出しの画面に「動画（MP4）」を足した。フレームの範囲（初めは 0〜作品の終わり）、大きさ、なめらかにする、背景の色、画質（標準・高画質）、シーンの音声を入れる、書き出し先（初めは「ビデオ\3DTheater\（プロジェクトの名前）.mp4」）。設定は次に開いたときのために覚える。
- 「名前.書き出し中.mp4」に書き、書き終えてから「名前.mp4」に置き換える（入れ物の形式は拡張子で決まるので .mp4 のまま）。やめた・失敗したときは書きかけを消し、同じ名前の元のファイルはそのまま残る。同じ名前のファイルがあるときは、書き出す前に置き換えるかを尋ねる。
- 進み具合は「何フレーム目 / 全部」で出す。終わったら、フレームの数・秒数・音声のあり／なしを知らせ、フォルダを開くかを尋ねる。

### 確かめたこと・まだのこと

- テスト: MP4 を書いて読み戻す（大きさ・フレームの速さ・長さ・音声の形式、上下が逆さまでないこと、色の決まりが書く側と読む側で合っていること）、音声なしの動画、奇数の大きさや対応しない音声を断ること、同じ名前のファイルを置き換えて書けること、音声の位置合わせ（前の無音・途中から・音量・周波数の変換）、動画の設定の確かめ（偶数・上限・下限・データの量）。
- 画面（実物のモデル・測定用のモーション・聞こえない確認音）: 0〜90 フレームを 1280 × 720・なめらか・音声ありで書き出し（約 4 秒かかった）、1280 × 720・30 fps・約 3.05 秒・音声 48 kHz 2 チャンネルの MP4 になった。最初のフレームは、同じフレームの静止画（PNG）と比べて平均 0.19 段の差（99% の画素は 5 段以内）。同じ名前のファイルがあるところへ 1920 × 1080 で書き始めて「やめる」と、元のファイルが残り、書きかけも残らないこと。終わったら元のフレームに戻ること。1920 × 1080・なめらかで、1 秒に約 15 フレーム。
- 色の変換が大きさで変わることは、確認のための試しで見つけて直した。
- **ほかの再生ソフト（ブラウザー・動画サイトなど）での見え方と音のずれはまだ**（この PC には ffmpeg などの調べる道具が無く、Windows の部品で読み戻して確かめた。色の決まりが書き込まれていることは、ファイルの中身を読んで確かめた）。実際の曲を入れて、耳で音と映像が合っているかもまだ。
- 透明な動画、H.265、作品と違うフレームの速さ、音声だけの書き出しはまだ。

## 26. 描画品質の設定（確定・Phase 4 の 5 段階目）

指示書 6.1 の「編集用の軽量描画と、書き出し用の高品質描画を分離する。プレビュー品質プリセットも設ける」と、持ち越し事項の「描画のなめらかさ（MSAA）」にあたる。レンダリングのメニューの「描画品質の設定」（前は「予定」）を使えるようにした。

### プレビューの品質（利用者ごとの設定。プロジェクトには入れない）

| 品質 | なめらかさ（MSAA の 1 画素あたりの点の数） | セルフシャドウの奥行きの画像 |
|---|---|---|
| 軽い | なし（1 点） | 1024 |
| ふつう（初期値） | 4 点 | 2048（今までと同じ） |
| きれい | 8 点 | 4096 |

- 選ぶとすぐに全プレビューへ反映し、終了時に利用者の設定（`settings.json` の `Rendering`）へ保存する。
- GPU が使えない点の数のときは、描画エンジンが使える中でいちばん近い少ない数にする（ログに 1 度だけ残す。設定の画面にも「この GPU で使えるなめらかさは n 倍まで」と出す）。
- MSAA の描画先（1 点ごとに色 4 バイト・奥行き 4 バイト）が 1 つの区画で 512 MiB を超える大きさでは、収まるまで点の数を半分にする（4K の 1 画面で「きれい」の 8 点は約 506 MiB で、まだ収まる）。区画を大きくして点を減らすときは、大きな描画先を作る前に減らす。

### 書き出しの品質

- プレビューの品質に関係なく、4 点・影 4096（`RenderQuality.Export`）。「なめらかにする」では、さらに 2 倍の大きさで描いて縮める。そのときは描く大きさが 2 倍になるので、上の 512 MiB の決まりで点が減ることがある（4K をなめらかにして書き出すと 8K で描くので 2 点）。作れなかったときは MSAA なしで描く。
- 書き出しの間はプレビューを描かない（`RenderLoop.IsSuspended`）。今までは、書き出しのフレームごとにプレビューまで描き直していた。終わったら描き直す。

### 描画エンジン（API 0.10）

- `tt_view_set_sample_count`（1・2・4・8）。ビューの中に MSAA の描画先と奥行きを持ち、描いた後に、表示・読み出しに使う面（D3DImage と共有する面・スワップチェーンの面）へまとめる（Resolve）。共有する面は変わらないので、WPF 側で面を渡し直さなくてよい。
- MSAA の描画先では、線（格子・座標軸・ボーン・ギズモ・選択の枠）を四角形として描く設定にして、線もなめらかにする（1 点のときより少し太く見える）。
- 作れなかったとき（メモリ不足など）は 1 点に戻して描ける状態にしてから、失敗を知らせる。GPU を作り直すときは、頼まれた点の数で作り直す（新しい GPU で使える数に合わせる）。

### 確かめたこと・まだのこと

- テスト: 斜めの四角形の縁に中間の色ができること（1 点では出ない）、使えない数の扱い、大きさを変えても・大きさ 0 の間に変えても・GPU を作り直しても保たれること、ウィンドウ用のビューでも描けること、C# から変えて読み出せること。品質ごとの値、メモリの上限での減らし方、設定が変わったときだけ知らせること。
- 画面（実物のモデル・顔の寄りのカメラ視点と自由視点）: 3 つの品質を切り替えて撮り比べ、「軽い」は線や髪の縁がギザギザ、「ふつう」「きれい」はなめらかになること。終了時に品質が保存されること。書き出しの後にプレビューが描き直されること。
- 重さ（GeForce RTX 4060 Ti。2 つのプレビューを 4 分割した 8 区画で、測定用のモーションを再生）: 1 回の描画の GPU 待ちは、軽い 1.2 ms・ふつう 2.3 ms・きれい 2.6 ms（全体では 6〜7 ms）。15 章の目安（5 ms）より小さいので、描画専用のスレッドへはまだ分けない。
- 書き出し: 連番 61 枚（1920 × 1080・なめらか・4 点）が、押してから知らせが出るまで 3.8 秒。
- 弱い GPU（内蔵の GPU など）での重さと、ソフトウェア描画（WARP）での画面の確認はまだ（WARP での MSAA と読み出しはテストで確かめた）。
